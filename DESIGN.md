# PassBundle design

Status: draft, 2026-10-14. Decisions here are made unless marked "open".

## Goals

1. Onboarding that needs nobody on the phone. Install, sign in, and the vault fills itself from the browsers already on the machine.
2. Sane defaults. Nothing a business expects should require building policies first.
3. Better autofill and passkeys than upstream, proven by numbers, not claims.
4. Managed by MSPs through the RMM they already have. Entra is optional.
5. Tested by machines. A person looks only at red builds.

## Architecture

### Server

- Fork of Vaultwarden (`passbundle-server`), AGPL-3.0.
- Postgres in production. SQLite stays supported for self-hosters.
- Individuals and families share pooled instances. Each business org gets its own instance.
- Cloudflare in front: WAF, and rate limits on the login and identity endpoints.
- The server never holds a key that can decrypt a vault. Any feature that would need one is redesigned or dropped.

### Clients

- **Our own apps for desktop and mobile** (decided October 20, 2026). Bitwarden's format and our server stay for storage and encryption; the apps are ours.
  - **One look everywhere:** one Flutter app for Windows, macOS, Linux, iOS, and Android, with our own design (brand colors, bundled Google Sans Flex), light and dark. It doesn't try to look like each OS.
  - **One core:** a Rust library (`docs/core.md`) does everything but drawing: keys, the vault format, sync, search, one-time codes. A logic bug shows up everywhere or nowhere.
  - **Small native pieces only where an OS insists**, such as the phones' autofill, drawn from the same design.
  - **Desktop:** the window is part of the tray app. Closing the window ends its process, leaving only the small agent.
  - **Order:** the core, then desktop (Windows, macOS, and Linux), then mobile (`docs/phones.md`: Android first, then iOS).
  - **Status (October 21, 2026):** in the public repo `PimpinPumpkin/passbundle-apps`, whose CI builds, tests, and measures it on Linux, macOS, and Windows.
    - **The core** follows its design and vectors, and signs in, syncs, saves, and does two-step login on a real server (see `docs/core.md`, "Tests").
    - **The app** signs in to a PassBundle server, unlocks offline or with Windows Hello (through the desktop agent), copies through the core, adds, edits, and trashes items, and locks by itself after a chosen time or when the computer sleeps (`docs/core.md`, "Locking by itself").
    - **Android** (`docs/phones.md`):
      - The core is built with the NDK for phones and the emulator.
      - The app opens the vault kept in its own folder. It copies straight from the core to the clipboard through Kotlin, marked sensitive and cleared after 30 seconds. It checks certificates with Android's own verifier.
      - It keeps the session's refresh token sealed with a key in the Android Keystore.
      - It unlocks with the phone's biometrics. The user key is sealed with a Keystore key that needs the person's strong biometrics for each use and is voided when a fingerprint or face is added. It goes from the Keystore to the core without passing through Dart.
      - It locks the phone way: after a time away (5 minutes by default, or "Immediately"), when the phone locks, and it checks on coming back. The vault stays out of screenshots and the app switcher.
      - It fills other apps' and browsers' sign-in forms as Android's autofill service. Logins match by an app's `androidapp://` link or the page's registrable domain, the domain only from a browser on Google's privileged list (by signing certificate) or one the person trusted, so another app can't say it's a website. A password is taken from the core only once someone picks its login, and a locked PassBundle offers to unlock first. Signing in somewhere with something new, Android offers to save it to PassBundle, which opens the editor filled in, or the login it updates.
      - CI runs it all on an Android 10 emulator: the core's tests, the app's own tests (signing in to a real server through adb), and filling a test app's sign-in form through autofill (and not giving its screen that says it's a website that website's login until it's trusted as a browser), then saving a new sign-in from it and a new password for it. Biometric unlock uses debug builds' stand-in for Android's prompt there. The app's tests also pass on a real Pixel.
      - The real biometric prompt gets checked by hand on a phone.
    - **iOS** (`docs/phones.md`):
      - The core is a static library in an XCFramework, linked into the app, where Dart finds it in the process.
      - The app opens the vault kept in its own folder. It copies straight from the core to the pasteboard through Swift, for this device only and expiring after 30 seconds. It checks certificates with iOS's own verifier.
      - It keeps the session's refresh token in the Keychain, and unlocks with Face ID or Touch ID: the user key is a Keychain item for this device only that needs the person's current biometrics, voided when a face or finger is added. It goes between the Keychain and the core without passing through Dart.
      - It locks the phone way, as on Android, including when the phone locks. The vault stays out of the app switcher's snapshot.
      - CI runs it on an iPhone simulator: the core's tests, and the app's own tests (signing in to a real server on the runner), with debug builds' stand-in for the Face ID prompt.
      - Next: the AutoFill extension. The real prompt gets checked by hand on an iPhone.
    - **The prototype, measured in CI** (first launch on CI machines; Linux in a virtual display with software rendering, which inflates its memory):

      | | Windows | macOS | Linux |
      |---|---|---|---|
      | Download, compressed | 12.3 MB | 17.5 MB | 10.2 MB |
      | First frame | 1.3 s | 2.1 s | 3.8 s |
      | Memory, vault open | 103 MB private | 42 MB footprint | 290 MB (software rendering) |
- Open-source build of the Bitwarden clients (`passbundle-clients`), rebranded: web vault, browser extension, CLI. The extension and web vault stay upstream's for now, and can move onto the core later, compiled to WebAssembly.
- **No Electron.** We don't ship upstream's Electron desktop app (about 150 MB on disk and hundreds of MB of RAM for what is mostly a tray icon). The desktop side is a small native agent. See "Desktop agent" below.
- Mobile push delivery is our own (APNs, FCM, and UnifiedPush on Android).
- The SDK comes from the upstream open-source `sdk-internal` build. Fork it only when we need to change it.

### Desktop agent (no Electron, no web view)

One small native app per computer, written in Rust. No bundled browser engine and no web view.

- **No windows in version 1.** It lives in the tray (menu bar on macOS) with a native menu, and talks through native notifications. Anything visual, like onboarding steps, the vault, or settings, opens in the browser extension or the web vault, which people already have.
- **What it does:**
  - Unlocks the extension with Windows Hello or Touch ID, and unlocking one unlocks the other (the 1Password behavior). It speaks the native-messaging protocol the extension already uses with upstream's desktop app. That app has its own login and holds the user key; the agent has neither, so the extension hands it the user key when someone turns biometric unlock on. That's a change to key handling, so it has its own design and test vectors: see "Biometric unlock".
  - Reports what's set up on the machine: which browsers and profiles have the extension, and whether the browser's password manager is off.
  - Drives onboarding for managed users by opening the right page at the right time.
- **Upstream's Rust, with care:** the `desktop_native` crates are GPL-3.0, but `biometric` links Bitwarden's SDK crates, which declare a license file instead of a standard open-source license, and `desktop_core` links `bitwarden-russh`, which declares none. So the agent is its own Cargo workspace (`agent` in `passbundle-apps`, moved there from `passbundle-clients` on October 21, 2026, next to the app) and links neither. GPL code it takes from upstream is copied in with a note saying where from.
- **Targets:** installer under 10 MB, under 20 MB of RAM when idle, no extra processes.
- **Updates:** a small self-updater. A release is a manifest signed with our offline update key (minisign), and the agent installs it only if the signature verifies with the key compiled in, it's for this platform, it's newer, it's served over HTTPS, and the download has the stated size and SHA-256. Installed agents update from a scheduled task (Windows), never because the network told them to. On macOS the agent is inside the app, and replacing one program would break the app's signature, so the app updates whole: from the RMM for now, and by itself later. Organizations that push updates through their RMM turn self-updates off by policy.
- **The desktop vault window** is our Flutter app (see "Clients" above, decided October 20, 2026), built into the agent's tray app.
- **Order:** Windows first, then macOS.
- **Status:** the foundation is built (`agent` in `passbundle-apps`, version 0.1): the tray icon and menu (the version, Open web vault, Quit), one agent per signed-in user, settings by policy (web vault URL, self-updates off), and the signed self-updater. Its CI (in `passbundle-apps`) runs its tests on Windows, macOS, and Linux, checks the release build is under 10 MB (0.9 MB on macOS), and runs it in the tray; tier 1 builds its test build for the extension's end-to-end tests. Idle, it uses 8.5 MB of memory on macOS. Not yet: the update key (made offline; until then builds don't update themselves) and installing it from the RMM script (waits on code signing). Biometric unlock is built (see "Biometric unlock"). The agent won't do the MSP background work (see "MSP templates").

### Biometric unlock (Windows Hello and Touch ID)

Unlock the browser extension with Windows Hello or Touch ID, through the desktop agent. The agent has no login and no vault, so it can only hand back a key the extension gave it.

**Status:** built for Windows, not yet tried on a real Windows Hello device. The agent's channel and protocol (`agent/src/channel.rs`, `protocol.rs`, in `passbundle-apps`), its socket and native-messaging host (`ipc.rs`, `host.rs`), Windows Hello (`windows_hello.rs`, `sealed.rs`), and the extension's side (`apps/browser/src/keykeeper/agent-biometrics.ts`). Tier 1 runs it all with a stand-in for Windows Hello, on Windows, macOS, and Linux. Next: one check on real Windows Hello hardware, then the installer registering the host (it waits on code signing). macOS waits on signing too.

- **The protocol is upstream's native-messaging one**, the one the extension already speaks with upstream's desktop app, and all of it is GPL TypeScript we can read:
  - The browser starts our native-messaging host, a pipe to the agent: 4-byte native-endian length, then JSON, 1 MB at most. The host sends `{"command":"connected"}` once it reaches the agent and `{"command":"disconnected"}` when the agent goes away.
  - **Key exchange:** the extension sends `setupEncryption` with a new RSA-2048 public key (SPKI) and the active user's id. The agent makes a 64-byte session key (AES-256-CBC key and HMAC-SHA256 key) and returns it encrypted with RSA-OAEP (SHA-1, as upstream). Unlike upstream's desktop app, it sets up a channel for any user, since enrolling needs one and nothing comes back without a prompt; upstream answers `wrongUserId` for an account it doesn't have. A message under a session the agent doesn't have, or with a bad MAC, gets `invalidateEncryption`, and the extension starts over.
  - **Messages** are then type-2 EncStrings (AES-256-CBC with HMAC-SHA256) under the session key, carrying `command`, `messageId`, `userId`, and `timestamp`. Both sides drop a message more than 10 seconds from their clock, and replies carry the request's `messageId`. The extension waits 60 seconds for a reply, so a prompt must finish in that time, and the agent stamps a reply when it sends it, after the prompt.
  - **Commands the agent answers:** `getBiometricsStatus`, `getBiometricsStatusForUser`, `unlockWithBiometricsForUser` (prompts, then returns the user key), and `authenticateWithBiometrics`. Unknown commands get no reply, as upstream.
- **Not upstream's "shared unlock".** That newer feature runs over the SDK's own IPC protocol, whose messages, encryption, and peer checks live inside the SDK, which we can neither read nor link. It's off unless the server sends two feature flags, and ours can't: they aren't on its list of flags it will send (`SUPPORTED_FEATURE_FLAGS`).
- **One command of our own, `keykeeper.biometric.enroll`.** Upstream's desktop app has its own login and holds the user key; ours doesn't. So when someone turns on "Unlock with biometrics" in the extension while unlocked, the extension sends the agent the active user's id and user key over the encrypted channel. The agent asks for Windows Hello or Touch ID ("Turn on unlock with Windows Hello for <email> in <browser>?"), and stores the key only if the person confirms. `keykeeper.biometric.remove` deletes it, sent when the setting is turned off and at logout. The agent also deletes a user's key when it can't be opened any more (Windows Hello was set up again, or the stored key is damaged), so a stale key can't keep failing; a prompt that fails for now (a locked or busy device) keeps it.
- **Where the agent keeps the key:**
  - **Windows:** like upstream's GPL implementation, without its SDK crates. Each enrollment gets a random 32-byte challenge. Windows Hello signs it with a key credential only after the person authenticates, and the signature (RSA PKCS#1 v1.5, so the same every time) is hashed with HKDF-SHA256 into a key that seals the user key with AES-256-GCM. The challenge and the sealed key are stored in the user's app data, wrapped with DPAPI. Windows Hello opens its prompt behind the browser when the program asking isn't in front, so the native-messaging host, which the browser started and so may, lets the agent bring it forward (`AllowSetForegroundWindow`).
  - **macOS:** a keychain item that only Touch ID (the current set of fingerprints) can open, in the data protection keychain. That needs the agent signed with our Apple developer ID and a keychain entitlement, so on macOS biometric unlock waits for signing. We won't ship the weaker "ask for Touch ID, then read a normal keychain item" fallback upstream uses.
- **What it protects against, and what it doesn't:**
  - Nothing leaves the computer, and the server isn't involved.
  - The key exchange isn't authenticated: any program running as the person can connect, as with upstream's desktop app. It still can't get a key without the person passing Windows Hello or Touch ID. One prompt at a time, and none for 10 seconds after a cancel, so a program can't nag the person into approving. Windows shows its own text in a key credential's prompt, so on Windows the prompt can't name the browser or the account.
  - The agent's socket is the signed-in user's alone: a Unix socket in their own folder (0700) on macOS, and on Windows a named pipe whose access list allows only them and SYSTEM, created as the first instance of its name so no other program can claim it while the agent runs.
  - **The host checks who it reached.** When the agent isn't running (its tray's Quit), a program running as the person could make the pipe or socket first and be handed the user key at the next enrollment. So before it forwards anything, the host asks the operating system which program is at the other end (on Windows, the pipe's server process and its image path; on macOS and Linux, the socket peer's executable) and goes on only if it's the `passbundle-agent` installed next to the host. Later, with signed builds: checking the code signature as well.
  - **Copies of the user key** in the agent's decrypted messages and replies are overwritten before they're dropped (`zeroize`), besides the stored and returned keys themselves.
  - **Known gap:** any program running as the person can still ask the agent to forget a user's key or whether one is enrolled, which costs them the setting, not the key.
  - Malware already running as the person is out of scope, as for every password manager: it can read an unlocked extension's memory.
- **The host's name is ours.** Upstream's extension asks for `com.8bit.bitwarden`; `brand/apply.mjs` changes it at build time to brand.json's `nativeMessagingHost` (`com.passbundle.agent`). The installer registers the host machine-wide for Chrome, Edge, and Firefox, allowed only for our extension IDs, which are compiled in.
- **Extension changes**, each in a `// Keykeeper:` block: the host name (by brand), sending `enroll` when biometric unlock is turned on and `remove` when it's turned off or at logout, and showing the agent's answer ("Windows Hello is set up" or why not). How the extension unlocks with the key the agent returns is upstream's code, unchanged.
- **The extension asks for native messaging at install, not later.** Upstream makes it an optional permission, so turning biometric unlock on means a permission prompt and an extension reload. Ours makes it required (by brand, in the manifest), which matches "Biometrics by default" below: one less prompt, and nothing to approve on managed installs. The cost: the store listing's install warning adds "Communicate with cooperating native applications."
- **Test vectors, before any code:**
  - **Crypto interop (done):** `agent/tests/vectors/native-messaging.json` (in `passbundle-apps`) holds a fixed session key, four messages with fixed IVs and the EncStrings they make, and a session key wrapped to a fixed test RSA key. `check-upstream.mjs` runs upstream's own crypto (the SDK's `PureCrypto`, which the extension uses for exactly these operations) on them: every message decrypts, a change to the IV, ciphertext, or MAC is refused, the wrapped key unwraps, and upstream's own EncStrings have the same layout. The agent's Rust tests decrypt every message and re-encrypt each, with its IV, to the identical string, and their wrapped keys unwrap with the same RSA parameters.
  - Windows sealing: a fixed challenge, a fixed stand-in signature, and a fixed user key give a known sealed blob.
- **Tests:**
  - Rust protocol tests: the key exchange, a wrong user, the 10-second window, unknown commands, oversized messages, and the prompt limits.
  - End to end in Tier 1 on Linux Chromium: a test build of the agent with a stand-in authenticator (only with a test feature, and release builds refuse to build it) and no tray, registered as the test profile's native-messaging host. The real extension turns biometric unlock on, locks, and unlocks with it; a canceled prompt leaves it locked; another user gets nothing.
  - Real Windows Hello and Touch ID prompts can't run in CI. Each release gets one check on real hardware, with the Windows Hello test kit (`.github/workflows/test-kit.yml`, `installer/windows/test-kit/`): one zip with a Windows build of the server, the web vault, the agent, and an extension with a fixed ID, and `Try-WindowsHello.ps1`, which runs the server on localhost, installs the agent for the person, registers it for the kit's extension, and points that extension at the server by policy. CI tries the kit on a fresh Windows machine: the extension gets the server from policy and reaches the agent, which reports no Windows Hello there; `-Remove` leaves nothing behind.

### Installer and agent (Windows first)

- A signed MSI plus a bootstrap script per client org, copied from the admin portal with the org's enrollment token included.
- The MSP runs the script from its RMM. The script downloads the current MSI from a fixed URL, checks the Authenticode signer against a fingerprint written into the script, and installs silently.
- The install runs once with admin rights. It installs the desktop agent, writes browser policies, installs the import helper, and enrolls the machine to the org.
- **No resident service that accepts remote commands.** A hacked server must not become remote code execution on every client machine.
- Our extension IDs are compiled into the installer. It can force-install only our extension, never one named by the server.
- To change targeting, the MSP reruns the script, which applies the org's current settings.
- **Status:** `installer/windows/Install-PassBundle.ps1` applies the browser policies and, with the agent's two programs in an `agent` folder next to it, installs the desktop agent: to Program Files, started at every sign-in (the machine's Run key), registered for Chrome and Edge as our native-messaging host for our extension IDs only, with the server address in its policy, and a SYSTEM task that runs its signed updater daily and at startup (`-DisableAgentUpdates` for MSPs who update through their RMM). With the app's files in an `app` folder too, it installs our app next to the agent, with a Start menu shortcut: the agent's tray opens it, and it starts the agent if it isn't running. `-Remove` undoes all of it. Tier 2 builds the agent and the app on a Windows machine, installs as an RMM would, checks every piece, has the installed host reach the running agent, and opens the installed app. Not yet: the signed MSI and the download with a pinned signer (waits on code signing), the import helper, Firefox, and updating the host program and the app along with the agent (the updater replaces only the agent). The app installed this way is in Program Files, which only an administrator can change, so it only says when there's a new version (see "Desktop updates"), and the RMM updates it by running the script again.
- **Status, macOS:** `installer/macos/install-passbundle.sh`, run as root by the RMM with `PassBundle.app` next to it, does the following:
  - installs the app to /Applications, with the agent and the native-messaging host inside it as an app of their own (`Contents/Helpers/PassBundle Agent.app`, no Dock icon), so macOS doesn't take the running agent for PassBundle when someone opens the app;
  - starts the agent at every login (a LaunchAgent that restarts it after a crash, not after Quit), and now for whoever is at the screen;
  - registers the host for Chrome and Edge, for our extension IDs only;
  - run again with a new app, replaces it and restarts the agent; with the same app, changes nothing;
  - `--remove` undoes it all.

  macOS takes browser policies and the agent's settings only from a configuration profile that an MDM installs. `make-profile.sh` writes that profile with the Windows script's options: the forced extension, the browser's own password manager and autofill, and the extension's server, enrollment token, join secret, and key fingerprint. The agent gets the server too.

  Testing:
  - Tier 1 lints the scripts and reads the profile back.
  - Tier 2 builds the app on a Mac, installs it as an RMM would, and checks every piece. It checks the agent is running and listening, that launchd restarts it after a crash, and that the app opens. Then it updates and removes it.

  Not yet: a signed and notarized app and a download with a pinned signer (waits on the Apple Developer account), Touch ID unlock, Firefox, and the app updating itself.
- **Status, Linux:** `installer/linux/install-passbundle.sh` is run as root by the RMM. With the app's bundle in a `passbundle` folder next to it, it installs the app to /opt/passbundle, with a desktop entry and icon so it's in the applications menu.
  - Linux browsers read managed policies from files, so the script sets the Windows script's policies itself, with the same options: one file of our own in Chrome's and Edge's managed policies folders.
  - A list policy set in two files is the browser's pick of one, so if another vendor's file also force-installs extensions, it says so and leaves that file alone.
  - With a server address, it also writes the app's own policy (`/etc/passbundle/policy.json`), so the app signs in to that server without asking (`docs/core.md`, "Servers").
  - Without the app's folder, it sets the policies only.
  - Run again, it changes nothing; with a new app, it replaces it. `--remove` undoes it all.
  - The desktop agent isn't installed: on Linux it has no tray and no biometric unlock yet.

  Testing: tier 2 builds the app on Linux and installs as an RMM would. It checks every file, owner, and mode, and the desktop entry. It checks the app opens, and that another vendor's policy file is left alone. Then it updates and removes, and real Chrome and Edge report the policies.

  The app installed to /opt is root's, so it only says when there's a new version (see "Desktop updates"), and the RMM updates it by running the script again.

  Not yet: packages (.deb, .rpm, Flatpak), Firefox, and the agent.

### Import helper

- A small component, installed with admin rights, that only decrypts the browser's password key (Chrome app-bound encryption) when our signed desktop agent asks for it.
- Standard users get no UAC prompt.
- EDR products will flag it, because reading browser passwords looks like credential theft. We publish signed hashes and exclusion steps for Defender, SentinelOne, and Huntress.

### Updates

- The desktop agent updates itself (see "Desktop agent").
- The apps' test releases update themselves from GitHub: Android and the Mac by the OS's own signatures (passbundle-apps README, "Android test releases" and "Mac test releases"), Windows and Linux by a signed manifest (see "Desktop updates" below).
- Releases are signed with a separate update-signing key kept offline.
- Release rings: internal org, then early-access MSPs, then everyone.
- Every store publisher account (Chrome Web Store, Microsoft Edge Add-ons, Firefox Add-ons, Apple, Google Play) uses hardware security keys.

### Desktop updates (Windows and Linux)

The Windows and Linux apps' test releases update themselves from GitHub, as Android's and the Mac's do (passbundle-apps README, "Windows and Linux test releases"). There's no Windows code-signing certificate yet, and Linux has no code signature the OS checks, so a release's authenticity comes from a manifest signed with our own Ed25519 key instead.

- **Releases:** tagged `windows-v<major>.<minor>.<build>` and `linux-v<major>.<minor>.<build>` on `PimpinPumpkin/passbundle-apps`, never marked as the latest release (that stays Android's). Each has the app (`PassBundle-<version>-windows-x64.zip`; `PassBundle-<version>-linux-x64.tar.gz` and `PassBundle-<version>-linux-arm64.tar.gz`), each holding one `PassBundle` folder, and `manifest.json`, `manifest.json.sig`, and `SHA256SUMS`. The build number counts each platform's releases and only goes up, so it alone says which is newer.
- **The manifest** is compact JSON, as jq writes it:

  ```json
  {"format":1,"app":"com.passbundle.app","tag":"windows-v0.1.5","version":"0.1.5","commit":"<the commit>","notes":"<what's new>","files":[{"name":"PassBundle-0.1.5-windows-x64.zip","platform":"windows-x64","size":15728640,"sha256":"<64 lowercase hex digits>"}]}
  ```

  `platform` is `windows-x64`, `linux-x64`, or `linux-arm64`; Linux's manifest names both of its files. The app ignores fields it doesn't know, so later releases can add some, and refuses any `format` but 1.
- **The signature:** `manifest.json.sig` is base64 of an Ed25519 signature (RFC 8032, pure Ed25519) of the bytes `PassBundle desktop release v1\n` followed by the manifest file's exact bytes. The prefix means a signature the key made for anything else can never pass for a manifest's. The app checks it strictly (ed25519-dalek's `verify_strict`: no malleable signatures, no weak keys) with the public keys compiled into the core, and reads nothing in the manifest until it checks out.
- **What the app checks, in order:**
  1. GitHub's list of releases (`api.github.com` only); its non-draft, non-prerelease tags for this OS that are newer than this copy, newest first, at most 10. Each is tried in turn, through step 5, and the first that checks out is offered: a release that doesn't (one someone with access to GitHub made up, say) can't keep the real ones behind it from being offered. A network failure stops the check.
  2. That release's `manifest.json` and `manifest.json.sig`, each at exactly `https://github.com/PimpinPumpkin/passbundle-apps/releases/download/<tag>/<name>` as the list gives it, fetched over HTTPS and only through `github.com`, `objects.githubusercontent.com`, and `release-assets.githubusercontent.com` (every redirect checked, none to plain HTTP), at most 256 KB and 1 KB.
  3. The signature, with a pinned key.
  4. The manifest: for `com.passbundle.app`, for the tag it was found on, at the version that tag names, newer than this copy (never the same version or an older one), with exactly one file for this platform, named `PassBundle-<version>-<platform>.<zip or tar.gz>`, at most 200 MB, with a SHA-256.
  5. GitHub's own size and SHA-256 of that file, where its list gives them, agree with the manifest's.
  6. The file, from its exact address with the same host rules, hashed as it's written to a folder of the updater's own and stopped at the manifest's size; then its size and SHA-256.
  7. Unpacking: every entry a plain file or folder inside the one `PassBundle` folder (no links, absolute paths, `..`, or names Windows reads as devices or streams), at most 100,000 entries and 8 times the archive (between 64 MB and 1 GB), counted as it's unpacked.
  8. The unpacked folder: its `release.json` says it's `com.passbundle.app` at the manifest's version for this platform, it has the app's program, the core, and the updater, and it holds exactly the paths its `release.json` lists, folders made 0755.

  The Android updater's checks are the bar: HTTPS only, the same hosts, the URL's shape, a size cap, the version equal to the tag, and hashing while streaming. Android's "signed with the same key as the running app" is, here, "signed with a key the running app pins".
- **Putting it in place:** Windows can't replace a running program, nor rename the folder it runs from, so the app quits and `passbundle-update` (a small program of the core's, run from its own copy in the work folder next to the app's) does it. The work folder (`.PassBundle-update` beside `PassBundle`) is one the updater makes for itself, this person's alone: on Linux mode 0700; on Windows owned by them, with a protected access list for them and SYSTEM only. Anything else at that path (shared, or a link) is never read, written through, or removed, and the app won't update while it's there. Files in it are read and written without following links. The updater acts only on its own work folder, and only on details (`update.json`) about the app next to it: its work folder is that app's, its program is the app's, and that folder is a release of this app. It waits for the app to end, stops the desktop agent running from the same folder, and puts the new version in the old one's place: on Linux by exchanging the two folders at once (`renameat2` with `RENAME_EXCHANGE`), so the app's path is never free for anyone to take; on Windows, and on a Linux disk that can't exchange folders, by two renames on one disk, in a folder no one else can change. Then it opens the new version. When that has drawn its first frame, the old version is removed, then the work folder; if it ends or hasn't drawn one within a minute, the updater ends it, puts the old version back the same way, and opens that, which tells the person. No old version, download, or copy of the updater is left behind.

## MSP console

The MSP side is where we win, so it gets the most care: one place to run every client, and a backend that's small and tested end to end. Upstream's version of this ("Providers") is under the Bitwarden License, so ours is written from scratch (see CLEAN_ROOM.md).

### How an MSP reaches its clients

- **An MSP** is a server-side group: a name, its staff, and its client orgs. Each client org belongs to at most one MSP.
- **Staff roles:** MSP admins manage the MSP, its staff, and its clients. Technicians work in client orgs.
- **Staff are ordinary members of each client org,** marked as coming from the MSP: MSP admins as owners, technicians as admins. Adding someone to the MSP adds them to every client; adding a client adds every staff member. Removing someone from the MSP removes them everywhere at once.
- **No new crypto.** Staff get each org's key the normal way: an org member who already holds it confirms them, which encrypts the org key to the new member's public key. The MSP console does this automatically whenever any MSP admin has it open. The server never holds a key that can decrypt a vault. The trade-off is the same as upstream's automatic confirmation: we trust the server to hand out the right public key. Showing key fingerprints when staff are added comes later.
- **The client stays in control.** A client org's owner sees the MSP's staff listed separately ("Your MSP"), and can remove the MSP, which removes all of its staff from the org in one step.
- MSP staff don't count as the client's seats.

### What the console shows

- **Clients:** one row per client org with members (confirmed, waiting, invited), the preset, items expiring soon, password health (weak, reused, exposed), and last activity. Expiring and health figures are computed in the browser, which can decrypt org items because MSP staff are members. The server only sees counts of members. Exposed passwords are checked with k-anonymity, so no password leaves the browser (see "Exposed passwords"), and a client's counts open its list of what to fix, by name.
- **Add a client:** name it, pick a preset (Business by default). The org, its default collections, and its policies are created in one step, and every staff member is added.
- **Waiting for approval:** members added by the portal or RMM are confirmed automatically by the console. Invite-link joins wait for one click. People Entra adds get in with no click through the install command, or after an admin lets them in once (see "Provisioning from Entra ID").
- **Per client:** opens the org's admin console (members, groups, collections, policies), which upstream already provides as open source.
- **Across clients:** expiring credentials, default policies every client follows (see "Default policies"), item templates sent to every client or chosen ones (see "MSP templates"), and the RMM install script for each client.
- **Staff:** add by email, change role, remove.

### Roles and permissions

Two layers: what a client's own people can manage, and what each MSP technician can do.

**Per client: custom roles.** Upstream's member dialog already offers a "Custom" role with permissions, but Vaultwarden ignores them and treats Custom as the old Manager role. We store and enforce them, so a client's point of contact can manage their own people without being an admin.

- **Version 1 permissions:** manage members (invite, confirm, remove, revoke, restore, and edit regular members), account recovery (recover regular members), manage policies, view event logs (and the members' names and emails, to say who acted), and import and export. Later: collections, groups, and reports.
- **Storage:** our own table, keyed by membership. Upstream's membership stays a regular member, so other clients just see a member.
- **Enforcement:** one map in the server from each admin endpoint (route template and method) to the permission it needs. The admin guard admits a custom member only to endpoints their permissions cover. Everything else still needs an owner or admin.
- **No escalation:** a custom member acts with an admin's rules but only on regular members. They can't grant roles or permissions, can't give access to all items, can't act on themselves, and can't touch admins, owners, or other custom members. Account recovery reaches only regular members.
- **Never more than they have (security review, October 2026):** a custom member gives others only collections they reach themselves (every one, if they have access to all items), never with more access than their own, and never the right to manage a collection. They don't add people to groups or change anyone's groups, and editing someone leaves that person's other collections alone. They can read the groups, which the Members page and the member dialogs show, but only owners and admins create, edit, or delete them, and in each group a custom member sees only the collections they reach themselves. Otherwise a role that manages members could give a second account of its own every item, and "no vault items" would mean nothing.
- **Export needs access to all items:** the export holds every item in the organization, so it refuses a custom role without access to all items. A client's own custom roles can't have that yet, so for them import and export covers import. A technician given import and export must also be given vault items.
- **Who assigns them:** owners and admins, including MSP staff. Not custom members.
- **Tests:** the permission matrix gains a custom member per permission, across every mapped endpoint, plus escalation tests for each limit above.

**Status:** built on the server and tested: storage, the endpoint map, the limits, and Custom showing in the apps with its permissions. The member dialog offers only the permissions we enforce. Custom roles with these permissions can't also manage all collections: the member dialog doesn't offer both, the server refuses them, and the apps never show a custom role as managing collections. Otherwise the web vault opens the admin console's Vault tab for them, whose endpoints no custom permission covers, and the refusals sign them out. Upstream's Custom with only "Manage all collections" is still a manager of every collection. The Members page works for custom members: whoever can open it (manage members or account recovery) can read the collection list it loads, and manage members and import and export can read the invite and edit dialogs' and the import page's collection list, which shows them only collections they're assigned to. Groups are on for every organization, so the Members page also loads the group list (names, without a directory's id), which whoever can open it can read, and the invite and edit dialogs load the groups with their collections, which manage members can read, each group listing only the collections the custom member is assigned to. Every other group endpoint refuses custom members. Endpoints a custom member's role doesn't cover refuse them with 403 rather than 401, so clients can tell a missing permission from an expired session. The exception is the endpoints behind upstream's manager guards (a folder's endpoints, and the organization's folder, member, and group lists), which answer 404 to every confirmed member they turn away, custom or not ("Folders and permissions"): the web vault reaches a folder's endpoints for any folder it shows, and 403 would sign a custom member out. **Known gap:** upstream's web vault signs out on 403 as well as 401, so any page the web vault shows a custom member must load only endpoints their role covers. The event log is on for every organization too, and it loads the short member list (`users/mini-details`: each member's id, account id, role, status, name, and email) to say who acted, so a custom role that views event logs can read that list, the same one an admin gets, and nothing more about members. A member's Options menu on the Members page offers their event log only to roles that can view event logs (owners, admins, and custom roles with that permission), since the member's events would refuse anyone else and sign them out. The end-to-end tests open the organization, the Members page, the invite dialog, and a member's edit dialog as a custom member who manages members, the event log as one who only views event logs, and a member's event log as one with both, check that a role without view event logs isn't offered a member's event log, and fail on any refused request.

**Per MSP: technician access.**

- **Which clients:** each technician gets every client (today's behavior) or chosen ones. New clients reach only technicians with every client.
- **Role in those clients:** admin (today's behavior) or a custom role with chosen permissions, such as a helpdesk role that manages members and account recovery. Separately, whether they can see vault items (access to all collections).
- **A different role in some clients:** the role above is the default; chosen clients they reach can have their own (admin, or a custom role with its own permissions and vault items), such as admin at the one client a technician looks after and helpdesk at the rest. Stored per client (`msp_staff_client_roles`), applied by the same server step, and a client they stop reaching loses its role too.
- **Install commands:** whether they see the clients' RMM install commands, which let anyone who has one ask to join.
- **Changes apply everywhere at once,** like adding or removing a technician, and go in the audit log.
- MSP admins stay owners of every client.

**Status:** built and tested (`keykeeper_msp.rs`, migrations for SQLite and PostgreSQL, the console's Staff section). MSP admins choose a technician's access when adding them (an invitation carries it until they join) or edit it later; one server step brings all of their client memberships in line, adding them where they now reach (waiting for the org key, which the console gives), changing their role, and removing the MSP's memberships where they no longer reach. A client's own grants are left alone. A limited technician's console and audit log show only their clients, and the install command endpoint refuses technicians without it. Custom roles are the client roles above, so the same limits apply: they act only on regular members. Vault items give access to every item, which a technician sees and edits in their own vault; the apps don't show it as managing all collections, because the admin console's collection tools need permissions custom roles don't enforce yet and its refusals would sign them out. A client's own owners and admins see, on their Members page, each of the MSP's people there with their role (owner, admin, or a custom role and its permissions) and whether they see vault items. A technician can have a different role in chosen clients (the Staff section's access editor), and the audit log names those clients.

### Default policies

An MSP sets its policies once, and every client follows them. A client that needs something different gets its own setting for that one policy, and keeps the defaults for the rest.

- **The defaults** are one setting per policy (on with its options, or off), kept on the MSP. A new MSP starts with the Business preset's policies (see "Defaults (Business preset)"). MSPs created before defaults existed get the same, which matches what their Business clients already have.
- **New clients start with the defaults.** Add client applies them along with the Everyone and Admins collections.
- **Following or own setting.** A client follows a default while its setting for that policy matches it. A client whose setting differs has its own setting for that policy. Nothing else marks it: there's no flag to drift out of step with the real policy, and every way of changing a client's policy (its admin console, its own owners, a point of contact with the policies permission, MSP staff) works the same.
- **Changing a default** changes every client that follows it, in one step, and leaves clients with their own setting alone. The console says which clients changed and which kept their own setting.
- **Giving a client its own setting:** change the policy in that client's admin console, as today. **Back to the default:** "Use default" in the console, for one client or several at once.
- **Same rules as the admin console.** The server applies a default to a client through the same code as upstream's policy endpoint, with the same checks and side effects. Turning on two-step login revokes members without it, and single organization revokes members who belong to another organization, in every client that follows. The console warns before changing either. If a client refuses a change, the console names it, and that client shows as having its own setting.
- **Who:** MSP admins change defaults and use them in clients. Technicians see the defaults and which of their clients have their own settings. A client's owners see on their Policies page that the MSP sets defaults, and that changing a policy there makes it the organization's own.
- **Editing:** the console edits a default with upstream's own form for that policy, so options, wording, and checks match the admin console. Only policies the server supports are offered; account recovery only when the server sends email.
- **Audit log:** each default change, with how many clients changed and kept their own setting, and each client moved back to the default.
- **Tests:** API tests for following and own settings (a changed default reaches followers and skips others; changing a client's policy makes it its own; using the default brings it back), side effects through a default (two-step login revoking a member), the legacy MSP defaults, and the permission matrix. A console e2e test changes a default, sees which clients took it, and uses the default for a client with its own setting.
- **Status:** built (`keykeeper_msp_policies.rs`, a migration for SQLite and PostgreSQL, the console's Default policies section, and a note on each client's Policies page that names its own settings). The server compares what each policy does: an off policy's options don't count, and missing, empty, and null options are the same. A changed default goes only to clients whose policy matched the old default, so a client's own setting is never overwritten by accident. The edit dialog lists the clients that follow the default, all checked; unchecked ones keep what they have, which then counts as their own setting (`keep` in the request). Not offered as defaults: Require single sign-on, since each client's sign-in is its own (see "Sign in with Microsoft Entra ID"). One default isn't an upstream policy: two-step login for admins, which a client keeps as its own setting, never as a policy (see "Two-step login for admins").

### Joining

Someone invited to an organization gets in without anyone clicking Confirm: no "the person you invited signed up, now go approve them" step, which 1Password and Bitwarden both have.

- **Why there's a step at all:** joining means giving the person the organization's key, encrypted to their public key, and the server never holds that key. So a device that has it must do the handoff. Upstream makes a person click Confirm for it; we do it in the background.
- **Who does it:** the web vault or browser extension of any owner or admin of the organization (for an MSP's clients, anyone on the MSP's staff who can confirm there), while it's unlocked: when it unlocks, when its items change, and every five minutes. Usually within a few minutes; if every owner's and admin's apps are closed, the person waits until one opens. Upstream's rule stands: admins confirm regular members, owners anyone.
- **Settings, per organization** (its Settings page, owners and admins): let people in automatically (on by default) or have an owner or admin approve each one on the Members page, and how long invitations last (2 hours, 1 day, or 5 days; the server allows 1 hour to 30 days). The invitation email says how long it works, and the link stops working after that.
- **MSPs** set a default for their clients in the console; a client with its own setting keeps it, and an MSP admin can put it back on the default. Changes go in the MSP's activity log.
- **Outside an MSP** the default is the server's: automatically, and `INVITATION_EXPIRATION_HOURS` (5 days).
- **Who hears about it:** with nobody clicking Confirm, an email is how anyone notices a join. Whoever sent the invitation gets "<email> joined <org>", which says nobody needs to confirm them and links to the Members page to remove someone unexpected. Where an admin approves joiners, it's upstream's "accepted your invitation, confirm them" instead. A join with the install command goes to the client's own owners (see "Onboarding through the RMM").
- **The trust this assumes:** the server says which public key belongs to the person who accepted, so apps confirm on their own only when something the server can't forge vouches for them (see "Joins a hacked server can't forge"). Organizations that want a person to compare fingerprints can require approval.
- **When the organization requires two-step login:** someone who joins without it can't be confirmed until they turn it on (upstream's rule; owners and admins are exempt, an MSP's staff aren't). Upstream just leaves them under "Needs confirmation", where nobody knows why. Ours: the list of who's waiting says so (`needsTwoStep`), so apps don't try to confirm them every five minutes, which would also use up the day's limit for letting people in on their own; the Members page says who's waiting for two-step login; and their own web vault and extension say "<org> requires two-step login before you can get in", with a button to its settings (`GET /keykeeper/organizations/two-step-needed`). Once they turn it on, they're confirmed as usual. Unit tests cover skipping them without using up the limit; API tests cover the flags, the exemptions, and confirming once it's on; an end-to-end test covers both notices in the web vault.
- **Tests:** API tests for the settings, how they resolve (own, MSP default, server), the list of who's waiting, and permission matrices; mail tests that invitations last as long as the setting and say so, and that the inviter's email matches the setting; an end-to-end test where someone invited gets in with no click while another organization's invitee waits for approval.
- **Status:** built (`keykeeper_joining.rs` and its migration on the server; the background work in `libs/admin-console/src/common/keykeeper/msp-work.ts`, which the web vault and the extension share; the Settings page card and the console section).

### Joins a hacked server can't forge

Letting someone in means encrypting the organization's key to their public key. The server never holds the organization's key, but it does say who is waiting and with which public key, and it serves the organization's public key to the extension that escrows a user key for account recovery. So a hacked server could ask the apps that confirm in the background to encrypt the organization's key to a key of its own, or hand the extension its own key in place of the organization's. These rules close that for the install command, and narrow it for email invitations to the one thing only a person comparing fingerprints can catch. Decided October 2026; the protocol is versioned (v1), and the test vectors are in `docs/vectors/joins-v1.json`.

**The join key.** Each organization has a join key that only holders of its organization key can compute, and the server can't: `joinKey = HKDF-SHA256(ikm = the organization's 64-byte symmetric key, salt = empty, info = "passbundle join key v1", 32 bytes)`.

**The install command carries a secret the server never sees.**
- When an owner or admin makes or replaces the command, their browser makes a 32-byte join secret and the server stores it only encrypted with the organization's key (an `EncString`, so owners, admins, and MSP staff who confirm there can read it, and the server can't). The command shows it next to the token: `-EnrollmentToken '<token>' -JoinSecret '<secret>' -OrgKey '<fingerprint>'`, each 43 base64url characters, checked and single-quoted like the rest.
- `<fingerprint>` is the SHA-256 of the organization's public key (SPKI, DER). The browser derives the public key from the organization's private key, which it decrypts with the organization key (owners and admins fetch it encrypted from `GET /keykeeper/organizations/<id>/private-key`), never from the public key the server reports.
- The install script writes all three to the extension's managed settings. The extension never sends the secret or the fingerprint anywhere.
- **Joining:** the extension refuses an organization whose public key (from the server) doesn't hash to the fingerprint, so a swapped key never gets a user key for account recovery. It sends, with the token, a proof: `HMAC-SHA256(secret, "passbundle join v1" ‖ 0x00 ‖ organization id ‖ 0x00 ‖ user id ‖ 0x00 ‖ SHA-256(the person's public key))`, where the public key is the one derived from the person's own private key on that device. The server stores the proof with the join.
- **Confirming:** an app confirms a token join on its own only when the proof checks out against the public key it's about to encrypt to (constant-time compare), and the command is limited to email domains (see "No click only with domains"). Otherwise the join waits for an owner or admin's Confirm on the Members page, with the fingerprint. A hacked server can't make a proof for a key of its own without the secret.

**Email invitations carry a seal.**
- When an owner or admin invites someone from upstream's member dialog, their browser seals the invitation: `HMAC-SHA256(joinKey, "passbundle invite v1" ‖ 0x00 ‖ organization id ‖ 0x00 ‖ lowercased email)`. The server keeps it by organization and email (`join_seals`), and an invitation sent without one removes any earlier one.
- An app confirms an invited member on its own only with a seal that checks out for that email. A membership the server made up for an address nobody invited waits for approval.
- **What it doesn't catch:** the server could still present a key of its own as someone an admin really invited (or as an invited address) at the moment they join. Only a person comparing fingerprints catches that, which is what requiring approval is for. The seal narrows the risk from "anyone, any time" to "the addresses an admin invited", and the limits and notice below make it loud.
- **MSP staff:** an MSP admin's browser seals each staff member's place in each client it reaches (`"passbundle staff v1"`, with that client's join key) when it adds them, widens their access, makes them an admin, or makes a client (for the staff the console lists as reaching every client). The server removes a staff member's seals when they leave or stop reaching a client. Staff without a seal wait for approval, as do invited people with only an invitation seal.

**The settings carry a seal too.** Whether an organization lets people in without approval, and its email domains, are sealed with its join key by the browser that saves them: `HMAC-SHA256(joinKey, "passbundle joining v1" ‖ 0x00 ‖ organization id ‖ 0x00 ‖ "1" or "0" ‖ 0x00 ‖ the domains, sorted and joined with ",")`. An app treats a setting without a valid seal as "an admin approves each one", so the server can't turn approval off. An MSP's default is sealed per client by the MSP admin's browser that saves it. Saving the setting keeps the domains only if the old seal vouches for them, and saving domains keeps "let people in" only if the old seal vouches for it, so a change the server slipped in is never resealed.

**Limits and notice.**
- An app confirms at most 20 people per organization per day on its own; past that, the rest wait for an admin's Confirm, and the app says so.
- Each confirm on its own shows a notice on that device naming the person and the organization ("Let ana@acmedental.com into Acme Dental"), so an unexpected one is seen where it happened, besides the owners' email.

**Organizations made before this** have no join secret, seals, or settings seal, so their joins wait for approval until an owner or admin saves how people join, and their invitations until they're sent again. The first time an owner, admin, or MSP admin opens an install command without a join secret, their browser adds one (the token stays); commands already run without one still let people ask to join, and an admin approves them.

**What the server still decides:** who is on an MSP's staff when a client is made, what an organization's members see, and everything else it decides today. It can't decrypt anything, and with these rules it can't get an organization's key from an app on its own, except by posing as an invited address or a staff member's email at the moment they join.

**Tests:** unit tests for each computation against the vectors (`libs/admin-console/src/common/keykeeper/join-seals.spec.ts`, which keeps a copy, and `join-checks.spec.ts` for who's let in, the daily limit included); API tests for who may leave seals and secrets, what the server checks, that the pending lists carry them, and that a change made without a seal drops the old one (`e2e/tests/api/join-seals.spec.ts`); and a web vault test where the server's answers about who is waiting are altered in flight (a made-up person, a stripped joining seal, a stripped invitation seal) and nobody is let in until the answers are real (`e2e/tests/joins-forged.spec.ts`). The install-to-recovery test runs the whole command, secret and fingerprint included.

**Status:** built: the server's storage and routes (`keykeeper_seals.rs` and a migration), the shared checks and computations (`join-seals.ts`, `join-checks.ts`), the web vault's sealing (`join-sealer.service.ts`, used by upstream's invite, the console, the Settings page, and organization creation), the extension's fingerprint check and proof, and the installer's two parameters.

### MSP templates

An MSP makes an item template once (a firewall, a Microsoft 365 tenant, a line-of-business app) and every client gets it, so technicians and the client's own people document things the same way everywhere. See "Item templates" for what a template is.

- **The source** is an ordinary custom template the MSP admin can see and share (a shared folder's share permission, "Folders and permissions", since its copies go to other organizations): in their own vault, or better in an organization all of the MSP's admins share, so any of them can change it. It's never one of the MSP's clients. The server records which item it is, never what's in it. The server names the source, so each admin's device checks it before copying: a template (never an ordinary item), not itself a copy from an MSP, not in one of the MSP's clients, and one they can still share. A device whose person can't share it (someone took share away, or another admin chose it) skips it and says why, and the server records copies only from someone who can share the source. And it replaces only a copy of that template in each client, never another item the server points it at, and moves to the trash only items that are copies.
- **It applies automatically,** like a default policy: an MSP admin adds a template for every client (including clients added later) or for chosen ones, and that's all. Nobody sends anything.
- **How:** each client gets a copy, with the same template id, in its "Templates" collection, encrypted with that client's key. The server can't read templates, so it can't make copies; a browser holding the clients' keys must. Any MSP admin's web vault or browser extension does this in the background: when they unlock, whenever their items change (such as after editing a template), when the MSP console opens, and every five minutes in the extension. It creates the collection the first time. The server records each copy's item and which version of the source it was made from (the source's revision date), so any admin's vault can tell which clients are behind. It never sees a template's name or fields. If no MSP admin is signed in to either, changes wait until one is. The desktop agent doesn't do this work: it holds the user key only behind Windows Hello or Touch ID, and working in the background would mean keeping it unlocked. Two devices writing a client's copy at the same moment leave a duplicate; the next run moves the one the server didn't record to the client's trash.
- **Updating:** edit the template (the console's Edit opens it). Clients get the change on their own. The console shows "Update" only if a client couldn't be updated, to try again; a failure isn't retried automatically, so it can't repeat forever. A copy is the MSP's: an update replaces whatever the client changed in it. A client that wants something different makes its own template, which is just a template in its organization.
- **Removing:** MSP admins can remove a template, and choose whether its copies stay in the clients or go.
- **Who sees copies:** everyone with access to the client's Templates collection: MSP admins and technicians who see vault items, the client's owners and admins, and the client's own members, read-only. Members get it when the collection is first made and, after that, when they're confirmed, by any way in (an email invitation, the install command). Read-only, because the MSP keeps the copies: members use them in "New item from a template". A member an admin already gave the collection keeps that access, and the MSP's people reach it through the MSP as before.
- **Templates from an MSP** show once, under "From <MSP>", in "New item from a template", even for MSP staff who see the same template in many clients.
- **Who:** MSP admins add and remove templates, and their vaults keep copies current. Technicians see which templates their clients get.
- **Audit log:** templates added, changed (which clients), applied to clients, and removed. Entries name the template only by id; the console shows the name to people who can see it.
- **Tests:** API tests for recording templates and copies (only the MSP's own clients, only items in that client, never a client's copy as a source), what a limited technician sees, and the permission matrix. A console e2e test creates a template, adds it for every client, sees a new client get it, edits it and sees every copy change with nothing else clicked, and finds it once under "From <MSP>" in the vault. An extension e2e test, with no vault tab open, edits a template in the popup and sees the client's copy change.
- **Status:** built (`keykeeper_msp_templates.rs`, a migration for SQLite and PostgreSQL, the console's Templates section, and `libs/admin-console/src/common/keykeeper/`: `msp-work.ts`, the background work the web vault and the extension share, and `msp-template-sender.ts`, which writes copies with upstream's own item and collection code). A copy's definition names the MSP, so "New item from a template" groups it under "From <MSP>" and the item view and editor say the MSP keeps it up to date. Copies stay in the client's Templates collection: the web vault's and the extension's lists leave them out unless that collection is open, since every member has them and nobody edits them (`isMspTemplateCopy`). Someone's own templates stay in the lists, where they edit them. Clients, on a template's row, changes which clients get it in place; copies in clients that no longer get it can go to their trash or stay as those clients' own templates. Members get the Templates collection read-only (server: `give_templates`, called when the collection is recorded and in upstream's confirm), with an API test.

## Onboarding

A domain is never required. Each org picks a preset: Solo, Family, or Business.

- **Solo:** install, create an account, automatic import from local browsers, extension added to the default browser profile. Done.
- **Family or small team:** the owner creates an org and shares an invite link or QR code. Members join with any email address. The owner sets approval to automatic or one tap.
- **Business:** the admin adds emails (any domain), runs the RMM script, or connects Entra (optional). Users added any of these ways are pre-approved. The org-key confirmation runs silently on any admin device that is online.

The target is a working vault, with imported passwords, after zero decisions beyond the org name. Tier 2 tests this for every preset.

### MSP staff and account recovery

An MSP staff member's account reaches every client they work in, so whoever could recover it could reach all of them. So no organization recovers a staff account, through any membership: the server refuses enrolling a staff member in any organization's account recovery (accepting an invitation, the install command, or enrolling later), refuses recovering one, and ends every enrollment someone has when they join a staff. This is per person, not per membership, so a membership a client grants a staff member itself is covered too.

### MSP staff and two-step login

A client's "Require two-step login" policy applies to its MSP's staff, who reach its items (decided October 2026). Staff without two-step login can't be confirmed into a client that requires it, and a technician who turns it off loses that client, as a regular member would. An MSP's admins own its clients, so the policy never removes them, as upstream never removes owners; the console asks them to turn it on. Separately, the MSP requires two-step login (an authenticator app, a security key or passkey, or Duo; not email codes) of everyone on its staff by default, at sign-in (see "Two-step login for admins").

### Adding MSP staff

Adding someone to an MSP's staff always sends an invitation they accept themselves, with or without an account, and the answer to the admin is the same either way: adding an existing account directly would make them an owner of every client without asking, and would say which emails have accounts. Invitations expire with the server's invitation lifetime, need a verified email where the server sends email, and end when the person joins or leaves the staff.

### Login limits

Upstream limits logins per address: a burst of 10, then one a minute, and 50 requests shared by signup, pre-login, and the password hint. On rollout day a whole office comes from one address, so it stopped after ten to twenty-five people. What stops someone guessing a password is a limit on the account, wherever the guesses come from, so that's where the strict one is now.

- **Each account:** 10 login attempts from one network (an IPv4 /24 or IPv6 /64), then one a minute (`LOGIN_RATELIMIT_ACCOUNT_*`), counting the 2FA step and the email two-step code request, which checks the password too. Across every network, 100, then one every 36 seconds (`LOGIN_RATELIMIT_ACCOUNT_ANYWHERE_*`). Keyed by the email as typed (trimmed, lowercase), whether or not an account has it, so being refused says nothing about which emails have accounts. Keys are 32-byte hashes, and the server forgets the ones whose limits have filled back up.
- **Nobody can lock someone else out (security review, October 2026):** counting per network means guesses from elsewhere don't use up the owner's own allowance, and a device already signed in to the account isn't limited at all, so the owner's own devices always get through.
- **Each address:** 100 logins, then one every 6 seconds (`LOGIN_RATELIMIT_*`, upstream's settings with new defaults). Pre-login, which every login starts with, gets the same allowance, counted on its own; it only says how to derive the key, the same way for an email without an account.
- **Signup and the rest:** the shared allowance for signup, the password hint, recovery emails, and Send access is 150 at once (was 50), still refilling at one a minute, so 50 people can sign up together.
- **What it costs:** one address can now try 10 accounts' passwords a minute instead of one. Every guess also needs the client's KDF (600,000 PBKDF2 rounds by default), each account still allows only 10, and the hosted service has Cloudflare's rate limits in front.
- **Self-hosters** who set these settings keep their values.
- **Tests:** unit tests for the account key (case, spacing, emails without accounts, per network, across networks, IPv6 and mapped IPv4); API tests on a third test server that keeps the real limits (the other two relax them), where 30 people at one address sign up, pre-login, and log in, and guessing one account stops at its 11th attempt, the right password included, while a colleague logs in and an email without an account is refused the same way. Both fail on upstream's limits.

### Onboarding through the RMM (Business, version 1)

No desktop agent needed: browsers already let policy hand an extension its settings, and our installer already writes browser policy.

1. **The MSP copies one command.** In the MSP console, each client has an install command: our install script with the server address and that client's enrollment token. The MSP runs it from their RMM on the client's machines.
2. **The script configures the browsers.** It force-installs the extension where targeted, turns off the browser's password manager, and gives the extension two managed settings: the server address (upstream already reads this) and the enrollment token.
3. **The person signs up or signs in in the extension.** The server is already filled in. After unlock, the extension sees the token, asks the server which organization it belongs to, and asks the person once, in a small window: "Join Acme Dental?", what joining means, and, where the organization uses account recovery, that its admins will be able to reset their master password and sign in as them (with its fingerprint phrase, and a word that this would reach any organization where they're an owner or admin). On Join, it encrypts the person's user key to that organization's public key for account recovery (upstream's own enrollment code, as an emailed invite does) and sends the join. "Not now" sends nothing and asks again a week later.
4. **MSP staff's apps confirm them** in the background, like any member waiting for the org key, when the join doesn't need approval (see "No click only with domains"): the web vault or browser extension of anyone on the MSP's staff who can confirm in that client, while unlocked. The extension checks every five minutes, and the console confirms on opening. Joins that need approval wait for an owner or admin's Confirm on the client's Members page, which shows the person's fingerprint. The desktop agent doesn't confirm, for the same reason as in "MSP templates".

**The enrollment token** is per client, random (256 bits), and shown to the MSP's staff in the console. It lets an account ask to join that client as a regular member; it never grants the org key. Joins through it are auto-approved, per the Business defaults, so the token is a credential: the console can replace it (old installs then stop working for new joins), and each join is recorded with when it happened. The server keeps it like upstream keeps organization API keys. An account in another organization can't join (single organization).

- **Limiting it to email domains:** an MSP admin can list a client's email domains (acmedental.com, and others), and then only accounts at exactly those domains can join with the command; mail.acmedental.com is its own entry. An email counts only once it's verified, or anyone could sign up as ceo@acmedental.com and walk in, so the limit needs a server that sends email, and the extension tells an unverified person to verify first. Someone the client's admins invited by email can still join with the command from any address: an admin chose them. Changes go in the MSP's activity log.
- **No click only with domains (decided October 2026):** a join with the install command gets in without anyone approving it only when the command is limited to email domains (verified emails), and the join's proof checks out against the command's join secret (see "Joins a hacked server can't forge"). Without domains, the command can be copied off any machine it ran on and used with any account, so those joins wait for an owner or admin to approve them, and the owners' email says so. The console asks MSPs to set domains.
- **Invitations through the command:** someone the client invited by email can join with the command instead of the link, but only for a regular invitation (not admin, owner, access to all items, or a custom role) and, where the server sends email, from a verified address. Otherwise registering an invited address would be enough to take its invitation. Joining gives Can edit in the Everyone collection, except to someone whose invitation already gave them a grant there, which stays as the admin set it.
- **Who hears about a join:** the client's own owners get an email for each one ("<email> joined Acme Dental with your IT provider's install command", or "is waiting to join" where an admin approves joiners), with a link to the Members page. Its MSP's people don't: a rollout to 50 machines would be 50 emails, and the console's Activity has every join. A person who was invited by email first is the inviter's to hear about, as for any invitation.

- **What the extension won't do:** send the token to any server but the one the same policy names (an account on another server never sees it); join for MSP staff, who sign in on their clients' computers; or keep the token itself (it remembers a hash, to ask once per token).
- **The command can't carry code:** the console checks each part of the command it shows (the token, join secret, and key fingerprint are 43 base64url characters each, the server a plain HTTPS address, the script name a `.ps1` file) and single-quotes them for PowerShell. A token that isn't one isn't shown or copied, so a hacked server can't turn the command into code the RMM runs on every client machine. The install script checks the token and address again.

**Status:** built. The server issues a token with each new client and joins through upstream's invite acceptance; the MSP console shows each client's install command with a copy button, the number of people who joined with it, and (for MSP admins) a way to replace the token; the install script writes the extension's managed settings; the extension asks, joins after unlock, and says so once. An end-to-end test runs the whole path with real keys on the mail test server: the extension asks, the person joins, an MSP admin approves them on the Members page and recovers their account, and they sign in with the new password to an intact vault. Another says "Not now" and checks nothing joined, and that a token for another server goes nowhere. Email domains and join emails are built too (`enrollment_domains` on the server, the console's install command panel), with mail tests for both and a console test. Not yet: the install script's download URL with a pinned signature (the console shows the command for a local copy of the script).

**Tests:** API tests for the token endpoints and their permission matrix, joining (with and without account recovery, already a member, single organization, a replaced token), and that a join never includes the org key. The extension's join logic gets unit tests with managed settings stubbed. Tier 2 runs the real install script on Windows and checks the policy values the browsers will read.

A company that runs its own IT gets what an MSP's client gets, without setting up the MSP console: the Business defaults, the Everyone and Admins collections, and an install command. An IT team that runs several companies or locations uses the MSP console instead.

- **"New organization" asks what it's for.** A business (the default choice) gets the Business preset in one server call (`POST /keykeeper/organizations`), so a closed browser tab can't leave it half set up: single organization, master password requirements, account recovery with automatic enrollment, the Everyone and Admins collections, and an install command. - **The install command is on the organization's Settings page**, below Joining, for its owners and admins: the command with a copy button, how many people joined with it, email domains (with a server that sends email), and Replace token. ## Folders and permissions

One word, "folder", for every place an item lives, grouped by who owns it, like a drive: **Personal** holds your private folders, and **each organization** holds its shared folders. An item in Personal is yours alone; to share it, move it into an organization's folder, and from then on it belongs to that organization. Each shared folder says, per person or group, exactly what they can do there, as a grid of capabilities with presets for speed. (Decided by the owner, October 23, 2026.)

### The model

- **Personal** is upstream's individual vault, and its folders are upstream's folders: only you see them, and nothing in Personal has permissions, because it's yours.
- **An organization's shared folders** are upstream's collections. Everything in them belongs to the organization, encrypted with its key; who reaches a folder is upstream's collection access (directly or through a group), with the capabilities below.
- **Sharing is moving:** "move to an organization" re-encrypts an item with the organization's key (upstream's share), into one of its folders. Nothing moves back out of an organization (upstream's rule); a copy is a new item.
- **An organization item can be in several of its folders** (upstream). Upstream also lets anyone file any item they see in one of their personal folders, which is per person; the web vault no longer offers that for organization items, and a personal folder in the menu shows whatever its owner filed there.
- **Words:** "vault" leaves the screens (see "Where 'vault' stays" below). Code, wire, and database names stay upstream's (collections, folders, organizations), as the naming rule says.

### The grid

Ten capabilities, set per shared folder for each person and each group that reaches it:

| Capability | Lets them | Enforced by |
|---|---|---|
| See items | Get the folder's items at all: in sync, by id, their attachments | Server |
| See passwords | See and copy passwords, hidden fields, one-time codes, card numbers and codes, and SSH private keys | Apps |
| Create | Make new items in the folder, or add an existing item to it (with share on that item) | Server |
| Edit | Change an item's contents and attachments, and restore an earlier version | Server |
| Delete | Move items to the trash, restore them from it, and delete them for good | Server |
| Export | Include the folder's items in an export | Apps |
| Share | Move an item out of the folder, add it to another folder, or copy it somewhere else | Apps (the server also refuses moving it out and adding it to another folder) |
| Print | Print an item | Apps |
| View item history | See an item's earlier versions (who and when only, without see passwords in the same folder) | Server |
| Manage | Change the folder's name, and who reaches it and with what | Server |

- **What needs what:** every capability needs see items, so taking see items away takes the person or group out of the folder. Export, print, and share need see passwords, since each puts an item's secrets somewhere this folder's rules don't reach. Manage includes every other capability: whoever manages a folder can give themselves anything in it, so the grid says so. Create, edit, and delete are independent: a drop folder has create without edit, and a reference folder edit without delete. The server refuses a grid that breaks these rules; it never fills in a capability that wasn't asked for.
- **Presets**, in the access selector, with Custom opening the grid:

  | Preset | Capabilities |
  |---|---|
  | Can view | See items, see passwords, print, view item history |
  | Can view but not see passwords | See items, view item history |
  | Can edit | See items, see passwords, create, edit, delete, share, print, view item history |
  | Can manage | All ten |
  | Custom | Any other set |

  Export is in Can manage only, as upstream lets only folder managers and admins export an organization's items; Custom adds it. Upstream's fifth preset, "Can edit except passwords", is a Custom set (see items, create, edit, delete, view item history).
- **More than one way to a folder:** someone who reaches a folder directly and through groups gets, for each capability, the most open of those ways. So see passwords is off only if every way turns it off: the Access page's rule, and now the server's on every path (upstream's server let a direct grant override all of a person's group grants on some paths, and not others).
- **An item in more than one folder:** for each capability, what any folder holding it allows, as upstream decides edit and see passwords. Adding an organization's item to another folder needs share on the item and create there, and taking it out needs share in the folder it leaves (below). Two things need two capabilities in the same folder, never one from each of two: an item's old versions' contents (view item history and see passwords) and clearing its history (view item history and delete).
- **Who the grid doesn't limit:** the owner of a personal item, and owners, admins, and managers with access to all items (upstream's custom role that manages all collections) have every capability in every folder. Other members with access to all items (an MSP's technician with vault items, or someone in a group with access to all) have every capability in every folder but manage: a custom role never manages every folder ("Roles and permissions"). Everyone else gets what their grants say, upstream's Manager role included (Vaultwarden showed a Manager's editable folders as managed without letting them manage them; now what it shows is what it allows).

### What the server enforces, and what the apps do

**The server enforces see items, create, edit, delete, manage, and view item history.** No client can get past these, whatever it runs:

- **See items:** only people who reach a folder get its items, in sync or one by one, and their attachments (upstream).
- **Create:** every way an item comes into a folder: making an item in it, moving a personal item into an organization (share), importing into the organization, and adding an existing item to the folder (one item or several at once, from the vault, the admin console, or upstream's share request for an organization's item).
- **Adding an existing item to another folder is sharing it:** that folder's people then see it, under that folder's rules, which can let the person who added it delete it or read its history where the folders it was in didn't. So it needs share on the item (what any of its folders allows, the same rule the apps use for copying it) as well as create in the new folder, on every path above. Someone who can edit an item without share can't move it somewhere they could do more with it. An MSP template's source needs share too, since its copies go into other organizations.
- **Edit:** saving an item's contents, as one item or as part of a move, and adding or deleting its attachments. Restoring an earlier version is an edit.
- **Delete:** moving to the trash, restoring from it, and deleting for good, one item or several, from the vault or the admin console. Clearing an item's history, or deleting one of its versions, needs delete and view item history in the same folder.
- **Changing an item's folders:** needs edit and see passwords on the item (upstream's rule, so moving an item can't show someone passwords they couldn't see), share on the item and create in each folder it's added to, and share in each folder it leaves. An item must stay in at least one folder for anyone without access to all items, who would otherwise lose it. An item's `collectionIds`, in sync and in every response about one item, list each of its folders the person reaches, read-only ones included, so the item form posts back the folders it was in and a save never takes it out of one by leaving it off.
- **Manage:** the folder's name, people, and groups (`PUT /organizations/<org>/collections/<id>` and bulk access). A regular member who manages a folder now gets exactly what upstream's dialog needs for it, from a fixed list of routes (`keykeeper_folder_permissions.rs`): that folder's details and access, the names and emails of members who have joined (`users/mini-details`: accepted and confirmed, not invitations or revoked members), the group names (without a directory's id, as for custom roles), and the folder list, with access lists only for the folders they manage. Making and deleting folders stays with owners, admins, and managers (upstream's "limit collection creation" and "deletion" settings, which our server turns on). A confirmed member turned away from a manager's route gets 404, as for something that isn't there, not upstream's 401, which signs the web vault out. Custom members get 404 there too, since the web vault signs out on 403 as well (they keep 403 elsewhere, "Roles and permissions"). When the database can't say whether someone manages a folder, these routes answer 500, not 404, so an admin isn't told they aren't a manager.
- **View item history:** `GET /api/keykeeper/ciphers/<id>/history` answers 404 without it, as it does for a missing item. Versions come back with their contents only for someone with view item history and see passwords in the same folder of the item (or access to all items); otherwise with who and when only. Someone with history in one folder and passwords in another gets who and when: merging them would show old passwords where neither folder allows it. Clearing refuses with 400, not 403, which signs the web vault out.
- **Imports are checked before anything is saved:** every relationship names an item and a folder of the import, every folder is one the person can add to (or, for someone with access to all items, may make), and someone without access to all items places every item. Each item goes into its folders as soon as it's saved, and an item that can't be saved stops the import there, so no item is ever left outside the folders it named.
- **A database error refuses:** if our rows can't be read, the request fails rather than reading grants as their presets, which can be more open. Upstream's row and ours for a grant are written in one transaction, so they can't disagree.

**The apps enforce see passwords, export, print, and share.** Anyone who can decrypt an item can take it out with their own tools: a member holds the organization's key, because the item's other fields need it, and the server can't send the item without its password. 1Password documents the same limit for the same reason. So the server does what can't be bypassed, and our apps do the rest:

- **See passwords:** apps hide the secret fields and their copy buttons (upstream). The server already holds back what it can: version contents in item history, and moving an item into a folder that would show its passwords.
- **Export:** an export includes only items in folders where the person can export. The export page offers an organization only if they can export one of its folders, and refuses an organization export that would include a folder they can't export. A personal export never includes organization items (upstream).
- **Print:** the web vault's item view has Print only where the person can print the item.
- **Share:** the apps offer copying (clone) only where one of the item's folders lets the person share, and moving an item out of a folder (the item dialog's Folder picker, Add to shared folders) only where that folder does. A copy is a new item to the server, so only the apps can stop it; the move out is a server change, so the server refuses it too.

### Storage and the API

- **Upstream's three fields stay the closest preset:** each grant (`users_collections` for a person, `collections_groups` for a group) keeps `read_only`, `hide_passwords`, and `manage`: manage if the grid manages, otherwise `read_only` is "can't edit" and `hide_passwords` is "can't see passwords". Upstream clients read those, so they show Can view, Can edit, or Can manage and the like, and see each item's `edit`, `viewPassword`, and `permissions.delete`/`restore`, which follow the grid exactly.
- **Our tables** `keykeeper_users_collections` and `keykeeper_collections_groups` hold the other six (create, delete, export, share, print, view item history) for a grant, with the three upstream values it was saved with. They count only while the grant's upstream values are still those; a grant without a row, or whose row no longer matches, is the preset its upstream values name (upstream's "Can edit except passwords" included). Rows go with their grant (`ON DELETE CASCADE`). No migration: nobody has data yet.
- **One object everywhere a grant goes:** every request and response carrying upstream's `{id, readOnly, hidePasswords, manage}` gains `keykeeper: {seePasswords, create, edit, delete, export, share, print, viewHistory, manage}`: making and editing a folder, bulk access, inviting and editing a member, making and editing a group, and the folder, member, and group lists. Each collection in sync carries the person's merged capabilities there. When a request has the object, it decides the grant and the server derives upstream's three fields from it.
- **A grant sent without the object keeps its grid while its fields are unchanged.** Every save resends every grant (a folder's people and groups, a member's folders, a group's folders, bulk access), and upstream clients can't send ours, so the server reads the grants a save replaces before deleting them: a grant whose upstream fields are the ones it had keeps its grid, and one whose fields changed becomes the preset they name, as an upstream client showed it. Our CLI sends each grant's grid back, and refuses a grant whose grid and fields disagree ("make readOnly/hidePasswords/manage match the grid, or remove keykeeper to use the preset"): sent without its grid, an edited grid would be dropped without a word while the fields stayed as they were.

### Who can give what

- **Owners and admins,** including an MSP's admins and admin technicians: anything, in any folder.
- **A folder's managers:** anything in that folder, to anyone in the organization, since they have everything there. Only for the folders they manage.
- **Custom roles that manage members, and MSP technicians with a custom role** ("never more than they have", in "Roles and permissions", now per capability): in a folder, only capabilities they have there themselves, merged over all their ways in; any capability except manage if they have access to all items; never manage. The rule checks the grant that would result, so a request with only upstream's fields is checked as the grant they'd keep or the preset they name. A grant an edit leaves exactly as it was isn't one the role gives, so it isn't checked: re-saving a member someone else gave more doesn't fail, and changes nothing. Editing someone leaves their other folders alone, and custom roles still can't change groups.
- **Technicians and client members are just people in the grid:** a client's admin can give an MSP's technician a folder like anyone else, and a technician without vault items sees only folders given to them.

### The Access page and offboarding

- **The Access page** shows each person's merged capabilities in each folder they reach: the preset's name when it's one, otherwise "Custom" and the capabilities in words. Reaching a folder several ways shows each way with its own. By folder, the same for each person.
- **Removing or revoking someone** still lists the logins whose passwords they could see: in folders where any of their ways gave see passwords. Export, print, and share don't change that list: whoever could see a password could have copied it.

### Upstream clients

They keep working, a little less precisely. They show the closest preset and the server enforces the grid, so they can offer something it then refuses (creating where someone can edit but not create), but never get more than the grid allows. Export, print, and share are ours, so an upstream client doesn't hide them, the limit every app-enforced capability has anyway. Saving from an upstream client keeps each grant's grid unless the client changed that grant, which then becomes the preset it showed.

## Provisioning from Entra ID

People join and leave a client's Microsoft 365 every week, and adding and removing them by hand is an MSP's daily chore. With provisioning on, Microsoft Entra ID's provisioning service keeps the client's PassBundle organization in step over SCIM 2.0: someone assigned to the PassBundle app in Entra is invited, someone turned off or unassigned loses access, and someone deleted leaves. Entra's groups can become PassBundle groups with the same members. Built from RFC 7643 (the SCIM schema), RFC 7644 (the protocol), and Microsoft's public documentation for SCIM endpoints, never from another product's code (CLEAN_ROOM.md). Any SCIM 2.0 client should work; Entra is the one we test against.

### Setting it up

- **Where:** the organization's Settings, then Provisioning, for its owners and admins. For an MSP's client, its MSP's admins and the client's own owners and admins, but not technicians, as for script tokens. Anyone else gets "not found", never 403 (upstream's web vault signs out on 403).
- **What it shows:** the organization's SCIM URL, `https://<server>/scim/v2/<organization id>`, "Create token", and once there is one, when it was made and by whom, when it was last used and from where ("last sync"), Replace token, and Revoke.
- **In Entra** (the page says this in a few steps): Enterprise applications, New application, Create your own application, "Integrate any other application you don't find in the gallery". Then Provisioning, mode Automatic (or New configuration), Tenant URL = the SCIM URL, Secret Token = the token, Test connection, Save. Assign the users and groups who should be in the organization, and start provisioning. Entra's first cycle takes a while; after that it syncs about every 40 minutes. Adding `?aadOptscim062020` to the Tenant URL turns on Entra's more standard PATCH requests; we accept both.

### The token

- **Made by the server:** 32 bytes from the operating system's random generator (`ring`'s `SystemRandom`), written as `pbscim1_` and 43 base64url characters: 256 bits of entropy. The prefix lets secret scanners and people recognize it, and the version leaves room for a later format.
- **Shown once:** only in the answer to the request that made it. The page shows it with a copy button and says it won't be shown again.
- **Kept only as a hash:** the server stores the SHA-256 of the whole token (base64). A 256-bit random secret needs no slow hash: there's nothing to guess.
- **One per organization.** Create makes one. Replace makes a new one and the old one stops at once (Entra's requests fail until the new one is pasted in, then Entra retries). Revoke deletes it: provisioning stops, and Entra quarantines the job after repeated failures.
- **Checking a request:** the server reads `Authorization: Bearer <token>`, requires the token's shape, finds the stored hash of the organization named in the URL, and compares the SHA-256 of what was presented with it in constant time (`crypto::ct_eq`, the `subtle` crate). It never looks a token up across organizations: the URL's organization picks the one row a token can match, so a token only ever works at its own organization's URL. Every failure (no header, another scheme, a malformed or wrong token, an organization with no token, an organization that doesn't exist) is the same 401 SCIM error with `WWW-Authenticate: Bearer`, so the answer never says whether an organization exists.
- **Never in logs:** the server's request log leaves out SCIM query strings (filters carry names and emails) and never logs headers. Event and activity entries say a token was made, replaced, or revoked, and by whom, never its value.
- **Limits:** 600 requests a minute per organization; 200 new invitations a minute and 2,000 a day (each sends an email, so a stolen token can't make the server a source of spam); and 60 refused tokens a minute per address. Past a limit, 429 with `Retry-After: 60`; Entra retries later. Every 1,024 requests the limiters forget addresses whose limits have filled back up, as the login limiters do, so requests from many addresses can't grow them without bound.
- **The same work either way:** for an organization with no token, the presented token is still hashed and compared, in constant time, with a stand-in as long as a real hash, so timing doesn't say whether an organization has one.
- **Last sync:** the time and address of the last accepted request, written at most once a minute.

### What a token can and can't do

This is the whole of what a stolen token is worth, in its own organization only.

**It can:**
- list the organization's members as SCIM users: their account email, what Entra sent about them (name, emails, externalId, and so on), and whether they're on; and the groups provisioning made, with their members.
- invite any email address as a regular member, which also lets that address make an account on a server where only invited people can sign up (with email, from the invitation's link). An invitation alone gives nothing in the organization: the organization's key comes only from an owner's or admin's app, which lets in someone only the directory invited only after an owner or admin lets them in, or when they join with the install command at the client's verified email domains (see "Getting in").
- turn regular members off and back on, and remove them. It turns back on only people provisioning turned off.
- make, rename, and delete the groups provisioning made, and change which regular members are in them. That changes which shared folders they reach through those groups, which an owner or admin gives each group in PassBundle.

**It can't:**
- read any vault item, key, or other encrypted data. No SCIM endpoint returns any, and SCIM never gets or gives a key.
- let anyone in: give the organization's key, confirm anyone, make or read seals, or read the install command or its join secret.
- make or replace tokens, or change any setting or policy.
- add, change, turn off, or remove owners, admins, custom roles, anyone with access to every item, or an MSP's staff (refused with 403, below).
- give a group access to shared folders, give anyone a role, or touch a group made in PassBundle.
- reach another organization: the token is checked against the URL's organization only.

### Users

| Entra sends | PassBundle does |
|---|---|
| `GET /Users?filter=userName eq "..."` | Finds the member Entra knows by that userName, or a member whose account email it is. |
| `POST /Users` | Invites them as a regular member, or links someone already in the organization. 201, or 409 for a userName already provisioned. |
| `GET /Users/<id>` | The member, on or off. |
| `PATCH /Users/<id>` | Keeps the new attributes; `active` false or true turns them off or on. 200 with the user. |
| `PUT /Users/<id>` | The same, replacing what's kept. |
| `DELETE /Users/<id>` | Removes them from the organization. 204. |

- **Who SCIM sees:** every member of the organization, so Entra matches people who were there before provisioning instead of inviting them twice. A user's id is their membership's id.
- **What's kept:** what Entra sent (name, displayName, emails, title, the enterprise extension, and so on) as it sent it, in `scim_users`, returned as sent. Attributes sent as null are left out. Never kept: a password, roles, entitlements, groups. At most 16 KiB per person.
- **Matching:** filters on userName, externalId, `emails[type eq "work"].value`, and id, with `eq`, `ne`, `co`, `sw`, `ew`, `gt`, `ge`, `lt`, `le`, `pr`, `and`, `or`, `not`, and value paths in brackets. Attribute names and operators in any case; values in any case, except `id` and `externalId`, which RFC 7643 makes case exact. A member Entra hasn't linked shows their account email as their userName.
- **Who's invited:** the work email Entra sends (`emails[type eq "work"]`, which Entra fills from the user's mailbox), else the primary or first email, else the userName when it's an email address (Entra fills userName from the user principal name). Without any, 400 saying so. An account's email never changes through SCIM; a new userName is kept for matching only.
- **Someone already in the organization** (that email's account is a member): a regular member is linked, and their membership isn't changed. Linked to two Entra users at once: 409. Someone provisioning never changes (below) isn't linked: 409, saying so; Entra matches them by their account email as userName instead.
- **A userName is never another member's email:** creating or renaming someone to another member's account email is 409, so the directory can't take the name an owner or anyone else is matched by.
- **Always a regular member:** roles in the request are ignored; making owners, admins, and custom roles stays in PassBundle.
- **The Everyone collection:** people provisioning invites get the organization's Everyone collection, if it has one (the Business preset), as people who join with the install command do.

**Getting in.** Joining means getting the organization's key from an owner's or admin's app, which does it on its own only when something the server can't forge vouches for the person (see "Joins a hacked server can't forge"). An admin's browser seals the invitations they send from the Members page; Entra's requests reach only the server, and nothing in them can be checked by an app, so a hacked server could claim Entra invited an address of its own. So invitations from provisioning carry no seal (an earlier seal for that address is removed), and:
- **With the install command (the MSP way):** someone who joins with the client's command, limited to its email domains, with a verified address there, is let in without a click: the extension's join proof vouches for them, as for anyone who joins with the command. Unlike an admin's invitation, the directory's doesn't exempt the address from the command's domains: otherwise a stolen provisioning token plus a command copied off any machine would let in any address.
- **By the emailed invitation, or by signing up on a server without email:** they accept as anyone invited does (signing up first if they have no account; without email, upstream's rule lets the invited address sign up and joins them at once), then wait to be let in. The Provisioning page lists everyone the directory invited whom nothing vouches for yet; an owner or admin looks at the list, ticks the people they recognize, and Let them in, and their browser seals those invitations exactly as if they'd sent them from the Members page. Their apps then let them in in the background, before or after the person accepts. The Members page's Confirm, with the fingerprint, still works for one person.
- **Who hears about it:** the server treats these as waiting for approval (`confirms_automatically`), so the pending list says so and apps don't try them, and the inviter's email (the billing email, since nobody in PassBundle sent it) is upstream's "accepted your invitation", not "joined".
- **Why not let them in automatically:** sealing the directory's invitations by itself (say, every address at the client's domains) would let a hacked server get the organization's key by making up an address at those domains. An admin looking at the list once, or the install command's secret, is what a hacked server can't fake.

**Turning off and on.**
- `active` false (Entra sends this when someone is turned off, unassigned, or deleted in Entra, and the string "False" without its compliance flag) is the Members page's Revoke: no access, but the membership, its groups, and its folders stay, so turning them back on restores everything, as Microsoft asks of a soft delete. Their own vault is theirs throughout.
- `active` true is Restore, with upstream's checks (single organization, two-step login): refused with 409 and upstream's reason if they fail.
- Provisioning turns back on only people it turned off. Someone an owner or admin revoked in PassBundle stays off until an owner or admin turns them on (403).

**Removing.** `DELETE` (Entra sends it when a user is permanently deleted, 30 days after a soft delete) is the Members page's Remove: the organization's items stay with it, and the person's own vault stays theirs.

**People provisioning never changes:** owners, admins, custom roles, anyone with access to every item, and an MSP's staff. They're listed and matched by their account email, so Entra doesn't invite them again, and they're read-only: every PATCH, PUT, and DELETE for them is refused with 403 and a sentence saying why, nothing Entra sends about them is kept, and group changes leave them out. The one thing noted is whether Entra asked to turn them off, keyed by their own account email, never by a userName the directory chose. When Entra asks to turn one off or remove them, the Provisioning page lists them ("Entra turned these people off; remove them here if they've left"), so someone who left the company doesn't keep an owner's or a technician's access unnoticed.

### Groups

- **Made by Entra:** `POST /Groups` makes an ordinary PassBundle group with no shared folders and no access to every item; an owner or admin gives it folders in PassBundle. Its externalId (Entra's object id) is upstream's group external id.
- **Names are unique** in the organization, in any case, as Entra matches groups by displayName: a name another group has is 409.
- **Only groups provisioning made** are visible to SCIM. Groups made in PassBundle are never read, changed, or removed by it.
- **Members:** `PATCH` adds and removes members in the shapes Entra sends: `add` with `path: "members"` and a list of `{ "value": id }`; `remove` the same way, or with `members[value eq "<id>"]`; `replace` with the whole list. 204, as Microsoft asks. An id that isn't a member of the organization is 400. People provisioning never changes are left out of every change. A regular member the directory puts in a group before they're confirmed gets nothing from it until an owner's or admin's app confirms them and an owner or admin gives the group shared folders.
- **Rename and externalId:** `replace` on `displayName` or `externalId`. A renamed or changed group in PassBundle is overwritten at Entra's next change to it.
- **Remove:** `DELETE` removes the group; its members lose what they reached through it.
- **Reading:** `GET /Groups?filter=displayName eq "..."`, `externalId`, `id`, and member checks (`id eq "..." and members[value eq "..."]`); `excludedAttributes=members` is honored.

### The protocol

- **Discovery:** `ServiceProviderConfig` (PATCH yes; bulk, sort, ETags, and password changes no; filters up to 200 results; the bearer token), `ResourceTypes` (User, Group), and `Schemas` (User, Group, and the enterprise User extension). All need the token.
- **Lists:** a ListResponse, `startIndex` from 1, `count` 100 unless asked for fewer, at most 200, with `totalResults`; `attributes` and `excludedAttributes`.
- **Errors:** RFC 7644's error JSON, with the status as a string and `scimType` where one applies (`invalidFilter`, `invalidSyntax`, `invalidPath`, `invalidValue`, `mutability`, `noTarget`, `uniqueness`), as `application/scim+json`.
- **Entra's quirks:** `op` in any case (Entra sends "Add", "Replace", "Remove"); attribute names in any case; `active` as a boolean or "True"/"False"; replace without a path whose value has paths as keys (`"name.givenName"`, enterprise URNs); `emails[type eq "work"].value` creating the work email when there's none; unknown query parameters such as `aadOptscim062020` ignored; resource names in the path in any case. Bodies up to 1 MiB.

### Events

- **The organization's event log:** invited, revoked, restored, removed, group created, changed, and deleted, and a member's groups changed, with "SCIM" as who acted (upstream's system user 1, which the web vault names) and Entra's address.

## Sign in with Microsoft Entra ID

Each organization, and so each of an MSP's clients, can let its people sign in with their Microsoft 365 work account. Each one connects its own Entra tenant: there's no PassBundle-wide identity provider, and one organization's sign-in never signs anyone in to another's. Single sign-on proves who someone is; their master password still unlocks their vault, so nothing about keys changes (upstream's "SSO with master password"). Built from the OpenID Connect Core 1.0 and Discovery specs, RFC 7636 (PKCE), and Microsoft's public documentation ("OpenID Connect on the Microsoft identity platform", "ID token claims reference", "Optional claims reference", "Signing key rollover", "Register an application"), never from another product's code (CLEAN_ROOM.md). Vaultwarden's own OpenID Connect code (one provider for the whole server, accounts matched by email) stays in the server for merges, but the server refuses `SSO_ENABLED`.

### Setting it up

- **Where:** the organization's Settings, Single sign-on, for its owners and admins, and for an MSP's client its MSP's admins (not technicians), as for provisioning. Anyone else gets "not found", never 403 (upstream's web vault signs out on 403).
- **What it asks for:** turn it on; the SSO identifier people type (3 to 40 lowercase letters, digits, and hyphens, unique on the server); the Directory (tenant) ID and the Application (client) ID, both GUIDs; and the app's client secret. The page shows the redirect URI to paste into Entra (`https://<server>/identity/connect/oidc-signin`), a link that starts the sign-in, the setup steps (docs/sso-entra.md has them in full), the email domains, and the accounts linked so far.
- **Turning it on checks the tenant:** the server fetches the tenant's OpenID configuration and refuses a tenant Microsoft doesn't know, and the personal-accounts tenant (`9188040d-...`).
- **The secret is write-only:** sent once with Save, never in any answer. The page says when it was saved; saving with the field empty keeps it.
- **Changing the tenant** removes the links to the old tenant's people, who can't sign in here anymore, and ends their sessions everywhere (their refresh tokens stop working). It's refused while Require single sign-on is on, since everyone would have to link again at once. Turning single sign-on off ends the sessions of everyone linked.
- **Who isn't linked yet:** the page, and the Require single sign-on policy's dialog, list the members the policy covers (or would) who aren't linked, and say what happens to them when it's on (below).

### How a sign-in works

The server is the OpenID client of the organization's tenant: it holds the app's secret, redeems the code, and checks the ID token. The web vault is the server's client, with its own state and PKCE challenge, as upstream's apps already expect, so upstream's sign-in pages work unchanged.

1. The person types their email and chooses Use single sign-on. If the email's domain is verified (below), the web vault finds the organization's identifier by itself (`POST /api/organizations/domain/sso/verified`); otherwise they type it. `GET /identity/sso/prevalidate` checks it.
2. `GET /identity/connect/authorize` (web vault and browser extension only, back to the web vault's `sso-connector.html` only, at most as often as pre-login per address): the server keeps the app's state, client, redirect URI, and PKCE challenge, makes its own state, nonce, and PKCE verifier (32 random bytes each), sets a cookie tying the answer to this browser (HttpOnly, SameSite=Lax, path `/identity/connect/`, ten minutes, and Secure whenever the server's own address is HTTPS, never decided from a request header), and sends the browser to the tenant's authorization endpoint with `response_type=code`, `scope=openid profile email`, `response_mode=query`, the state, nonce, and S256 challenge.
3. Microsoft sends the browser back to `/identity/connect/oidc-signin`. The server takes the sign-in by its state, once, from the browser with the cookie, and right away redeems Microsoft's code at the tenant's token endpoint with the client secret, its PKCE verifier, and the redirect URI, then checks the ID token (below). Whatever that comes to, the browser goes back to the web vault with a one-time code of the server's own and the app's state; the outcome is told when the code is redeemed, so the person sees why.
4. The web vault redeems that code at `/identity/connect/token` (`grant_type=authorization_code`) with its PKCE verifier, the same client, and the same redirect URI. The server decides which account it is (below), runs two-step login as for a password, and answers as a password sign-in does: the account key wrapped by the master key, which the person's master password unwraps. Someone invited who has no account yet is asked to set a master password, upstream's first single sign-on.
5. The session is PassBundle's own, refreshed as a password session is, while the account is still linked in an organization whose single sign-on is on (checked at every refresh). Microsoft's tokens aren't kept.
6. **Linking an account** (upstream's Link SSO, in an organization's menu in the vault, or a linking session, under Require single sign-on below), in four steps:
   1. **A ticket:** `POST /api/accounts/sso/user-identifier`, from a signed-in session with its master password hash (a one-time code only for an account without a master password, since a code proves only the mailbox; never an API key's token, which proves no password), or from a linking session, which already proved the password and two-step login. 32 random bytes, five minutes, once, kept as a hash. The answer sets a cookie (HttpOnly, SameSite=Strict, path `/identity/connect/`) that the ticket only works with, so a ticket finished in another browser (say, a coworker's, where Microsoft would sign the coworker in) links nothing and is gone. A linking session's ticket works only for its organization.
   2. **Microsoft:** the web vault passes the ticket to authorize as `user_identifier`, and the server adds `prompt=select_account`, so the person picks the Microsoft account instead of the browser using whichever one is signed in.
   3. **A pending link:** the callback checks the ID token as for any sign-in, and holds the result with the account and the session that asked (a device, or the linking session). The browser goes to the web vault's `/sso-link` page with a one-time code. A link's code is never redeemed as a sign-in.
   4. **Confirmation:** the page shows which Microsoft account (its name and email), which PassBundle account, and which organization (`POST /api/accounts/sso/link/pending`), and the person confirms (`POST /api/accounts/sso/link/confirm`). Both need the session that asked: another account's, or another session of the same account, gets "expired" and doesn't use up the code. Only then is the link made, under the rules below. A linking session ends with it.

   Unlink SSO (`DELETE /api/accounts/sso/<organization>`) undoes a link and signs the account out everywhere. Leaving or being removed from the organization deletes the link too, so sessions it started stop refreshing.

### What's validated

The ID token (`api/core/keykeeper_sso/token.rs`, a pure function with a unit test per check):
- **Signature:** RS256 only (never `none`, never an HMAC keyed with a public key), with a key the tenant publishes at its own `jwks_uri`, by `kid`. An unknown `kid` fetches the keys again, at most every five minutes per tenant, as Microsoft's key rollover guidance says.
- **`iss`** is exactly `https://login.microsoftonline.com/<tenant id>/v2.0`, the tenant's own issuer (the discovery document must name the same issuer, and its endpoints must be on the same host).
- **`tid`** is the organization's tenant, and **`ver`** is `2.0`.
- **`aud`** is exactly the app's client id, one audience; `azp`, if present, agrees.
- **`exp`**, **`nbf`**, and **`iat`** are in range, with five minutes of clock skew, and `iat` no older than ten minutes.
- **`nonce`** is the one this sign-in sent (constant-time compare); a missing one fails.
- **`oid`** is there and is a GUID.

And around it: the state is single use (taken before anything else happens) and expires in ten minutes; the cookie must match (so Microsoft's answer can't be replayed into another browser, and a sign-in started elsewhere can't be finished here); the server's one-time code is single use, expires with the sign-in, and needs the app's PKCE verifier, client, and redirect URI; states, codes, and the cookie are kept only as SHA-256 hashes; the server follows no redirects from Microsoft and reads at most 256 KiB; the request log leaves out the identity routes' queries.

### How accounts link

People are identified by Entra's immutable tenant id and object id (`tid` + `oid`), per organization (`keykeeper_sso_links`), never by email. Entra's `email` claim isn't verified (Microsoft: "never use it for authorization"), and an Entra admin can set a user's mail to anything; matching accounts by it is how the nOAuth class of account takeover happens. The rules (`link.rs`, a pure decision with a unit test per rule):

- **Already linked:** the person signs in to that account, whatever email Entra sends now, while the account is still within the rules below. A spoofed email never moves a link.
- **First sign-in, by email, only for an invitation without an account:** the email Entra sends is only a suggestion, and it links only an invitation whose account has no keys yet (invited by email or by provisioning, no master password set), never an account that has keys: anyone who can write a user's mail in the tenant (User Administrators, Exchange admins, apps with User.ReadWrite.All, on-premises AD through Entra Connect) could otherwise sign in to an owner's account. The email must be plain ASCII (lowercasing other characters can turn one into a letter: U+212A becomes k) and vouched for: Entra's `xms_edov` claim says its domain owner is verified, or, when Entra doesn't say either way, it's at a domain this organization verified with DNS and the person isn't a guest in the tenant (`acct` 1, or an `idp` other than the issuer). `xms_edov` false is never vouched for. The invitation must be this organization's (invited, joined, or confirmed, not turned off).
- **An account with keys links from its own session** (Link SSO, above): its person proved their master password (or their password and two-step login, for a linking session), picked their Microsoft account, and confirmed the link, so the email doesn't matter. The account must be a member of this organization, not turned off, or in no organization at all with an email at one of its verified domains; the Microsoft account must not be linked to another account here. A sign-in by email to such an account is refused and says how to link it.
- **Every link is told:** the account gets an email naming the organization ("If you didn't do this, tell its administrator"), and the event log has the person's first single sign-on (1510).
- **Never:** an account on any MSP's staff, by email or from a session (their account reaches every client, so one client's directory could otherwise sign in to all of them; they sign in with their master password); an account already linked to another Entra person here, or a Microsoft account already linked to another account; a member of another organization who isn't a member of this one; a disabled account. Nobody is made an account: someone with no account and no invitation is told to ask for one.
- **Each refusal says why** on the sign-in page ("isn't a member of Acme Dental", "is already linked to a different Microsoft account") and in the event log.
- **Unlinking:** the settings page lists linked accounts; unlinking one (say, after the person's Entra account was recreated) signs it out everywhere, and it links again the way it did the first time.

### Email domains

- **Proving one:** add the domain, and the page shows a TXT record for the domain itself, `passbundle-verification=<43 random characters>`. Verify asks the DNS (no cache) and verifies the domain when the exact value is there. Domains are exact (a subdomain is its own) and at most 20 per organization.
- **One organization each:** any organization may add a domain, but only one can verify it (a unique index decides a race), and a domain verified elsewhere can't be added.
- **What it does:** typing an email there finds this organization's sign-in (the answer is only its SSO identifier, since anyone can ask; never the organization's name), and emails there are vouched for when an invitation links, for members of the tenant. Removing it stops both; accounts already linked keep signing in.
- **It trusts the configured tenant:** a verified domain vouches for emails at it from whichever tenant the organization's settings name. An admin who points the settings at a tenant they control can make its users' emails at the domain look vouched for; that still reaches only invitations without an account, in this organization, and every link is emailed and logged. Admins are trusted with the organization's settings, as with any SSO.

### Require single sign-on

Upstream's policy (type 4), enforced by the server:
- **Who:** members who joined (accepted or confirmed) as anything but an owner: regular members, custom roles, and the organization's own admins. **Never:** owners, memberships that came through an MSP, and staff of the MSP that manages this organization. Decided per organization: being on some other MSP's staff (or making one) never gets anyone out of it. So an organization always has someone who can sign in with a password and fix its settings. Someone the policy covers who is also on another MSP's staff can't use the client's single sign-on either (it never signs in MSP staff), so they're stuck until an owner makes them an owner there or removes them; the sign-in refusal says so.
- **How:** a password sign-in (including a sign-in approved from another device) that checks out answers `SsoOrganizationIdentifier`, and the apps send the person to that sign-in; a wrong password says nothing about it. A password session ends at its next refresh. A sign-in with another organization's single sign-on doesn't count: it's refused, naming the organization whose sign-in to use (to the person; the event says only "another organization").
- **Members not linked yet aren't locked out:** without a link, single sign-on can't sign in an account that has keys, and a password would only send them there. So their password sign-in goes on through two-step login and then answers `SsoOrganizationIdentifier` with `KeykeeperSsoLinkSession`: a linking session (32 random bytes, kept as a hash, fifteen minutes, one at a time per account), not a login. It isn't a login token, so every request but the link ones refuses it (no sync, no vault, nothing else, and no refresh token); it can get a ticket for that organization's single sign-on and confirm the link, and it ends when the link is made. The web vault keeps it in the tab and takes the person to `/sso-link`: Microsoft, confirm, then single sign-on, then their master password unlocks. A sign-in approved from another device proves no password, so it can't start one. This covers the policy turning on, an unlink while it's on, and anyone who joins later. The other apps (the extension, for now) say to link in the web vault first.
- **API keys:** an API key sign-in (the CLI's `client_credentials`) skips the policy, as upstream's does. With the policy on, the Single sign-on page offers to replace the covered members' API keys (`POST .../sso/rotate-api-keys`; owners' and IT provider staff's stay), so old keys stop working; members get new ones from their account settings after signing in with single sign-on.
- **Prerequisites:** single sign-on on, and the Single organization policy (so a regular member belongs to one organization). Turning off Single organization, or single sign-on, while it's on is refused. It isn't an MSP default policy: each client's sign-in is its own.
- **Account recovery keeps working:** an owner or admin resets a member's master password as before; the member signs in with single sign-on and the new master password unlocks.

### The client secret

The server must use the secret, so it can't be hashed. It's sealed with event streaming's sealed-secrets module ("Sending events to security tools", "Secrets at rest"), so a copy of the database alone doesn't reveal it (`keykeeper_sso/secret.rs`):

- **Its own key:** AES-256-GCM under a key derived from the server's private RSA key as event streaming's is (HMAC-SHA256 over the key's PKCS#1 DER), but over another label, `passbundle sso client secrets v1`. The key lives with the RSA key, never in the database. So an event destination's ciphertext never opens as a client secret, and a client secret never opens as a destination's secrets, whatever the associated data says.
- **Bound to its organization:** the associated data is its own, `sso client secret`, a zero byte, and `organization <id>` (the module seals and opens with associated data its caller gives, `seal_aad_with` and `open_aad_with`; event streaming's binding is unchanged). A sealed secret copied to another organization's row doesn't open.
- **Opens only these secrets:** neither key can decrypt a vault, and the server holds no key that can.
- **Changing the tenant or app keeps the secret**, unlike event streaming's Sentinel secret: this one only ever goes to Microsoft's token endpoint for the organization's tenant, on the authority the server's operator configures (`SSO_ENTRA_AUTHORITY`), so another admin can't send it anywhere they can read.
- **If the RSA key changes,** the secret can't be read. Sign-ins are refused, saying an admin needs to enter it again, and the Single sign-on page says so. With Require single sign-on on, owners (exempt) still sign in with their password to fix it.
- **Test vectors:** `docs/vectors/sso-client-secret-v1.json`, made by `make-sso-client-secret-v1.mjs` with Node's crypto alone, from event streaming's vectors' RSA key. They check the key, the associated data, two sealed secrets, that one doesn't open as two other organizations', and both ways across the features: the same secret and associated data sealed with event streaming's key doesn't open as a client secret, and a client secret doesn't open with event streaming's key, as a client secret or as a destination's secrets. The server checks its copy in its unit tests, and Tier 1 checks that the copy is the meta repo's and that the generator still makes the file.

A certificate credential instead of a secret is later.

### Events

In the organization's event log: single sign-on turned on and off (upstream's 1604 and 1605) and its settings changed (1694, ours, naming what changed: identifier, tenant, app, client secret, or API keys replaced), high severity; a domain added, verified, not found, and removed (upstream's 2000 to 2003, with the domain); someone's first sign-in, which links them (upstream's 1510, by email or from a session); every sign-in (1590, ours); every refusal, with why in this server's own words (1591, ours: "ana@acme.test isn't a member", "the ID token was for another tenant", "Microsoft refused, as the browser reported it: access_denied"); and an unlink, by an admin or the person (upstream's 1505). What the browser brings back from Microsoft can be made up by whoever started the sign-in, so the event keeps Microsoft's error only when it looks like an OAuth error code (lowercase letters, digits, and underscores, at most 64; otherwise `unrecognized_error`) and never its description, which only the person sees. An MSP's activity log has the settings, domain, API key, and unlink changes in its clients, with who made them. Never logged: the secret, tokens, codes, tickets, or states.

Event streaming sends them to security tools with these severities: high for single sign-on turned on or off, its settings changed, a domain added, verified, or removed, and a link (1510); medium for a refusal and an unlink; low for a sign-in and a domain not found yet. Each carries its detail (what changed, the domain, the Microsoft account's email, or why someone was refused), never a secret, and a refusal its fixed `reason` code (such as `not_member`, `microsoft_refused`, `another_browser`, `code_redeem_failed`, and one per ID token check: `token_signature`, `token_tenant`, and so on). The changes and links are never dropped from a full queue; refusals, which anyone can make many of by starting sign-ins and sending back bad answers, merge like failed logins, but only with refusals for the same reason. In an MSP's feed, its activity entries are 9180 to 9187, high except unlinks (medium).

### Threat model

- **Another tenant's users** (the nOAuth case): can't sign in, because the issuer and `tid` must be the organization's tenant, and email never identifies anyone.
- **People in the organization's own tenant:** an account that has keys never links by email, so writing a user's mail (which tenant admins, Exchange admins, some apps, and on-premises sync can do) reaches at most an invitation that has no account yet, at an address vouched for, in this organization; the account hears about every link by email. A spoofed email never moves an existing link. The organization's Entra admins can already sign in as any of their users, so for that organization's sign-in they're trusted, as with any SSO; single sign-on still only authenticates, and the master password is needed to read anything.
- **One organization against another, or an MSP's clients against each other:** a client's sign-in never signs in a member of another organization who isn't its member, never MSP staff, and doesn't satisfy another organization's requirement.
- **A stolen browser code or callback URL:** useless without the browser's cookie, the app's PKCE verifier, and within ten minutes, once.
- **Linking someone else's Microsoft account:** a link ticket works only in the browser it was issued to, Microsoft is asked to let the person pick the account, the page names the Microsoft account before the session that asked confirms it, and the account is emailed. A stolen session alone can't link, even with the mailbox: a ticket needs the master password.
- **Login CSRF and sign-in mix-ups:** the state, the browser cookie, PKCE on both legs, and the one-time code.
- **A copy of the database:** holds no secret usable alone (the client secret is sealed under a key that isn't in it), only hashes of states and codes, and no key that opens a vault.
- **A hacked server:** gains nothing from single sign-on: it already issues sessions, and it still can't decrypt vaults.
- **DNS:** domain checks trust the server's resolver; DNSSEC isn't checked. A forged answer could verify a domain for the wrong organization, which matters only for finding the sign-in and for linking accounts at that domain that are in no organization (who still need a vouched-for email from that organization's tenant). Checked once, not again later.
- **Sessions outlive Entra:** turning someone off in Entra doesn't end a PassBundle session already open; provisioning's revoke does (it revokes their membership), and the next single sign-on is refused. Unlinking, a tenant change, removal from the organization, and turning single sign-on off end sessions; a single sign-on session refreshes only while its account is linked where single sign-on is on. Someone the policy covers who isn't linked yet and is turned off in Entra can't link, so can't sign in.

### Out of scope (for now)

Trusted-device unlock and anything else that changes how keys are held (its own design, with test vectors, first); making accounts on first sign-in without an invitation; single sign-on from the desktop and phone apps and the CLI (the web vault and the browser extension use it; the extension hands off to the web vault, upstream's way, untested); other identity providers (Okta, Google) and SAML; a certificate credential; single sign-out; checking domains again later; an MSP's own staff signing in with single sign-on.

## Two-step login for admins

"Client admins def need SSO or 2FA of some sort" (the owner, October 2026). Whoever runs an organization, or works for its MSP, can change who sees what, recover accounts, and reach every item, so their password alone isn't enough.

### Who
- **An organization's owners, admins, and custom roles that manage members, policies, or account recovery**, once they've joined (accepted or confirmed), where the organization requires it. Not regular members, upstream's managers, custom roles that only see the event log or import and export, nor invited or revoked memberships. Upstream's "Require two-step login" still covers regular members, and still exempts owners and admins.
- **Everyone on an MSP's staff**, every role, where the MSP requires it.
- A client's setting covers everyone in those roles there, an MSP's staff included, so a client can require it of its MSP's people even if the MSP doesn't.

### What counts
- An authenticator app (TOTP), a security key or passkey (WebAuthn), or Duo, that this server can use.
- **Email codes don't count (decided October 2026; the owner can change this):** a client's email admins could read a member's codes, the same reason linking to single sign-on never trusts an email. Upstream's YubiKey OTP doesn't count either (it needs Yubico's cloud, which the hosted service doesn't set up). Either is a one-line change (`QUALIFYING_TWO_STEP` in the server's `db/models/keykeeper_two_step.rs`).
- **Once someone it covers has a method that counts,** their sign-in doesn't offer or take email codes, so a mailbox alone never passes for the second step (upstream's recovery code still works). Setting up a method that counts also forgets the devices remembered for their two-step login, which may have been remembered with an email code.
- **Single sign-on:** a sign-in with an organization's own single sign-on meets that organization's requirement for its admins and custom roles, since the tenant's MFA covers them. Never another organization's requirement, never for owners (Require single sign-on exempts them so they can always sign in with a password, so their password needs the second step), and never for MSP staff (no client's single sign-on signs them in): for them two-step login is the protection.

### Defaults and settings
- **On** for the Business preset (a company's own organization, "A company's own IT") and in every new MSP's default policies, so Add client turns it on. **Off** for an organization made the upstream way (a family or a group). An organization from before it has no setting and counts as off; an MSP from before it requires it of its staff, but its clients' default is off until an MSP admin turns it on (there were no users to migrate).
- **The organization's setting:** its Settings page, "Two-step login for admins", for its owners and admins and its MSP's admins (not technicians), as for single sign-on; anyone else gets "not found" (`/api/keykeeper/organizations/<id>/admin-two-step`). Turning it on or off is an event in its log (1695, 1696), high for its security tools, and for an MSP's client goes in the MSP's activity log (`client_admin_two_step_set`).
- **An MSP's clients:** one of the default policies ("Two-step login for admins"), so following, own settings, and Use default work as for the others. Changing the default is logged high (`admin_two_step_default_set`). It isn't an upstream policy: upstream's apps refuse every policy when one has a type they don't know (the SDK's policy filter throws on it), so the MSP's default is kept with the others under type 1000, which the server never sends anyone as a policy, and each client's setting is its own row (`org_admin_two_step`).
- **An MSP's staff:** the MSP's own setting, on by default, in the console's Two-step login section; MSP admins change it, logged high (`staff_two_step_set`).
- **Who isn't set up:** the organization's Settings page lists everyone it covers (or would, before it's turned on) without a method that counts, and notes admins linked to its single sign-on, who are covered when they sign in that way. The MSP console lists its staff without one and each client's own admins without one. Each tells the person looking when they're on the list. Giving someone an elevated role without one is allowed; they set it up at their next sign-in.

### Signing in
- **A password sign-in** that checks out (the password, then any two-step login the account has, an email code included) by someone it covers who has no method that counts gets a setup session instead of a login: a 400 `invalid_grant`, as single sign-on's linking session, with `KeykeeperTwoStepSetup` (the token) and `KeykeeperTwoStepRequiredBy` (who requires it, by name). A wrong password says nothing about it.
- **The setup session** mirrors the linking session: 32 random bytes, kept as a SHA-256 hash, fifteen minutes, one at a time per account, and no refresh token. It isn't a login token, so every other request refuses it with 401. Only the endpoints that set up two-step login take it: `GET /api/keykeeper/two-step-setup` (what the page shows) and upstream's get-authenticator, authenticator, get-webauthn, get-webauthn-challenge, webauthn, get-duo, and duo, which still check the master password (or a one-time code for an account without one) as they do for a signed-in session. Setting up a method that counts ends it, and that answer carries the account's recovery code (`keykeeperRecoveryCode`), which the session couldn't fetch afterwards.
- **A single sign-on sign-in:** the same, for whatever that organization's single sign-on doesn't meet. Single sign-on proves no password, so the setup page asks for the master password.
- **A sign-in approved from another device** proves no password either, so it gets no setup session: it's refused, saying to sign in with the master password in the web vault.
- **An account without a master password yet** (an invitation's first single sign-on, which goes on to set one) isn't held up. The rule applies from its next sign-in, and its session stops refreshing once it has a password and no method that counts.
- **The web vault** keeps the token in the tab (sessionStorage, nothing else) and shows "Set up two-step login to continue" (`/two-step-setup`): who requires it, then an authenticator app (its QR code and key), a security key or passkey, or Duo. After a password sign-in the page has the master password's server hash in memory, so it doesn't ask again; after a reload or single sign-on, it asks. Once it's set up, the page shows the recovery code, and the person signs in as usual with their new method.
- **The browser extension, the desktop and phone apps, and the CLI** don't set it up: the extension says to set it up in the web vault, in a dialog that opens it; the apps' core turns the answer into its own error (`SetUpTwoStepFirst`), which the sign-in screen shows with the web vault's address, after a password or an email code; the CLI prints the server's sentence, which names the web vault.

### Sessions, API keys, and recovery
- **Sessions:** a session refreshes only while its person meets the rule. Someone who turns off their last method that counts, is given a covered role, or whose organization or MSP turns it on signs in again at the session's next refresh and sets it up there. Upstream's apps refresh before every sync, so in practice that's within moments, and at the latest when the access token expires. A single sign-on session counts for the organizations whose single sign-on still signs the account in.
- **Making a Business organization or an MSP** makes the person its owner, or its staff: without a method that counts, the web vault's New organization (for a business) and Set up your MSP say first that they'll be signed out once it's made, with a link to set it up in Settings first. If they go ahead, the web vault refreshes right after making it, which ends the session, and their next sign-in sets it up.
- **API keys (decided October 2026):** an API key sign-in (the CLI's `client_credentials`) skips two-step login, as upstream's does, so it's refused for someone the rule covers who has no method that counts, saying why; once they set one up, it works again. Not refused for everyone covered: the key is a separate secret that only a session with the master password can read (`/api/accounts/api-key`), scripts run as an admin need it, and the rule asks that the person have two-step login, which they then do. An organization's API key isn't a person, and isn't covered.
- **Recovery:** upstream's two-step recovery code still works: it turns two-step login off, as before, and a covered person's sign-in then goes straight to setting up a new method. Account recovery (an MSP or a client's admins resetting a member's master password) works as before, and the person, if covered, sets up two-step login at their next sign-in. MSP staff are never recovered ("MSP staff and account recovery").

## Browser import

Two ways in: guided import now, in the web vault and the extension, and automatic import later, through the desktop agent once it's signed. Both are optional.

**Guided import (built).** The person exports their passwords with the browser's own Export, and we take it from there.

- **Where:** the web vault (Tools, Import from your browser, with a pointer on the regular Import page, and the import step right after signing up) and the extension (Vault settings, Import from your browser, in its own window, since a file picker closes the popup). One component for both (`libs/importer/src/components/keykeeper/`).
- **Which browsers:** Chrome, Edge, Brave, and Firefox on Windows and Mac, and Safari (the Passwords app) on a Mac. It picks the person's browser and computer from the user agent, and they can pick another.
- **The steps:** that browser's export, step by step, with the confirm its computer asks for (Windows Hello, Touch ID, or the computer's password) and the file name it saves. The extension can open a Chromium browser's passwords page for them; a web page can't, so the steps say what to type.
- **The import:** upstream's importer for that browser's file, into the person's own vault. A login already there (same site, username, and password) or repeated in the file is left out, and one without a password is skipped. A login whose password differs from one they have for the same site and username is imported into a folder, "Check these: from <browser>", for them to compare. A file that isn't that browser's export is refused by name.
- **Afterwards:** a summary of what happened, a reminder to delete the export (it has every password in plain text), with how on that computer, and how to turn off the browser's own password saving. On managed computers the install script turns it off by policy.
- **Tests:** unit tests for detection, the steps, and the sorting (with upstream's Chrome importer on a real export); a web vault test (Chrome and Firefox exports, a file that isn't one, the folder to check) and an extension test.

**Automatic import (later).** Runs after first sign-in through the desktop agent, which ships after code signing.

- Sources: Chrome, Edge, Brave, Opera, and Vivaldi through the upstream GPL importer (`apps/desktop/desktop_native/chromium_importer`). Firefox is ours to write.
- Dedupe: identical URL, username, and password merge into one item. Same URL and username with different passwords: the most recently changed wins and the others go to the review queue.
- Skip "never save" entries and entries with empty passwords.
- Ends with a summary and a review queue that users clear whenever they like.

### Keeping up with upstream

- **The bases:** the server follows Vaultwarden's release tags (`passbundle-server/.keykeeper-base`) and the clients follow the web vault Vaultwarden supports (`passbundle-clients/.keykeeper-base`), not Bitwarden's newest: the server must understand the clients. The two move together.
- **Our own UI, upstream's security** (the owner's call, October 22, 2026): the web vault's and the extension's screens are ours to change as far as PassBundle needs, to look and work like its own product (familiar to Bitwarden and 1Password users, not a copy of either), and they don't have to stay mergeable with upstream. What has to stay close to upstream is the security core: the crypto, sign-in and keys, sync, the vault format, and the server. Upstream's fixes there get ported; a change of theirs to screens we've replaced can be dropped.
- **The weekly watch** (`.github/workflows/upstream-watch.yml`, `tools/upstream-watch/`) keeps one issue, "Upstream and dependency watch", open while something needs doing and closes it when nothing does. It raises a Vaultwarden release newer than our server base (flagging security fixes), Vaultwarden shipping a newer web vault than our clients base, and known vulnerabilities in what we ship: `cargo audit` of the server and the desktop agent, and `npm audit` of the clients' production dependencies.
- **Accepted advisories:** npm packages that never reach the web vault or the extension (the command-line client's, and build tooling) are listed with a reason in `tools/upstream-watch/accepted.json`; the watch notes them instead of raising them. The command-line client's need another look before we ship it.
- **Security fixes ahead of upstream:** when a fix is in a patch release of a dependency we ship and upstream hasn't taken it yet, we take it ourselves, as with Angular 21.2.25 in the clients (two cross-site scripting advisories) and rustls 0.23.46 for the server's outgoing connections (four advisories), and drop our change at the next base move. Advisories that don't apply to how we use a crate (Rocket's old rustls, which only serves TLS, or `rsa`, which has no fix yet) are accepted in the same file, by advisory and version, with a reason.

## UX we commit to

Fixes for things that annoy users of Bitwarden and 1Password today.

- **One unlock:** unlocking the desktop agent unlocks the browser extension, and the other way around, over the existing authenticated native-messaging channel. Locking either one locks both.
- **Biometrics by default:** Touch ID on Mac and Windows Hello on Windows are offered at first unlock, with no separate "browser integration" setup. Admins control biometrics and password requirements in the portal.
- **Survives profile migrations:** tools like ForensiT Profile Wizard change the Windows user's SID, so locally protected data (DPAPI, Windows Hello keys) stops decrypting. Upstream's extension then works once and needs a reinstall. Ours detects local state it can't decrypt, clears it, and asks the user to sign in again. Never a broken extension.
- **Custom fields are one tap away** in every item editor (web, extension, desktop, mobile), not buried in a menu.
- **Context-aware new items:** creating an item while viewing a folder or collection puts it there.
- **Onboarding day works:** upstream rate-limits logins per IP (a burst of 10, then one per minute) and signup, pre-login, and hint requests per IP (a shared burst of 50, then one per minute). A whole office behind one NAT address would get stuck after ten to twenty-five people. Built: the strict limit is per account now, and an address's limits fit an office (see "Login limits"). Later: allowances for an org's known addresses and enrolled devices.
- **No nags:** upstream's web vault interrupts every fresh login with an extension page, an "Are you sure?" dialog, and a welcome tour. All three go. Extension setup happens through onboarding instead.
- **New item picker (built, web vault):** New opens "What are you saving?": Login, Secure note, Card, and Identity as big tiles, and "More categories" for the other item types and every template (built-in, your own, your organizations', your MSP's), with a search and links to make a template. Folder and Collection are buttons at the bottom. Like 1Password's, so what people save most is one click and the rest is one more (`libs/vault/src/keykeeper/new-item-dialog.component.ts`). The admin console keeps upstream's menu for now.
- **Only categories with items** show in the left menu (Favorites too, once something is one); the one being viewed stays while it's open.

## Item templates

Like 1Password's item types (API key, server, Wi-Fi, software license, passport, and so on), plus custom templates that people, families, and MSPs define.

- **Built-in templates** beyond upstream's types (login, card, identity, secure note, SSH key, bank account, passport, driver's license): API key, server, database, Wi-Fi network, router, software license, domain, certificate, email account, membership, and later crypto wallet. Each is an upstream base type (login or secure note) with predefined, typed fields.
- **Typed fields:** text, hidden, date, URL, email, phone, number, yes/no, one-time code. Upstream only knows text, hidden, yes/no, and linked, so values are stored as ordinary custom fields and the template supplies each field's type, which drives the editor (date picker, URL check) and display.
- **Storage, with no server changes:** an item records its template in a text field `keykeeper.template` (template id, name, and version), so its template shows even to people who can't see the template itself. A custom template is itself an item: a secure note with a text field `keykeeper.template-definition` (an id, whether new items are logins or notes, and a version). The note's name is the template's name, and its custom fields are the template's fields, with any values as defaults. So people create, edit, share, and delete templates with the ordinary item editor, and everything stays end-to-end encrypted and syncs like any item. Other clients show a template as a plain note.
- **Where custom templates live:** personal templates in the personal vault. Family and business templates in an organization collection, which reaches everyone who can see that collection. An MSP pushes a template to many client orgs at once from the MSP console, which writes the same template item, same id, into each client's templates collection.
- **Creating items:** "New item from a template" lists each organization's templates, then the person's own, then built-in. An item from an organization's template still goes where the person is adding it (the open folder, organization, or collection), never into that organization by default, so a personal item can't land in a shared collection by surprise.
- **Built:** ten built-in templates (API key, server, database, Wi-Fi network, router, software license, domain, certificate, email account, membership); upstream already has passport, driver's license, and bank account types. Custom templates for logins or notes, made from "Create template" in the same picker or with "Save as template" from a login or note (the web vault's item menu and the extension's; it opens a new template with the item's name and its custom fields' labels and kinds, never their values, unsaved), with defaults, a hint in the editor, a description in the item view, and a "Template" badge in lists. "From template" in the web vault's New menu and the browser extension's (`libs/common/src/vault/keykeeper/templates.ts`, `template-chooser.component.ts`). New items keep hidden fields editable (upstream locked them when there was no original item). Tier 1 covers built-in and custom templates in the web vault and the extension.
- **MSP push to many orgs:** built; see "MSP templates".
- **Not built yet:** giving every org member access to the templates collection automatically; typed fields beyond text, hidden, and yes/no (date, URL, email, phone, number, one-time code) and a date field that sets the expiration; a Templates view, so someone's own templates can leave "All items" too (an MSP's copies already stay in their collection); "From template" in a desktop vault window, if we build one; and an organization template test (needs org creation in the test rig).

## Expiration dates

Any item can expire: API keys, certificates, licenses, domains, passports, cards.

- **Set it anywhere:** an "Expires" date on every item, plus template date fields marked "is the expiration date" (an API key's expiry, a passport's). Cards use their existing expiry month and year automatically.
- **Stored with the item:** a text field `keykeeper.expires` (ISO date), encrypted and synced, no server changes. A text field, not hidden: a date isn't secret, and list views only carry text fields' values, so lists can show badges without decrypting every item.
- **Built:** the "Expires" date in the item editor (web, extension, desktop share it), an Expiration section in the item view, badges in the web vault list and the extension's item list for items expired or expiring within 30 days, and card expiry in the item view. All of PassBundle's own fields stay hidden in views and editors and survive edits (`libs/vault/src/keykeeper/`). An "Expiring items" report on the web vault's Reports page lists everything expired or expiring within 30 days, cards included, expired first, then soonest. The extension checks every six hours while unlocked and shows a system notification at 30, 7, and 1 day before and once expired, never twice for the same step; a new date starts over (`apps/browser/src/keykeeper/expiration-reminders.ts`). What it already showed is kept per account and cleared at logout. Tier 1 covers each.
- **Not built yet:** card expiry badges in lists (list views don't carry card expiry), the "Expiring soon" filter, Health integration, per-item reminder days, and desktop agent reminders.
- **See it:** "Expires in 12 days" and "Expired" badges in every list, an "Expiring soon" filter, and expiring items in Health.
- **Reminders, on the device:** the extension (built) and desktop agent check while unlocked and notify at 30, 7, and 1 day before, and once expired. Steps adjustable per item later. Nothing leaves the device.
- **Reminders by email (open):** the server can't read items, so emailed reminders would mean storing an unencrypted reminder date with an opaque item id ("an item in your vault expires on Oct 30", no name). Opt-in per user or org, or skip it.
- **MSP view (built):** the console lists everything expired or expiring within 30 days across all clients, soonest first, with the client and a link that opens the item in the client's vault. It's computed in the MSP staff's browser from items they can decrypt, alongside the per-client counts, so the server never sees it.

## Item history

Every item keeps its past versions, as in 1Password: each edit keeps what the item was before, and anyone who can open the item can see its earlier versions and restore one. Upstream only keeps a login's last five passwords.

- **Kept by the server, readable only by apps:** when an edit replaces an existing item's contents (upstream's item update from the vault or the admin console, and the share endpoints, one item or several), the server first copies the item as it is stored: its encrypted fields exactly as they are (type, name, notes, custom fields, the type's data, password history, re-prompt, and its item key), when that version was saved and who saved it, and when and by whom it was replaced. Who saved an item is recorded from the moment it's made, so the first version has an author too. The version, the edit, and who saved it are written in one transaction. The server can't read any of it and never gets a key.
- **Not kept:** new items, imports, the same contents encrypted with a rotated key, and changes outside the encrypted fields (folder, favorite, collections, archive, trash). The web vault saves a favorite on its own (upstream saves the whole item again).
- **Every save, not every change:** apps encrypt the whole item again on each save, with fresh IVs, so the server can't tell a new password from a save that changed nothing. It keeps a version for every edit unless the encrypted fields are byte for byte what's stored. The web vault decrypts the versions and lists one of each run that looks the same: the oldest, so "Saved by" names who wrote those contents.
- **What an item keeps:** its newest 20 versions, every one; before those, one a day (UTC), the item as it was before that day's first edit; at most 100 versions and 4 MB in all. A burst of saves, accidental or scripted, can push out only the newest 20, never the days before. Merging a person's quick edits into one version instead would drop a real intermediate state (a password changed twice in a minute), and a plain count would let 50 saves flush everything older.
- **Size limits:** an item is at most 512 KB encrypted, not counting attachments, which are stored apart (a login is a few KB, and a note at most 10,000 characters); bigger saves are refused. Password history keeps the newest 100 entries (upstream's apps keep 5). So an item's history response is at most 100 versions and about 4 MB.
- **Who sees it:** who can open the item and has view item history in one of its shared folders (see "Folders and permissions"; every preset has it). The versions' contents need see passwords in that same folder. `GET /api/keykeeper/ciphers/<id>/history` makes the same check as reading the item, plus that one: its owner, members with one of its collections (directly or through a group), and owners, admins, and members with access to all items. Anyone else gets 404, the same as for a missing item, including members who are invited, accepted but not confirmed, or revoked, and members taken out of the item's collection. Someone given access later sees the history from before, as they see the item. The web vault says so above the list: everyone who can open the item can see its earlier versions, including old passwords.
- **Members who can view an item but not its passwords** get when and by whom only: no version's encrypted fields. The web vault lists the versions without View or Restore.
- **Who saved each version** shows by name and email to that person, and to those who can list the organization's members, by the same rule as `GET /organizations/<id>/users`: managers and above with access to all items (owners and admins have it), and custom roles that manage members or account recovery. Others see "Saved by another member". A deleted account's versions stay, unnamed.
- **Clearing it:** people with view item history and delete in the same one of its shared folders (or access to all items) can clear its history, or delete one version from its view (`DELETE /api/keykeeper/ciphers/<id>/history`, `.../history/<version>`). Both go in the organization's event log for its items (types 1190 and 1191, shown as "Cleared the earlier versions of item …" and "Deleted an earlier version of item …") and in the server's log. The item and who saved it stay.
- **Restoring:** the web vault decrypts the chosen version and saves it as a normal edit of the item. The server's rules for edits apply (a stale copy is refused, read-only members can't), the version it replaces goes into history like any edit, and upstream's password history keeps the replaced password. Attachments, folder, favorite, and collections aren't part of versions and stay as they are. Members who can edit an item but not see its passwords can't restore, which would put back secrets they can't see. There's no server-side restore: writing old ciphertext back blindly could pair the item with an item key or attachment keys it no longer has.
- **Item keys:** a version keeps the item key it was encrypted with, wrapped as it was by the account's or the organization's key, so it still opens after the item gets a new item key.
- **When history goes:** with the item when it's deleted for good (from the trash, emptying the trash, purging a vault, deleting an organization or an account): deleting an item deletes its history, and the database's cascade does too (SQLite connections turn foreign keys on). Moving a personal item into an organization deletes its history: those versions are encrypted with the person's own key, which nobody else there can open, and the organization shouldn't get them. Changing an account's key deletes its personal items' history once the new key is saved, since nothing could open it anymore, as with synced settings. Organization items keep theirs: they're under the organization's key.
- **Built (October 23, 2026):** the server (`keykeeper_cipher_versions`, `keykeeper_cipher_saves`, `/api/keykeeper/ciphers/<id>/history`) and the web vault: "Version history" in the item view, newest first, with who saved each; View shows a version next to the item now, changed fields marked and hidden values masked, to restore or delete it; Clear history (`libs/vault/src/keykeeper/item-versions*.ts`). **Our desktop and phone apps (October 23, 2026)** list the versions, show one beside the item now, restore it the same way, as an edit, and delete one or clear them where the server allows (docs/core.md, "Version history"). Restoring there keeps each passkey the item still has, with its raised counter, and says first which passkey a version without it would take away. **Not yet:** the extension.
- **Tests:** server unit tests (what a version keeps, what each kind of save does, sizes, what an item keeps); API tests on SQLite and PostgreSQL (versions for edits through every endpoint and none for the rest, authors, bursts, item keys, size limits, who can read and clear with a permission matrix, hidden passwords, membership states, collections and groups, custom roles and MSP technicians, names, moving into an organization, deletion checked in the database, key rotation); jest specs for comparing versions, the list, restoring, clearing, and favorites; a browser test that changes a login's password twice, compares the first version with the item, restores it, finds three versions, and clears them.

## Generator settings

The setting people reach for is the generator's: how long, which kinds of characters, words or characters. Upstream keeps it on each device, forgets it at logout, and its apps disagree on the default. Ours is set once and is the setting everywhere.

- **One default, everywhere:** 20 characters with upper and lower case, digits, and symbols, leaving out look-alikes (0 O, 1 l I); passphrases of 6 words. The web vault and the extension used upstream's 14 with no symbols; they now use the apps'.
- **Follows the account:** the generator's settings are saved to the server in a small document encrypted with the account's user key, and every app reads and writes the same one: the web vault and the extension (`libs/tools/generator/core/src/keykeeper/`), and the apps' core (`core/src/synced_settings.rs`). A change in any of them is the setting in the others at their next sync; saving tells the account's other devices to sync, which reads the settings again without downloading the vault. Signing out no longer resets them.
- **What's stored:** `{"type": "passbundle.settings", "rev": …, "generator": {…}}`, the generator's part named as the apps' core names its options (`kind`, `length`, `uppercase`, `lowercase`, `digits`, `symbols`, `avoidAmbiguous`, `minDigits`, `minSymbols`, `words`, `separator`, `capitalize`, `includeNumber`). Each app takes what it understands, held to its own generator's limits, and keeps the rest of the document, including generator settings other apps add, when it saves. Room for other settings later.
- **The server can't read it** (`GET`/`PUT /api/keykeeper/settings`): it checks only that it's a type 2 string, at most 16 KB, per account, never another's. Changing the account's key forgets it, since no app could read it anymore; the next app to save writes it anew. An organization's password generator policy still applies on top, as before.
- **Conflicts:** last save wins. A change on this device that isn't saved yet (offline, or made just before closing) wins over the server's copy at the next sync; each app keeps what the server had, as far as it knows, across sign-outs to tell the two apart. A document that isn't PassBundle's settings (something else encrypted with the account's key) is replaced with this device's.
- **A server handing back an old copy** (security review, October 2026): each save numbers the document (`rev`: after every number the app has seen, and the time in milliseconds), and an app refuses a copy numbered lower than one it has seen, saving its own again. A server could otherwise bring back settings someone chose before, say a short one for a picky site, without their noticing. What it can't do is make settings up: they're encrypted and authenticated with the account's key.
- **Tests:** unit tests for the mapping, limits, numbering, and each sync case (the server has none, has some, has an older copy, has something else; a change here first, during a sync, before closing; after signing out and in; other apps' settings kept); the core's against a real server, from one device to another and back; API tests (per account, only encrypted, no vault download, forgotten when the key changes); and an end-to-end test that a length chosen in the web vault is the extension's.

## Staying unlocked across a reload

Upstream's web vault locks on every reload, whatever the vault timeout: it keeps the user key only in the page's memory. The owner found that wearing ("I press refresh and type my master password again"), and chose (2026-10-26) to keep a tab unlocked across a reload, within its timeout, with a key the server holds. A security review on 2026-10-27 tightened it (reopened tabs, Back, its own setting, policies, limits), and a second review tightened it again (the leaving beacon, "On browser refresh" under policies, other tabs).

**What upstream does** (checked against our build, 2026-10-26, before building this):

- The user key is `USER_KEY` in `CRYPTO_MEMORY` (`libs/common/src/key-management/state-definitions.ts`): on the web, the page's memory, plus the SDK's copy in WebAssembly memory. A reload, closing the tab, locking, and signing out all clear it.
- The only key upstream ever keeps is the "auto" key for a timeout of Never, in `SECURE_STORAGE`, which production web builds keep in memory too, and which offer Never only in development builds.
- The tab's sessionStorage (the web's "disk": per tab, kept across a reload, not shared with a new tab, gone when the tab closes, though the browser brings it back with a reopened tab or a restored session) holds the access and refresh tokens (with the Lock action) and the user key encrypted with the master key, so a reload shows the unlock screen. With Log out, the tokens are in memory too, so a reload signs out.
- So the Business preset's Vault lock wasn't the cause: someone with no policy locked on every reload too. Our own end-to-end tests had relied on it since 2026-10-14.

**What ours does:**

- **At a real unlock** (signing in, the master password, any way but this one): the tab makes a random key R (`PureCrypto.make_aes256_cbc_hmac_key`, as upstream makes keys), wraps the user key with it using upstream's key wrap (`EncryptService.wrapSymmetricKey`, an EncString of type 2), and keeps only that wrapped key and a random tab id (16 bytes) in its own sessionStorage. It sends R and the tab id to the server over the signed-in session (`POST /api/keykeeper/reload-key`). The server answers with the tab's reload cookie (below).
- **Only a reload restores.** At startup, before anything reads the key, a page whose navigation type is "reload" (`performance.getEntriesByType("navigation")`) asks for R with its tab id (`POST /api/keykeeper/reload-key/release`, the browser adding the tab's cookie), unwraps the user key, and puts it in memory the way upstream does for its Never timeout (`KeyService.setUserKey`). A closed tab reopened, Back to the page, a new load in the same tab, a duplicate of it, or anything else stays locked, forgets its record, and asks the server to forget R at once; where the navigation's entry is missing, nothing restores. A page that comes back from the back-forward cache, with the key still in its memory, locks as it shows (in our tests Chrome loads the vault again instead of keeping it in that cache). A key unlocked from a reload key never makes a new R: only the next real unlock does. The page then syncs, as it does after any unlock.
- **As a page goes** (`pagehide`: closed, navigated away, or reloading), it sends a beacon (`POST /api/keykeeper/reload-key/leaving`) with only its tab id and its page id, a random 16 bytes new at each load; its cookie is the proof, so the beacon needs no access token, and it can only shorten an entry. From then on the server keeps the entry 15 seconds, for the reload that follows to ask; asking ends the leaving, and records the asking page's id. The server takes a leaving only from the page that kept the entry or asked for it last, so a beacon from the page before a reload, arriving late, can't end the reloaded page's entry; and a second leaving keeps the first one's time, so repeating it can't push the end back. What's guaranteed: once a closed tab's beacon reaches the server, nothing can restore that tab 15 seconds later. A beacon that never arrives (the browser crashed or dropped it) leaves the entry until 2 minutes after the tab's last check-in.
- **The person's own setting:** "Stay unlocked when I reload", on Settings, Security, Session timeout, under the timeout, on unless they turn it off, kept per account in this browser (`KEYKEEPER_STAY_UNLOCKED_ON_RELOAD`, localStorage). Its hint names shared computers: off, every reload asks. Turning it off forgets R at once, in every open tab of the account: the others hear of it from the browser's `storage` event, and forget theirs too. It's off, with a note saying why, while the person's own stored timeout is "On browser refresh", and a policy that writes its minutes over "On browser refresh" turns it off, with a note, until they turn it back on.
- **Only with a timeout in minutes and the Lock action.** "On browser refresh" and Log out keep upstream's behavior, and so do Vault lock policies of "immediately", upstream's "on app restart", signing out at the timeout, or `webReload: false`: no R is made, and a reload asks. Changing to one of these forgets R at once, in this tab and the account's other open tabs. Nothing rewrites the person's timeout to make room for a reload key, and "On browser refresh" keeps meaning a lock at every reload: where a policy shows it as minutes, or writes minutes over it, "Stay unlocked when I reload" goes off (below).
- **While open**, the tab checks in every 30 seconds (`POST /api/keykeeper/reload-key/check-in`) with how long since the person last used it (upstream's own activity record) and their timeout now. Browsers run a hidden tab's timers about once a minute, inside the server's 2 minutes.
- **Forgetting:** locking (upstream's lock waits for it before it reloads the page) and signing out (the web vault forgets before it clears the session, from the account menu's Log out or any other) ask the server to forget R (`POST /api/keykeeper/reload-key/forget`), with the access token refreshed first if it ran out, as a `keepalive` request that outlives the page. A forget that doesn't get through is tried once more a check-in later if the page is still open, and the page's leaving says so too.
- **The server keeps R in its process memory only**: never in the database, a file, or a log. Each entry belongs to one account, one device (the session its access token is for), and one tab id, and only a request with all three, and the tab's cookie, gets R back. Anything else gets the same "Not found". The entry ends:
  - when the tab hasn't been used for its timeout, as the tab reports it, capped by the strictest Vault lock policy of every organization the account has joined: a longest wait's minutes, or "when the computer locks"'s `webMinutes` (15 when it's missing). For reload keys only, this binds owners and MSP staff too, where the policy's other effects exempt owners as upstream does: refusing a reload key only costs a master password prompt, so nobody can be locked out, and our apps' lock policy already binds admins and MSP staff;
  - 2 minutes after the tab stops checking in: the browser closed or crashed, or the computer slept;
  - 15 seconds after the tab's page left, unless a reload asked;
  - when the tab forgets it (above);
  - when a policy now refuses reload keys, at the next check-in or reload;
  - when the account's security stamp changes (a new master password, key rotation, "Deauthorize sessions", an admin's deauthorization, a KDF or email change), or its devices are removed (deleting the account does);
  - when the server restarts, so the next reload asks.
- **The reload cookie.** When the server keeps R, it sets a cookie for the tab: a random 256-bit value, named `__Secure-pb-reload-<tab id>`, HttpOnly, Secure, SameSite=Strict, with no Expires or Max-Age (a session cookie), and a path of `/api/keykeeper/reload-key` under the server's own path, so it goes only to the reload endpoints. The server keeps only its SHA-256 with the entry. Getting R back, checking in, and leaving need the cookie; a missing or wrong one gets the same "Not found" as no entry, and changes nothing. Forgetting R expires the cookie with it; an entry that ended on its own expires its cookie the next time the tab asks, and keeping a new R expires the cookies of tabs nothing is kept for any more, so they don't pile up.
  - Why `__Secure-` and not `__Host-`: `__Host-` would also pin the cookie to the host, but only with a path of `/`, which would send it with every request. `__Secure-` makes the browser take it only with Secure from an https page, and the narrow path keeps it off everything else. Each tab has its own name, so tabs signed in apart in one browser don't replace each other's cookie.
  - Why a cookie: page scripts can't read an HttpOnly cookie, and Chrome and Edge keep cookies encrypted at rest with the operating system's own key (DPAPI, with app-bound encryption in Chrome, on Windows; the Keychain on macOS; the desktop keyring on Linux, where there is one). sessionStorage gets none of that: Chrome writes it to the profile as it is. So the two halves a reload needs live in different places with different protection.
  - Same origin: the web vault always calls the API at its own origin (`WebEnvironmentService` sets the base to `window.location.origin`, and the server serves both), so the cookie is first-party and goes with the reload calls, the keepalive forget, and the leaving beacon, without anything special. A web vault built to call an API on another site wouldn't get the cookie back (SameSite=Strict), and its reloads would ask for the master password, as upstream's do.
- **Under "when the computer locks"** the web vault makes the timeout a number of minutes, at most `webMinutes`, where the timeout is read, and doesn't write it into the person's stored choice, so leaving the organization leaves their choice as it was. Settings offers the waits up to it and Custom. "On browser refresh" isn't offered: it never locks while the page stays open, so it would turn the idle lock off. A stored "On browser refresh" counts as `webMinutes`, with "Stay unlocked when I reload" off, so it still locks at every reload. Under a longest wait, upstream writes the policy's minutes over a stored "On browser refresh", and the web vault then turns the setting off for that account, with a note saying why (`docs/core.md`, "Locking by policy").
- **Limits:** 20 tabs per account (a new one replaces the stalest), and a tab id already in use by another account or device is refused. Each tab's calls are limited to 20 at once, then one every 3 seconds, and each account's, all its tabs together, to 60 at once, then two a second, so a technician with many tabs open checking in twice a minute never meets them. The leaving beacon has a limit of its own per address, 300 at once, then five a second, which counts only beacons that match no entry, so an office closing many tabs at once never meets it and never uses up the server's limit for requests without a session (signing in, among others). Entries are kept by tab id, so a beacon finds its entry without looking through the others. Expired entries are wiped every 30 seconds; every call checks its own entry's expiry first.
- **What's wiped:** R is held in a heap buffer of its own, decoded straight into one from the request and wiped when its entry ends or is replaced, so the map moves only a pointer when it grows. The request body that carried R is wiped once read. Not wiped by us: the base64 text of R in the response that hands it back, the TLS library's buffers, and the bytes a reallocation inside serde may have copied; they're freed, and stay in freed memory until reused.
- **Core dumps:** the server turns them off at startup (`RLIMIT_CORE` 0) and, on Linux, marks itself not dumpable (`PR_SET_DUMPABLE` 0), which also keeps other processes of the same user from reading its memory through ptrace or /proc. `ALLOW_CORE_DUMPS=true` keeps them, to debug a crash; it's read once the `ENV_FILE` is loaded, so it can be set there or in the process environment. Swap is the other way memory reaches a disk: hosts should run without swap, or with it encrypted.
- **Files:** server `src/api/core/keykeeper_reload_keys.rs` (with the hooks in `User::reset_security_stamp` and `Device::delete_all_by_user`, and `no_core_dumps` in `main.rs`); web vault `apps/web/src/app/keykeeper/reload-key/`, started from `InitService`, with the setting's component on the session timeout page and the forget in `AppComponent.logOut`; the setting's state, which upstream's timeout code turns off when it replaces "On browser refresh", in `libs/common/src/key-management/session-timeout/keykeeper-reload-setting.ts`; the reload key's state is `KEYKEEPER_RELOAD_KEY_DISK`, which must stay the tab's sessionStorage.

**Threat model.** What each kind of attacker can do with a reload key, against what upstream's web vault gives them. Today, without reload keys, the tab's storage holds the access and refresh tokens and the user key encrypted with the master key: whoever copies it can call the API as the person and download the encrypted vault, but needs the master password to open it.

- **A copy of the tab's sessionStorage alone** (Chrome writes it to the profile on disk for session restore, so a backup, a sync tool, or malware that reads files but not memory can take it): the tokens, the tab id, and the wrapped user key, but not the cookie. Asking for R without the cookie gets "Not found", so the copy opens nothing more than it does today. (Our own web vault, finding no cookie on a reload, also asks the server to forget R, which ends the original tab's reload key; another client needn't.)
- **The cookie alone:** useless. It's a random value that opens nothing without the tab's tokens, its id, and the wrapped user key, which stay in sessionStorage. With it alone, someone can only say the tab is leaving, which shortens the entry.
- **Both, while the entry lasts:** the user key. That needs the sessionStorage copy and the cookie decrypted, which on Windows and macOS means the operating system's key for the browser: malware running as the person that can also get the browser's cookie key (Chrome's app-bound encryption on Windows makes that harder still for software that isn't Chrome), or someone with the person's unlocked session. Such an attacker could usually read the browser's memory, and so the key of an unlocked vault, anyway. Once the entry ends (the timeout, 15 seconds after the tab's leaving reaches the server, or 2 minutes after its last check-in), both together open nothing.
- **Session cookies on disk:** Chrome keeps session cookies in memory, and writes them to the profile only with "Continue where you left off" on; a copy of a profile without that setting doesn't hold the cookie at all.
- **Firefox and Safari** keep cookies on disk without that encryption (Firefox in plain SQLite), so there the cookie only adds what HttpOnly gives: page scripts can't read it, and it's in a different file. A copy of the whole profile is then enough while the entry lasts.
- **A browser extension with the cookies permission** can read HttpOnly cookies, and one that can also read the page has the tab's storage: both halves. An extension that can read the page could already read an unlocked vault. Choosing extensions is the person's, or their IT's (DESIGN.md, "Browser extension management").
- **A breached server alone** has R and the cookie's hash, but not the wrapped key, which stays in the tab: nothing. It gains nothing new anyway: the web vault already trusts the server for its code, so a breached server could serve a web vault that sends it the key at the next unlock.
- **A breached server and a copy of the tab's sessionStorage** together have R and the wrapped key: the user key, cookie or not, for as long as the server kept that R. The same breached server could already have taken the key through its code.
- **A crash dump of the server** would hold every live R; dumps are off (above), and an R alone opens nothing without its tab's storage.
- **Script injected into the web vault's page** (cross-site scripting, or an extension that can read the page) can't read the cookie, but it can read the user key from the unlocked page's memory, and make same-origin requests that carry the cookie. Unchanged from today.
- **Same-site siblings and the origins CORS allows:** SameSite=Strict is about the site, so a page on a sibling host of the same site (another subdomain) can make the browser send the cookie with a request to the reload endpoints; it can't read the answer (the server's CORS allows only its own origin, the Safari extension's and the desktop app's origins, and an SSO provider's), and asking for R also needs the tab's access token, which it doesn't have. `__Secure-` doesn't stop a sibling from setting a cookie of the same name for the whole site; it can't know the right value, so the worst it does is make a reload ask. Hosts should keep sibling subdomains of the vault's site trusted, or give the vault a site of its own.
- **The device id isn't a secret:** it's in the browser's localStorage and goes with sign-ins. Binding an entry to the device means binding it to that device's session: the access token's device claim, which the server signs.
- **The time limit** is the server's own clock counting from the tab's report of how long it's been unused, under the policy's cap. The server trusts that report: whoever can send it has the tab's storage and its cookie. A tab whose clock moves forward reports more and ends sooner. A tab that sends nothing is ended by the server's own clock alone.
- **A closed tab reopened, or Back to the page:** the server ends the entry 15 seconds after the page left, so after that nothing can restore it. Within those 15 seconds, the page restores only if the browser calls its load a reload. In our tests (Chrome), Back reports "back_forward" and a tab opened again "navigate", and both stay locked. Playwright can't drive "Reopen closed tab", and MDN notes that browsers may report a reopened or duplicated tab as "back_forward" or copy the original tab's type; so a tab reopened within 15 seconds of closing, in a browser that copies "reload", would come back unlocked. That's the gap left: 15 seconds, for the same browser. Firefox wasn't automated here.
- **A browser restart** that restores its tabs: the entry ended 15 seconds after its page left as the browser closed, or at most 2 minutes after its last check-in if the browser crashed or didn't let the page say so. A restart quicker than that, after a crash, could restore it if the browser called the restored load a reload.
- **Shared computers:** a vault left open in a tab is open to the next person, as upstream's is, until the timeout. What a reload key adds is only a reload of that same open tab within the timeout; a closed tab, a reopened one, Back, or a restarted browser all ask. Where people share computers, turn "Stay unlocked when I reload" off, or the organization's policy turns it off for everyone (`webReload: false`), and a short timeout matters more than ever.
- **Duplicated tabs:** duplicating a tab copies its sessionStorage, and cookies belong to the browser, so both have the same tab id and cookie. A duplicate that isn't reported as a reload asks, and ends the original's entry at once, so the original asks at its next reload too. One reported as a reload shares the original's entry, and locking either ends it for both; the beacons of whichever page didn't ask last are ignored, so closing one leaves the other's reload working. A window the web vault opens itself asks ("navigate"), and ends the entry the same way.

**The wrap's test vectors** are `docs/vectors/reload-key-v1.json`, made by `make-reload-key-v1.mjs` with Node's own crypto: R, a user key, and the EncString, with refusals (another R, a changed MAC, a changed ciphertext). Tier 1 opens them with upstream's own crypto (`check-reload-key-vectors.mjs`), and the web vault's unit test opens them through upstream's `EncryptService` from a copy (`apps/web/src/app/keykeeper/reload-key/reload-key-v1.json`; Tier 1 checks the copy matches).

**Tests:**

- The server's unit tests: who gets R back, the 2 minutes, leaving and the reload that follows, a repeated leaving that can't push the end back, a late leaving from the page before a reload that can't end the reloaded one's, another account that can't take a tab id in use, the timeout, the tab's report, forgetting, the timer's sweep, the tab limit, the policy cap and what refuses (signing out, `webReload: false`), the strictest of several policies, reading the body and decoding R, the cookie (only the tab's own opens it), and the cookie's attributes.
- API tests (`e2e/tests/api/reload-key.spec.ts`): the same over HTTP; the cookie's attributes as sent; R refused without the cookie or with a wrong one; forgetting and ending expiring it; refusals that never echo R; a new master password, key rotation, "Deauthorize sessions", and deleting the account forgetting it; the policy cap for members and owners; "immediately", signing out, and `webReload: false` refusing it; the strictest policy of two organizations; the server's own clock ending an entry with nothing from the tab; a page leaving, and a leaving from another page ignored; the limits per tab and for many tabs; and a flood of leaving beacons that leaves signing in from the same address alone.
- The web vault's unit tests: the wrap against the vectors, when it applies (the setting, the policies, a stored "On browser refresh"), restoring only a reload and forgetting on the server otherwise, the leaving beacon and its page id, locking a page back from the cache, the setting and its notes, another tab turning it off or choosing "On browser refresh", forgetting with a fresh token and once more, and each step (`reload-key.spec.ts`, `reload-setting.component.spec.ts`); the mapping under "when the computer locks", which offers only minutes, counts "On browser refresh" as the cap, and keeps the stored choice, and a longest wait replacing "On browser refresh" turning the setting off (`keykeeper-system-lock.spec.ts`, the settings services' specs).
- End-to-end tests (`e2e/tests/reload-key.spec.ts`): a reload stays unlocked with no prompt and the tab's storage never holds R; the cookie is HttpOnly, Secure, Strict, and for the session, page scripts can't see it, and without it a reload asks; another browser with a copy of the tab's storage but not its cookie gets nothing, even reloading; a closed tab reopened is locked and the server let R go; Back asks, with the back-forward cache off and on; locking asks and expires the cookie; the account menu's Log out forgets R first; "Stay unlocked when I reload" off makes every reload ask; a new browser asks; "On browser refresh" keeps asking, and under the Business preset, where Settings no longer offers it, a stored one still asks, with the setting off and a note; Log out signs out at a reload; a member under the Business preset signs in, reloads, and stays unlocked, with Settings explaining the cap; with the web vault's wait at 1 minute and the clock moved, it locks; a policy with `webReload: false` turns it off, Settings saying why; and a server that restarts asks at the next reload.

## Health (better than Watchtower)

Reports are only useful if they lead to a fix.

- **Org password rules:** admins set minimum length, character sets, or passphrases. Every generator enforces them, on every device.
- **Site-aware generation:** generated passwords also follow each site's own rules, using `apple/password-manager-resources` data, so they are never rejected.
  - **Built:** the extension's suggested password in the menu inside a new-password field; "Generate password" from the right-click menu and the keyboard shortcut, for the page in front; and the item editor's generator in the web vault and the extension, for the item's first website, where the generator shows the password that follows the rules, so what someone copies from it is what's saved. A password the generator made that the site's rules accept is kept; otherwise one is made to the rules, from a secure random source, never with a space, keeping the generated one's length and kinds of characters (uppercase, lowercase, digits, symbols) wherever the rules allow. So the generator's settings and an organization's password generator policy still count, and where they conflict with the site's rules, the site's win, since a password the site rejects is no use. The rules are Apple's password rules language, read by our own parser (`libs/common/src/tools/keykeeper/password-rules.ts`), from Apple's MIT-licensed list of 436 sites, vendored at a pinned commit by `scripts/keykeeper/update-site-data.mjs` with Apple's license next to it. A site's entry covers its subdomains.
  - **Tests:** unit tests for the language (Apple's custom set quirks included), every listed site read and a password made for it at three lengths that follows its rules, and the wiring; an extension test where the suggested password on a sign-up page is the usual 20 characters on a site without rules and follows airfrance.com's (8 to 12, a fixed set of symbols), served locally under that name; and a web vault test where the item editor's generator, for an item at www.airfrance.com, shows and uses a password that follows them.
  - **Keeping current:** the weekly upstream watch (`tools/upstream-watch`) flags when Apple's data has changed since the commit the clients take it from, with the command that takes the newer one. The Generator page on its own has no site, so it's unchanged.
- **One-click fix:** open the site's change-password page (`/.well-known/change-password` where available), generate a compliant password, and save it with history.
  - **Built:** "Change password" (on an at-risk item's view, and the extension's at-risk prompts) opens the site's own change-password page. The apps first check Apple's MIT-licensed list of 652 sites' change-password pages on the device (`libs/common/src/tools/keykeeper/change-password-urls.ts`, vendored with the password rules by `scripts/keykeeper/update-site-data.mjs`). Otherwise they ask the server, as upstream's apps do (`/icons/change-password-uri`), and ours answers with the site's standard address (`/.well-known/change-password`) when the site supports it by the W3C check: that address answers with success and a path no site has doesn't. The server asks sites only the way it downloads icons (not when icon downloads are off or go to an outside service, never a blocked address, through the same client, and at most twice per site a day), and only for people who show website icons, as upstream's apps already decide. With neither, the site itself opens.
  - **Tests:** unit tests for the list lookup and the apps' order (no request when the list has the site), the server's check and which websites it may reach; an API test that the lookup answers and never reaches a site with icon downloads off.
- **Privacy-preserving admin view:** org-owned items are checked by an admin's client. For private items, each member's client reports only counts (weak, reused, breached), never which items.

### Exposed passwords

Have I Been Pwned's Pwned Passwords says whether a password is in a known breach without being given the password (k-anonymity). Every check in the web vault and the extension goes through one client (`libs/common/src/dirt/keykeeper/pwned-passwords.ts`), which upstream's AuditService now uses, so the reports, the MSP console, the count beside Health, the item editor's Check button, and the master password check at sign-up all behave the same.

- **What leaves the browser:** for each password, only the first 5 hex characters of its SHA-1 hash (20 of its 160 bits), as `GET https://api.pwnedpasswords.com/range/<prefix>` with `Add-Padding: true`, without cookies or other credentials, without a referrer, kept out of the browser's cache, and refusing redirects. The service answers with every suffix it knows under that prefix (hundreds, plus decoys seen 0 times, so the answer's size says nothing), and the browser makes the match itself. Never the password, its full hash, or which item it's in. So an automatic check (the count beside Health, the MSP console) sends the service the set of 5-character prefixes of the vault's different passwords, in random order rather than the vault's. Like any website, the service (behind Cloudflare) sees the browser's IP address, when it asked, and the `Origin` header, which is the web vault's address. The web vault's content security policy (the server's header) already allows that one address.
- **Only the service's answer counts:** a 200 with at least 100 lines, each a 35-character uppercase suffix and a count of up to 10 digits, and at most 1 MB. Anything else (an empty or short 200, a 204, another status, a captive portal's page, a filtering proxy or inspecting firewall's answer) is a failed check, never "not exposed", and is never remembered.
- **Who decides:** Settings, Appearance has "Check my passwords against known breaches after unlocking", per account, on by default, kept in the web vault's local storage on each browser (it doesn't follow the account to other devices yet); other open tabs of the web vault follow a change at once. Off, the web vault sends nothing to the breach service on its own: the count beside Health counts weak and reused only, and the MSP console's Exposed column says "Not checked" beside a Check exposed passwords button. Passwords are checked only when the person opens the exposed passwords report, presses that button, or presses Check in the item editor. For MSP staff, the automatic count covers every client item they can edit, since a person's Health does. Separately, creating or changing a master password checks it the same way while the form's "Check known data breaches for this password" is ticked, as it is at first.
- **How often:** 4 requests at a time at most, starting at least 25 ms apart; a 429 or 5xx is asked once more after a short wait (Retry-After, at most 5 seconds). Within a run, each different password is one request, and passwords whose hashes start alike share one.
- **What's kept:** the client keeps nothing once a check is done: no password, hash, or answer, the master password included, in the web vault, the extension, and the desktop app alike. The web vault remembers what its automatic checks found by item id and revision date, never by password or hash, so the MSP console working its counts out again after an action doesn't ask again, and an edited item is asked about anew; failures are never remembered, and it's all forgotten when the vault locks or signs out (the web vault reloads then too). Nothing is kept across sessions: doing that would mean encrypting results with the account's key, a new use of a key that would need its own design and test vectors.
- **Calling a check off:** each run carries a signal. The MSP console calls its run off when it works the counts out again or the person leaves it, and the count beside Health when the items change or it's no longer shown. A request every waiting check has called off is dropped from the queue, or stopped if it's out. Automatic checks also read the setting again just before each request goes out, so turning it off (in any tab) while a run is queued sends nothing more.
- **When the service can't be reached** (offline, a firewall, a captive portal, an error, or no answer within 10 seconds): the check fails instead of answering "not exposed". The checks already waiting behind a failure fail at once, so a firewalled network doesn't wait out a timeout per password; checks asked for later try again. The exposed report says how many items couldn't be checked (and never says "Good news" then), the MSP console says "Couldn't check" with Try again and how many items, the count beside Health keeps weak and reused and shows a sign that it couldn't check (shown even when there's nothing else to fix, so a failed check never looks clean), the item editor says it couldn't check, and sign-up goes on without it, as before. What couldn't be checked is counted in items everywhere.
- **The same counts everywhere:** which passwords count, and what's weak, reused, and exposed, are upstream's report rules kept in one place (`libs/common/src/dirt/keykeeper/password-health.ts`) that the weak, reused, and exposed reports (a person's and each organization's), the MSP console, and the count beside Health all use. Counted: logins with a password the person may see, outside the trash, and in a person's own Health only items they can edit. Weak is a strength score of 2 or less out of 4, with the username's parts as hints. Reused is a password another counted item also uses (within one client, in the MSP console). Exposed is seen in at least one breach.
- **In the MSP console:** an Exposed column per client beside Weak and Reused. Weak and reused show first; exposed follows, with progress across every client ("Checking passwords against known breaches: 12 of 40"). For a client whose items the person can see, a count with something in it opens the client's list of items to fix by name (never their passwords), the most exposed first, with what's wrong (Exposed N times, Weak, Reused), how many items couldn't be checked ("Nothing weak or reused; 2 items couldn't be checked for breaches" rather than "Nothing to fix"), and Open: in the client's admin console for its owners and admins, otherwise in the person's own vault, since a custom role can't load the admin console's vault. The console counts the items the person's own vault holds, as its expiring list does; an organization's own reports count every item its admin console lists.
- **Tests:** unit tests for the client (only 5-character prefixes sent, padding asked for, no redirects, nothing else in the request; matching with either line ending and padding entries; every answer that isn't the service's refused and asked again next time: empty, whitespace, 204, other statuses, too few lines, lowercase, an over-long count, a short suffix, over 1 MB by header or by stream; one retry after a 429 or 5xx with Retry-After held to its cap, none when offline; nothing kept; the queue failing behind a failure; timeouts; at most 4 at once and spaced; calling off a queued run sends nothing more, a shared request goes on while any check wants it, and a setting turned off after queueing stops the rest; random order) and for the web vault's memory by item version (never failures, forgotten on lock), the shared rules, the MSP counts and details, the count beside Health (a sign when it couldn't check, calling off on recount, the setting read before each request), the setting following another tab, and the item editor's message; and an end-to-end test where Playwright stands in for the service (the test browser reaches no outside host): each client's counts, the console asking nothing more when it works them out again, the list of what to fix and Open, "Couldn't check" in items when firewalled and Try again, the count beside Health and its sign when firewalled, the exposed passwords report, and every request checked to be a padded GET for a 5-character prefix and nothing more; and, with the setting off, no request at all after unlocking (the count is weak and reused, the console says "Not checked") until the console's button or the report asks, and turning it back on in another tab reaches the open one.

## Account keys (open)

- **Upstream model:** the master password and email go through a KDF (PBKDF2 by default, or Argon2id) to make the master key, which unlocks the account key stored on the server. The server never sees the master password. If the database is stolen, each vault can be attacked offline, and only the master password's strength protects it.
- **1Password model:** the master password is combined with a 128-bit Secret Key that never leaves the user's devices, so a stolen database is useless. The cost is the Secret Key step in onboarding, which is exactly the friction we want to remove.
- **Proposal:**
  1. Version 1 keeps the upstream model with stronger defaults: Argon2id, plus master-password strength and breach checks at signup. Changing the key hierarchy is the riskiest change possible.
  2. Business orgs get trusted-device unlock, where a device key works like a Secret Key the user never sees.
  3. After an external crypto review: an optional account key for Solo and Family, added to the KDF input and kept on devices and in the recovery kit. New devices get it from an existing device by QR code, never by typing or downloading.

## Autofill

The goal is to be measurably better than upstream. 1Password currently does this much better than Bitwarden.

- **Corpus:** reduced fixtures of real login patterns. Multi-step logins, iframes, shadow DOM, single-page apps, one-time-code fields, signup and change-password forms, card forms.
- **Scoreboard:** every commit runs both the upstream extension and ours against the corpus. We publish the numbers.
- **Reference material** (compatible licenses only): Chromium autofill heuristics (BSD-3-Clause), Firefox form detection (MPL-2.0), and `apple/password-manager-resources` quirks data (MIT).
- **Per-site corrections:** handled by fill rules (next section), and shared, for people who choose to, as site fixes (see "Site fixes (opt-in)").

### How it keeps getting better

Most sites fill on the generic rules; the work is the long tail, found one site at a time. The loop:

1. **Finding them:** opt-in problem reports and shared site fixes (built, below) say which sites fail and how, as the shape of their sign-in fields, never values. MSP consoles see their staff's.
2. **A fixture for each:** every site we fix gets a reduced page in the corpus that reproduces its pattern (our own markup, not the site's code), so it can't break again unnoticed.
3. **The scoreboard:** CI runs our extension and upstream's against the whole corpus on every change and publishes the numbers. A change that makes any fixture worse fails.
4. **Curated fixes, shipped as data:** fixes we've reviewed ship in the extension as a list, like the site password rules: selectors and field roles only, never code from a server, so a compromised server or list can't run anything in a page. Fixes three people sent apply on their own server before that (built), and an MSP's apply to its clients at once.
5. **Generic first:** when several sites fail the same way, the fix goes into the generic matching instead of the list.

- **Not learned automatically:** nothing is learned from page contents in the background; every shared fix is something a person chose with the fill picker, and every curated one is reviewed by us.
- **Status:** steps 1 and the server half of 4 are built, and the corpus has started (`e2e/tests/autofill-corpus.spec.ts`): 12 sign-in pages, each one hard pattern (two steps on one page, a form drawn late, no form element, a shadow root, a same-site frame, decoy fields, a search box and a newsletter box nearby, labels wrapping fields, placeholders only, aria-labels only, a change-password form). Tier 1 fills each from the menu in a field, checks every field it should or shouldn't fill, prints the score, and fails when a page that filled stops filling, or when a known miss starts filling (so the list stays true). Today: 14 of 14 (one page is tried from two fields). The last miss, a username field the menu had no word for ("Account name", by aria-label), is fixed: a text field just before a sign-in password field in the same form is its username, whatever it's called. Next: add pages (one-time codes and card forms are tested separately today), run upstream's extension against it for the comparison, then the curated list.

### Choosing what fills where

Upstream fills a custom field only when its name exactly matches the page field's name, id, or label, so users end up reading HTML to make it work. Keeping the password from landing in the wrong field is just as hard. Ours:

- **Fill picker:** from the extension popup, or by right-clicking any field, choose "Fill this field with...". The list shows every value on the item (username, password, one-time code, each custom field, card and identity fields) plus "Never fill this field". One click fills it now and remembers the choice.
- **Rules travel with the item.** They are stored encrypted with the item, so they sync to every device. Site-wide "never fill" rules live in the user's encrypted settings.
- **Durable field identity:** a rule identifies a field by a fingerprint (autocomplete, name, id, label text, type, and position in the form), so small page changes don't break it.
- **Custom fields never fill on a guess.** They fill by rule, or by a confident label match ("Customer ID" against "Customer number") that the user confirms with one tap the first time.
- **Readable rules:** the item view and editor list an item's rules in plain language, for example "bank.example: the field with id custno gets the Customer ID field", and say when a rule's custom field is no longer on the item. The editor removes one; to change one, pick again in the extension (a new choice for the same field replaces the old one). The MSP console describes site fixes in the same words.
- **Storage (built):** a rule is a hidden custom field named `keykeeper.fill` whose value is a small JSON document (`apps/browser/src/autofill/keykeeper/fill-rules.ts`). It's encrypted and synced like any field, and the server and other clients need no changes.
- **Where a rule fills:** only on the host (and port) it was made on, so a rule on an item that matches several sites, or one someone with edit rights added, can't send a value anywhere else; only into a field the person can see; and, when the rule names a field id, only a field with that id (a name or label never stands in for it). For someone who can't see the item's passwords, a password or hidden field goes only into a password field. Our own fields (`keykeeper.*`) never fill a page field by name.
- **The picker keeps upstream's rules:** an item that asks for the master password asks before its password, code, or hidden fields fill (the rule is saved, and the fill after the prompt uses it); hidden fields aren't offered to someone who can't see passwords; and a secret never goes into a frame from another site.
- **Built so far:** the right-click picker (`fill-field-menu.ts`). Value rules fill first, before upstream's matching. Never-fill fields are hidden from upstream's field selection, so a value meant elsewhere moves to the next fitting field. Readable rules in the item view and editor of the web vault and the extension (`libs/common/src/vault/keykeeper/fill-rules.ts` reads and describes them, `libs/vault/src/keykeeper/fill-rules-*.component.ts` show them); the raw `keykeeper.fill` fields never show as custom fields. Unit tests cover the rules, the descriptions, removing one, and the menu. Tier 1 covers a custom field into a differently named field, never-fill, and a rule shown in the web vault, kept through an edit, and removed there, after which it no longer fills.
- **In the menu inside a field (built):** each login has a picker button beside it, which shows the same values; picking one fills the field the menu is in and remembers it, through the same code as the right-click menu (`fillFieldWith` in `fill-field-menu.ts`). The menu gets the values' names only, never the values. Arrow keys reach it like the menu's other buttons. Tier 1 picks a login's custom field for a site's Username box from the menu, then checks a normal autofill puts it there again.
- **Next:** one-tap label-match suggestions, site-wide never-fill, and translated strings for the menu and the rules.

### Site fixes (opt-in)

When a site doesn't fill right, someone fixes it with the fill picker. Site fixes let that fix help everyone else on the same server, and tell us which sites need work, without passwords, custom field names, or browsing leaving anyone's device unless they choose. Decided October 2026: opt-in, anonymous, and nothing applies to others until several people agree.

- **What a fix is:** the site's host, how to recognize the field (the id, name, or label a fill rule records), and which kind of value goes there: the username, the password, the one-time code, or "never fill". Never a value, a custom field's name (it can say something about the person), a page address beyond the host, or anything else on the page.
- **Sharing is off until the person turns it on** (the extension's Autofill settings: "Share fixes I make with the fill picker"). With it on, each fix they make with the fill picker goes to their own server: PassBundle's hosted service, or the server their organization runs. Custom-field fixes stay on their device either way.
- **"Report a problem with this site"** (the extension's current-tab view) sends the host and the shape of the page's sign-in fields (types, ids, names, labels, and autocomplete hints; never values) with an optional note. It's one report per click, sharing or not, and the form says exactly what goes.
- **Anonymous:** a fix is stored once, with a count of the different people who sent it. The server counts each person once by a keyed hash of their account and the fix, with a key only the server has, so it never stores who sent what; problem reports keep no account at all. At most 20 problem reports per site a day are kept.
- **Confirmed fixes apply to everyone on the server** once 3 different people have sent the same one (`SITE_FIX_REPORTERS`). The extension downloads the whole confirmed list when it unlocks and once a day, and matches it on the device, so asking doesn't tell the server which sites someone visits. A fix fills only where the person's own item has no rule for that field, with the same limits as their rules: the same host, a visible field, an id that decides, and passwords only into password fields for someone who can't see them.
- **MSPs:** fixes their own staff share also show in the MSP console, with who sent them (staff are accountable to their MSP). An MSP admin can apply one to every client right away ("Use for every client"); those MSP site rules reach the members of its clients and its staff the same way, without waiting for three people. Changes go in the MSP's activity log.
- **For us:** the server's admin page lists the sites with problem reports and the fixes waiting for confirmation, newest first. That's the private list of what needs work.
- **Privacy policy:** a section says what each choice sends and that it's off by default.
- **Tests:** unit tests for what a fix contains (and doesn't), sharing only when turned on, the downloaded list matched on the device, and fixes applied after the item's own rules with the same limits (`apps/browser/src/autofill/keykeeper/site-fixes.spec.ts`); API tests for counting each person once, the threshold, what a fix and a report can hold, the daily cap, and MSP rules with their permission matrix (`e2e/tests/api/site-fixes.spec.ts`); and an extension test where an MSP admin turns sharing on, fixes a field with the fill picker, sees it in the console, uses it for every client, and the extension applies it to a login without a rule, and another that reports a site from the current tab's suggestions and checks the report carries the fields' shape and the note, never what's typed in them (`e2e/tests/site-fixes.spec.ts`).
- **Status:** built: the server (`keykeeper_site_fixes.rs`, a migration, the admin page's Sites list), the extension (`site-fixes.ts`, the Autofill settings section, and the report page, linked from Autofill settings and from under the current tab's suggestions, in the popup or a popout), and the console's Site fixes section.

### One-time codes never become passwords

This is a hard invariant, enforced by tier 1 tests.

- Fields classified as one-time code inputs are never treated as password fields. Signals: `autocomplete="one-time-code"`, OTP, 2FA, MFA, or verification hints, and short numeric inputs that follow a login step.
- The save or update prompt never offers a value that equals the item's current TOTP code. It also never offers a value that looks like a code (4 to 8 digits) when the saved password is not itself all digits.
- Every password update keeps the old value in password history, and the notification has an Undo.
- The corpus includes many one-time-code page variants. Any save prompt on them fails the build.
- **Found in upstream:** the background keeps a sign-in's submitted form data for five seconds and fills a later username-less submission's gaps from it. A code pasted on the second step within that window becomes "alice-example changed her password to 123456". Fixed: a username-less submission whose only secret is 4 to 8 digits is never stored or merged. A username with a numeric PIN still saves.
- **Fields the page calls a code:** upstream skips fields tagged as codes. Ours also never takes a field for the password to save when the page calls it a code ("Enter the code we sent you", "Login code", an `otp` id) and nothing about it says password or PIN (`apps/browser/src/autofill/keykeeper/one-time-code-fields.ts`). That covers passwordless sign-ins that show the email next to the code, which the value check can't tell from a PIN login. A PIN on the same kind of page still offers to save.
- **Tier 1 coverage:** tagged, masked (`type="password"`), and bare code fields, each on its own page and as the second step of a sign-in submitted inside the five-second window, after a calibration that proves the prompt still works for a real password change; and a passwordless sign-in with the email and a masked code on one page, next to the same page with a PIN, which still prompts. Unit tests cover the guard and the field check, and fail without them.

### Missed save prompts on fast sites (upstream race)

After a sign-in form is submitted, upstream asks the page for the typed values over an async message while the request is in flight. When the site answers instantly (a fast intranet app, or a local server), the request completes first and the save or update prompt is silently dropped. Fix: capture the form values synchronously at submit time in the content script, and keep them until the response arrives. Until then, the test fixture server answers sign-ins after 300 ms, like a real site.

## Script access (our Secrets Manager)

Bitwarden's Secrets Manager is a separate DevOps product under its source-available license, so we can't use it. Ours starts from what MSPs need: RMM scripts that use credentials (domain admin, client API keys) without pasting them into the RMM in plain text. The full design is `docs/script-access.md`, with test vectors in `docs/vectors/script-access-v1.json`.

- **Scoped tokens:** a token reads only the fields of the items it was granted, in one organization. It can't list or browse the vault.
- **Made for scripts:** a PowerShell module first (`Get-PassBundleCredential -Item "Domain admin"`), the command-line client later.
- **Short-lived and limited:** tokens expire (at most a year), can be limited to networks, and are revoked instantly. Binding to a machine comes with the desktop agent.
- **End-to-end encrypted:** a grant is a copy of the chosen fields, encrypted with a key derived from the token's seed, which the server never sees. The token key is also sealed with the organization key, so apps that hold it keep copies current after edits.
- **Audited:** every read is logged with token, item, time, and address. A token's first use from a new address shows in the MSP's activity log.
- **Status:** built (October 20, 2026).
  - **Settings page:** an organization's owners and admins, and its MSP's admins, make tokens, see each token's reads, and revoke them. The token string shows once, with the lines a script needs.
  - **The module:** the server serves `PassBundle.psm1` with its own address filled in. It works in Windows PowerShell 5.1 and PowerShell 7 with nothing to install, and gives `Get-PassBundleCredential` and `Get-PassBundleSecret` (username, password, a current one-time code, or a custom field).
  - **Copies kept current:** the web vault and the extension refresh a grant's copy after its item changes, and the settings page shows a token as Updating until they have.
  - **Tests:** the API tests cover reads, refusals, networks, the 60-a-minute limit, refreshing, and who may do what. The module runs against the test server, and the vectors' checks run under Windows PowerShell 5.1 and PowerShell 7 on Windows. Upstream's crypto checks the vectors too.
- **Later:** rotation helpers that change a credential and update the item together, plus CI integrations if developers ask.
- **Clean room:** designed from public descriptions only. Never read Bitwarden's Secrets Manager code or SDK.

## Sending events to security tools

MSPs run security stacks (a SIEM or an MDR service such as Huntress, Blumira, or Microsoft Sentinel) that expect every business tool's audit events, and both Bitwarden and 1Password send theirs. Ours: an organization's events go to its security tools as they happen. What receivers get, and how to set up each tool: `docs/event-streaming.md`.

- **Where they go:** each organization has up to five destinations, of three kinds:
  - **Webhook:** an HTTPS POST of each event as JSON, signed the Standard Webhooks way: `webhook-id`, `webhook-timestamp`, and `webhook-signature` (`v1,` and the base64 HMAC-SHA256 of `<id>.<timestamp>.<body>`) with a secret per destination, shown once. An optional header (such as Authorization) carries a collector's own token, so HTTP collectors take events directly.
  - **Syslog over TLS:** RFC 5424 messages framed by octet counting (RFC 5425), facility "log audit", with a JSON or CEF message. A private certificate authority can be given for collectors on a company network.
  - **Microsoft Sentinel:** Azure Monitor's Logs Ingestion API, signed in as an app registration (client credentials) and sending to a data collection rule's custom stream. It trusts only the system's certificate authorities; a destination can't bring its own. Azure Government and Azure in China work through server settings, which are set only in the environment (never in the admin panel) and must be https and Microsoft's: a sign-in host of Microsoft Entra's, and a scope and ingestion domain under Azure Monitor's (`monitor.azure.com`, `.us`, or `.cn`). Only `EVENT_STREAMING_AZURE_TEST` lifts that, and only it allows a certificate authority of the server's own, for a test stand-in.
- **The MSP's feed:** an MSP's admins can add destinations for the MSP itself. They get every client's events, each tagged with the client and the MSP, and the MSP's own activity log (codes 9100 to 9199), so the MSP's SOC gets everything in one feed. A client's own destinations get its events without the MSP tag.
- **What an event says:** its id, time, type (upstream's code and a name in words), category, severity (low, medium, or high), the organization (id and name), who acted (a person's id and email, or "system" when nobody did, as with provisioning), what it was about (a member with their email, or an item, shared folder, group, or policy by id), and the address and device as upstream records them. Never item or folder names, vault contents, or secrets: the server can't read the vault, and an event says nothing the event log doesn't already keep.
- **Who sets it up:** an organization's owners and admins. Not custom roles, managers, or an MSP's technicians: a technician is an admin in each client but mustn't be able to send a client's activity somewhere the client and the MSP can't see. An MSP's admins for the MSP's feed, and in each client as its owners. A destination is reached only through its own organization or MSP (not an MSP's feed through a client, nor a client's through its MSP). One person sets up destinations in at most 20 organizations and MSPs (others there can add more). A destination stays with its organization or MSP when that person's account is deleted (it records who set it up as a foreign key that's then cleared), and then shares the worker's time as its organization's or MSP's own.
- **Changes are events:** every change is in the organization's event log (types 1690 to 1692) or the MSP's activity log (9170 to 9172), all high severity and never dropped from a full queue, and goes to the other destinations like any event, saying which destination (its id, name, kind, and what the console shows of where it sends, never a secret), what changed (`changes`: name, settings, where it sends, new signing secret, turned on, turned off), and whether it's on. When the server turns one off, that's an event too: 1693 by no one (the system), or the MSP's 9173, with the destination's id and why. A destination that's turned off, removed, or pointed somewhere else gets one last event saying so first, so even a lone SIEM sees it: in the background, two at a time on the server, a few per organization or MSP and then one every 10 seconds, tried three times (now, after 5 seconds, after 30). Not kept across a restart.
- **Delivery:** every event saved to the event log is copied into a queue in the database (`event_deliveries`) for each destination that takes it, so a restart loses nothing.
  - **At least once:** an event can arrive twice (receivers drop repeats by its id), and events aren't promised to arrive in order.
  - **Fair time:** one worker per server sends to 16 destinations at once, but never two of one organization or MSP, and never more than two set up by one person (one whose account is gone counts as its organization or MSP). Turns go by the sending time used, not by turns taken: the person (who set the destination up) who has used the least goes first, then, among theirs, the organization or MSP that has used the least. Someone new starts level with whoever has used the least, and what everyone has used decays every five minutes. So one person with many slow destinations, or many organizations, gets no more of the worker than anyone else. A turn ends after 20 seconds, or 50 webhook events (400 syslog or Sentinel events). A webhook gets 5 seconds to connect and 10 to answer.
  - **Finding work:** each destination keeps when its earliest waiting event is due (`next_due_at`, updated as events are queued and after each turn), so the worker's look for work is one indexed query on the destinations, at most 500, never a scan of the queue.
  - **Slow isn't failing:** an answer slower than 5 seconds (10 for syslog and Sentinel), a turn that ends at its deadline (mostly spent sending) without catching up, or a turn whose sending averages more than a second an event, counts as slow. Only time spent sending counts, never the server's own waits (a busy database doesn't make a receiver slow). What it took is delivered; the destination is held back for 10 seconds, growing with each slow turn in a row to 10 minutes, and the console says "Slow" and why. Slowness never turns a destination off and never counts as failing.
  - **Failing receivers wait:** a failure holds the destination back for 10 seconds, then growing to an hour, with some randomness. So a slow or broken receiver, however many an organization or a person sets up, holds up only its own events.
  - **Retries:** for three days; then the event is dropped and counted. Everything goes as soon as one delivery works again.
  - **Floods merge:** what an app reports (item views, copies, fills, exports, notice clicks), failed logins, and single sign-on's refusals, which anyone can make many of, wait as one event per kind, organization, person, and minute (of the server's clock) with a `count`, `lastTime`, and up to 20 different `targets` and `ips`. So someone in several of an MSP's clients gets one event per client in the MSP's feed, never one for all of them. Once the worker takes an event to send, nothing more joins it; the next ones start another.
  - **What apps report is bounded:** `/events/collect` refuses a request with more than 500 events (413, nothing recorded, rather than keeping some), and our apps send a longer backlog in batches of 500, keeping a batch that fails for the next try. A person's apps get 30 requests in a row and then one every 2 seconds (429 past that).
  - **A bounded queue:** at most 10,000 wait per destination, kept as a running count. Past that the least important go first (low severity, then medium, then high, oldest first), counted. Changes to who can do what are kept and never dropped: members (except notice clicks, and single sign-on's sign-ins and refusals), groups, shared folders, the organization's settings, its single sign-on and domains, policies, its destinations, and the MSP's staff and clients; past twice the limit with only those, the oldest go. In an MSP's feed, the client with the most waiting loses first, so one client's member can't crowd out the others. Dropped events are still in the event log, which exports to CSV or JSON.
  - **Leases:** a worker holds a lease on a destination while it sends, released only by the worker that holds it, so two servers sharing a database don't send the same events at once.
  - **Stopping:** a destination that has failed for a day (and at least 10 times in a row), answers 410 Gone, or whose secrets can't be read is turned off (never one that's only slow), logged as above, and its organization's owners and admins (or the MSP's admins) get an email, at most once a day per destination, saying only what kind of trouble (an HTTP status, never what a receiver said) and that slowness alone never turns one off. Events keep waiting for it, so turning it back on sends what it missed. Turning one off on purpose drops what's waiting.
- **Rate limits:** five destinations per organization or MSP, and organizations and MSPs with destinations per person (both checked inside the transaction that adds one); at most 20 webhook requests a second to one destination; syslog in batches of 200 over one connection (at most three of a name's addresses tried, all within 30 seconds); Sentinel in uploads under its 1 MB limit, at most 5 a second; what apps report, as above; tests: one at a time per organization or MSP and per person, three in a row and then one every five seconds per person, four at once per server, and without holding a database connection while they wait on a receiver.
- **Secrets at rest:** a webhook's URL (collectors often put their token in it), its signing secret, a header's value, and Sentinel's client secret must be usable by the server (HMAC needs the secret), so they can't be hashed.
  - They're encrypted with AES-256-GCM under a key derived from the server's private RSA key: HMAC-SHA256 with a fixed label (`passbundle event streaming secrets v1`) over the key's PKCS#1 DER encoding, as upstream derives its pre-login key from the RSA key, so rewriting `rsa_key.pem` in another PEM form keeps the key. Each ciphertext is `v1.` and the base64 of a random 12-byte nonce and the sealed text, bound (as associated data) to its destination's id, its owner (organization or MSP), and its kind.
  - Test vectors: `docs/vectors/event-streaming-secrets-v1.json` (made by `make-event-streaming-secrets-v1.mjs` with Node's crypto alone) gives a throwaway RSA key in both PEM forms and its DER, the derived key, and for fixed nonces the associated data, plaintext, and `v1.` text, plus bindings that must fail. The server's unit tests check its derivation and sealing (split out for this, with the nonce given) against a copy, and tier 1 checks that the copy is this file.
  - That key lives where the RSA key does (the data folder, or its bucket), never in the database, so a copy of the database, such as the backups kept at another company, doesn't reveal them. Keep the data folder's backup apart from the database's. Replacing the RSA key (which also signs everyone out) leaves them unreadable: those destinations stop and ask for their secrets again.
  - Wiped from memory, as a best effort: the derived key, the RSA key's DER once the key is derived, the secrets' JSON while it's sealed or opened, and the opened secrets when they're dropped. Not wiped: the RSA key itself (the server keeps it to sign logins), the request a secret arrives in, copies the HTTP and TLS libraries make while sending (the URL, a header's value, the signing key inside the HMAC), Sentinel's access tokens (kept until shortly before they expire), and whatever the allocator leaves behind. The console never shows a secret again; a webhook appears as its scheme and host only, and the URL, the header's value, and the client secret are masked like passwords, each with a button to show what's typed.
  - A secret stays with exactly what it was entered for. Any change to a webhook's URL, its certificate authority, or its header's name asks for the header's value again; a change to its certificate authority asks for the URL again too (trusting another authority could expose what's sent, so it takes knowing the URL, which can carry a token); and a new host gets a new signing secret (shown once). Changing Sentinel's tenant, app, or endpoint asks for the client secret again. So another admin can't redirect one to themselves.
  - What receivers answer is stored with the destination's secrets taken out before it's cut to 200 characters: header values and their tokens, signing and client secrets, the URL, its query and each query value, and each path segment of 8 or more characters (collectors put tokens there), also decoded and as JSON escapes them. Where a cut (or reading only the answer's first 4 KB) leaves the start of one of those at the end, that start goes too.
- **Server-side request forgery:** a destination is chosen by an organization's admin, so the server mustn't become a way into its own network.
  - Webhooks are HTTPS only, with no user name or password in the URL; no proxies, no redirects.
  - The server resolves every name itself and checks every address it resolves to, and the request is pinned to those addresses (no second lookup that could answer differently). A name with any refused address is refused.
  - Public addresses only: for IPv6, global unicast (2000::/3) only. Private networks, addresses, or host names only where the server's admin lists them in `EVENT_STREAMING_ALLOWED_NETWORKS` (each with an optional port), for a self-hosted server whose security tools share its network. Loopback only through an entry that's itself loopback, never through a host name or a broader network.
  - Never allowed, whatever's listed: link-local addresses, cloud metadata services (169.254.169.254, AWS's fd00:ec2::/32, Google's fd20:ce::254, Oracle's fd00:c1::a9fe:a9fe and 192.0.0.192, Alibaba's 100.100.100.200, Azure's 168.63.129.16), multicast and reserved addresses, IPv4 written as IPv6 (::ffff:0:0/96, NAT64, 6to4, Teredo, IPv4-compatible), and anything the server's `HTTP_REQUEST_BLOCK_REGEX` matches.
  - Errors don't map the network: anything that goes wrong before a connection and its TLS handshake are complete (a refused address, a name that doesn't resolve, a closed port, a timeout, a certificate rustls rejects) gives the same message, with the details in the server's log only, and the Test button answers it 16 seconds after the test started, whatever it was, so it can't be timed either. After that, people see a receiver's status and the start of its answer (redacted, 200 characters, from the first 4 KB, read no further), and only the status when private networks are allowed.
  - A Sentinel endpoint must be under Azure Monitor's ingestion domain, checked when it's saved and again before each upload.

## Capacity

What one Phase 0 server handles, measured by the load test in the private ops repo (`hosting/load/`): the Release image with the app and PostgreSQL sharing two cores (a mobile Xeon E-2276M) and 4 GB, 500 accounts with 100 items each (50,000 items in the database), and k6 on other cores.

| Request | Per second | Median | 95th percentile |
|---|---|---|---|
| Sync (`/api/sync`, what every app does on unlock and after changes) | 451 | 110 ms | 119 ms |
| Saving an item | 884 | 56 ms | 63 ms |
| Signing in with the master password | 9 | 866 ms | 1.3 s |

- **Signing in is the expensive one, on purpose:** the server hashes the master password hash again (PBKDF2, 600,000 rounds) before comparing it. Unlocking doesn't touch the server. On rollout day, 200 people signing in within the same minute wait at most about 20 seconds.
- **What that means for people (assumptions, not measurements):** in the busiest hour, an active person's apps sync about 6 times and save once, and 1 in 10 people signs in with their password. Then one starter server has room for well over 100,000 people active in that hour. A provider's vCPU is often slower than these cores, so halve it to be safe. Resize when the busiest hour uses half the CPU (launch plan, "How it scales").
- **Not measured yet:** live-update connections (one per open app), memory over days, and organizations with thousands of shared items.

**Sync used to get slower as the service grew.** Upstream's item query (`Cipher::find_by_user`) left-joins items to memberships, collections, and groups and ORs the access conditions across the joins, which no index can serve, and upstream has no secondary indexes. So every sync read every item in the database: the same 100-item vault synced at 258 a second with 2,000 items in the database and 65 with 50,000 (310 ms in the item query).

- **The fix (passbundle-server):**
  - **Narrowing:** every access condition in that query goes through the join on the person's confirmed membership in the item's organization, or else it's the owner condition. So the query is first narrowed to items the person owns or that belong to one of their confirmed organizations, with those organizations looked up first. The conditions that decide are unchanged, and so is what it returns.
  - **Indexes:** a migration (`keykeeper_lookup_indexes`) indexes what sync and sign-in look up by.
- **Tests:** every API and mail test (permissions across owners, collections, groups, admins, custom roles, and MSP staff) passes unchanged on SQLite and PostgreSQL. The load test is the regression check for speed.

Determinism rules:

- Inject the clock.
- Test encryption by round trip and known vectors, never by comparing ciphertext.
- No live network in tiers 1 and 2.
- Each test gets a fresh database.
- Wait on state, never on sleeps.

The maintainer gets a morning summary, with screenshots and video only for failures.

**Changes that span repos** use the same branch name in each repo. Tier 1 tests a pull request together with the same-named branches of the other repos, so linked pull requests pass before any of them merges, and none of them goes red only because another hasn't merged yet. Branches are deleted when their pull request merges, so a stale one is never picked up.
