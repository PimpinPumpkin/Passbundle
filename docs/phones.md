# The phone apps

Design, October 21, 2026. The phone apps are the desktop app's Flutter screens and the same core (`docs/core.md`), on Android and iOS. Phones keep keys and tokens differently from computers, unlock with the phone's own biometrics, and fill other apps through the OS's autofill. All of that handles keys, so per the rule in DESIGN.md, this note comes before the code.

## What's the same

- **The screens.** One Flutter app; the phone layout already exists (the narrow window: a header, the list, an item on its own page).
- **The core.** The same Rust library, built for each phone's chip. Everything in `docs/core.md` holds: the format and its vectors, signing in, sync, the kept vault, HTTPS only, secrets staying in Rust's memory where they can be wiped, and the bridge (plain C functions, JSON in and out).
- **The look.** Our own design, not each OS's. The one exception is what the OS draws itself: the biometric prompt, and the autofill and password suggestions lists.

## The core on phones

- **Android:** a shared library (`libpassbundle_core.so`) for `arm64-v8a`, plus `x86_64` for the emulator, built with the Android NDK and packed into the app. No 32-bit ARM: Google Play has required 64-bit since 2019, and business phones are.
- **iOS:** a static library in an XCFramework, for devices (`arm64`) and the simulator (`arm64`), linked into the app and its autofill extension. Dart finds it in the process (`DynamicLibrary.process()`). iOS 17 and later: the AutoFill extension's newer credential requests start there, and iPhones from 2018 on run it. `tools/ios-core.sh` in passbundle-apps builds it, and runs the core's tests on an iPhone simulator, as CI does.
- **The data folder** is the app's own: on Android the app's private files folder, which the app passes to the core at start (`pb_open`); on iOS an App Group container (`group.com.passbundle.app`), so the AutoFill extension reads the same kept vault; Swift passes it to the core as Kotlin does on Android. The session's refresh token and the Face ID item are in a Keychain group the two share, too.

## Kept where

| What | Android | iOS |
|---|---|---|
| Server, email, KDF settings, the last sync (secrets still encrypted), lock choices | the app's private files folder | the App Group container |
| Refresh token | encrypted with a key in the Android Keystore that never leaves it (AES-256-GCM, this app only, not backed up), in the app's private files | the Keychain, this device only, after first unlock (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`), in a keychain group the extension shares |
| The device token (DESIGN.md, "New-device check") | sealed with the same Keystore key as the refresh token, `tokens/<hash>.device.sealed` | the Keychain, service "PassBundle device token", as the refresh token |
| The user key, for biometric unlock (below) | encrypted with a Keystore key that needs the person's biometrics for each use | the Keychain, readable only after Face ID or Touch ID with the biometrics enrolled now (`biometryCurrentSet`), this device only |
| Master password, master key, private key, organization keys, anything decrypted | memory only, while unlocked | memory only, while unlocked |
| Browsers the person trusted for autofill (package names and certificate hashes) | the app's no-backup files folder | (none: iOS says which website) |

- **Several accounts** (DESIGN.md, "Several accounts in the apps"): each account has its own folder in the app's (`accounts/<id>`), its own refresh token, and its own biometric key: on Android a Keystore key named `passbundle-biometric-<id>` and `biometric-<id>.sealed`, on iOS the Keychain item `user-key-<id>`. The account's id is made on the phone and says nothing about the account. Autofill and passkeys offer every unlocked account's logins, each labeled with its account's name, and fill or sign from that account only (DESIGN.md, "All accounts").
- **Backups:** the app's backup rules leave its files out of Android's backups (auto-backup would include them otherwise), Keystore keys never leave the phone, and the iOS Keychain items are "this device only". The kept sync is still encrypted, so a backup of it alone would open nothing anyway.
- **"Never lock"** (keeping the user key without biometrics) isn't offered, as on the desktop.

## Talking to the OS

The core needs a few things only the OS's own APIs do on phones: the Keystore, the Keychain with biometrics, the clipboard, and autofill. Each phone app has a small native piece, Kotlin on Android and Swift on iOS, with plain functions the core calls:

- `seal(bytes) -> bytes` and `open(bytes) -> bytes` with the app's Keystore key (Android; on iOS the Keychain does this);
- `copy(text, sensitive, clear_after)`;
- on Android, the autofill service's calls into the core (below);
- on Android, a security key for two-step login (`SecurityKeys.kt`): it finds a key held to the phone (NFC's reader mode) or plugged in (USB, with Android's permission for it), and passes the core's APDUs or HID reports to it; the CTAP is the core's, as on computers (DESIGN.md, "Two-step login in the apps"). It also reads a YubiKey's one-time code held to the phone;
- Duo's way back at sign-in: on Android a screenless activity takes `passbundle://duo-callback` and brings the app back; on iOS the system's sign-in sheet (ASWebAuthenticationSession) hands the link back itself.

On Android the core reaches Kotlin through JNI; on iOS Swift hands the core C function pointers at start. Dart isn't in the path, so secrets stay out of Dart as on the desktop. Kotlin's and Swift's strings can't be wiped either, so a secret is only put into one where the OS takes nothing else (the clipboard, an autofill value), and byte arrays are zeroed after use.

## Unlocking with biometrics

The phone's own fingerprint or face unlock, standing in for the desktop agent's Windows Hello. It changes how the user key is kept, so the rules:

- **Turning it on**, while unlocked, in Settings: "Unlock with fingerprint" (Android) or "Unlock with Face ID" (iOS).
  - **Android:** a new AES-256-GCM key in the Keystore that needs the person's strong biometrics for every use (`setUserAuthenticationRequired`, `BIOMETRIC_STRONG`), is invalidated when someone adds a fingerprint or face (`setInvalidatedByBiometricEnrollment`), and is in StrongBox where the phone has one. The OS asks for the biometric (`BiometricPrompt` with the key's cipher), the user key is encrypted with it, and the result is kept in the app's files.
  - **iOS:** the user key goes in the Keychain with access control `biometryCurrentSet`, this device only.
- **Unlocking:** the lock screen offers it when it's on. Android asks for the biometric and decrypts the user key with the Keystore key; iOS reads the Keychain item, which asks for Face ID or Touch ID. The core opens the kept vault with the user key, without the KDF, as with Windows Hello.
- **Asked for by itself:** as PassBundle opens locked, and each time it comes back to the front locked, the lock screen starts the prompt on its own, once, and the keyboard waits; cancelling it leaves the master password, with the keyboard up. Not after the person pressed Lock, nor when it locks by itself while it's on screen (`app/lib/main.dart`, `biometricAsks`). Without biometric unlock, the field takes the keyboard as the screen opens.
- **The master password hint:** the lock screen's "Get your master password hint" asks the account's server, with no session (upstream's `POST /api/accounts/password-hint`): the server emails it to the account's email, or, on a server without email that's set to show hints, answers with it, and the app shows it (`Server::password_hint`, `pb_password_hint`). The server answers an email with no account the same as one with, as before.
- **The key goes from the OS's code to the core directly:** Kotlin or Swift hands the bytes to the core's native function and zeroes them; it never passes through Dart.
- **Someone adds a fingerprint or face:** the OS invalidates the key, the app can't decrypt, it turns biometric unlock off and asks for the master password once. The same if the account's keys change (the user key no longer opens the vault), as on the desktop.
- **Signing out and turning it off** delete the key and the kept user key: the account's own, with several accounts on the phone, each with its own key (DESIGN.md, "Several accounts in the apps"). The core names the account in every call, and the key a prompt opens goes back to that account's unlock only.
- **The master password always works.**

## Copying

- **Android:** Kotlin takes the value from the core (the screen asks Kotlin to copy an item's field; the value never passes through Dart) and puts it on the clipboard marked sensitive (`ClipDescription.EXTRA_IS_SENSITIVE`, Android 13 and later), so the keyboard's clipboard preview and the system's copy notice don't show it. After 30 seconds it clears it if it's still ours. Android hides the clipboard from apps in the background, so there the app can't tell what's on it, and it clears it anyway: the 30 seconds are the promise.
- **iOS:** Swift puts it on the pasteboard for this device only (`localOnly`, so not Universal Clipboard) with a 30-second expiry (`expirationDate`), which iOS enforces even if the app is suspended.

## Autofill

The part that's most of the work, and native, because each OS draws its own lists.

**Android: an autofill service** (`AutofillService`), in Kotlin, in the app's own process.
- **Turning it on:** the app does it with the person, so nobody has to find it in Android's settings, and it never asks for an accessibility service. When the vault opens (after signing in, or any unlock) and PassBundle isn't Android's autofill service, a sheet, "Turn on autofill", offers a card: a row for autofill and, on Android 14 and later where Credential Manager exists, one for passkeys. Each row shows On with a check, or a Turn on button.
  - **Autofill's button** opens Android's own request to use PassBundle (`ACTION_REQUEST_SET_AUTOFILL_SERVICE` with the app's package, started for a result, which is how Settings knows the app asking is the one named). Android shows its list of services: the person taps PassBundle and confirms Android's "Use PassBundle?". On Android 15 and later that list is the one service for passwords, passkeys, and autofill, so the same choice turns on passkeys too. Where a phone's Settings doesn't have the request, the button opens Credential Manager's settings (Android 14 and later), then Settings itself; if nothing opens, the card says where to look.
  - **The passkeys button** opens Credential Manager's list of providers (AndroidX's `createSettingsPendingIntent`), where the person switches PassBundle on.
  - **What's on** comes from Android (`AutofillManager.hasEnabledAutofillServices`, and Credential Manager's `isEnabledCredentialProviderService` for PassBundle's provider), asked again whenever the app is back in front. Nothing turns on without the person's yes in Android's own screens, and unlocking is as it was.
  - The sheet comes after the offer of biometric unlock, and closes by itself once every row is on. "Later", or closing it, isn't asked again on that phone, and the vault says so then, with a Settings button: "You can turn on autofill in Settings any time." Settings shows the same card, under Autofill, whether it's on or not.
- The OS asks it to fill a sign-in screen in another app or in a browser. The service asks the core for logins matching the app's package name or the page's domain, with the same matching rules as the extension (the item's websites and its Android app URIs, `androidapp://<package>`). It answers with datasets: the item's name and username, which the OS shows in its list. The password goes into a dataset only when the person picks it, through an authentication step (below).
- **Locked:** one entry, "Unlock PassBundle". With fingerprint or face unlock on, picking it asks for that and then offers the logins, without leaving the app being filled. Otherwise (and when the biometric prompt's "Use master password" is picked, or its unlock is off now) it asks for the account's master password in PassBundle's own dialog (`FillActivity`, "Unlock PassBundle", naming the account when there's more than one), so the fill isn't lost:
  - The core unlocks that account with it, off the main thread, as the lock screen does (JNI `unlockWithMasterPassword`, `ffi::unlock_with_master_password`). A wrong one says so in the dialog and asks again; Cancel fills nothing.
  - Then it hands back the logins to pick from, as after a biometric unlock: nothing fills until one is picked, and each fills only from its own account. With "Immediately", the vault stays open for the pick only (below).
  - The dialog is PassBundle's own window over the other app: out of screenshots and recordings (`FLAG_SECURE`), with nothing drawn over it on Android 12 and later (`setHideOverlayWindows`), touches through anything that is ignored, and the field kept out of the keyboard's suggestions and learning (`IME_FLAG_NO_PERSONALIZED_LEARNING`). The dialog for a login that asks for the master password again is kept the same way.
- **Signed out** (no account on the phone): one entry, "Sign in to PassBundle", which opens PassBundle to sign in.
- **Which logins:** the core decides (`core/src/matching.rs`), by the rules the web vault and the extension use. Each of an item's websites can be set to match by its registrable domain (the default, by the Public Suffix List, so `a.github.io` never fills on `b.github.io`), its host, or never. The rules that need a page's whole address (starts with, exact, regular expression) aren't offered, since Android gives only the domain. Editing an item in the app keeps each website's setting.
- **Saving:** when the person signs in with something new, Android offers to save it to PassBundle. Accepting opens the app (unlocking first, if it's locked) to the editor, with the name, username, password, and the site or the app's `androidapp://` link filled in; nothing is saved until they tap Save. A new password for a login it has (one login for the same app or site, by the rules autofill fills with, with the same username) opens that login instead, with the new password, so changing a password doesn't make a second login. The sign-in stays in the app's process (autofill runs there), and Android's offer only opens the app, so no other app can hand the editor a sign-in. Android 14 before its March 2024 update can stop the app from opening itself there; then the sign-in waits, for up to 10 minutes, for the person to open PassBundle.
- **Apps aren't websites:** an app's package name matches an item only through the item's own `androidapp://` URI, never a lookalike name. A page's domain counts only from a browser, because any app can put a website's domain on its own views, or show the real site in a WebView of its own and read what fills ("AutoSpill").
  - **Browsers** are the ones on the list Android's Credential Manager uses (Google's privileged browsers, kept in the app as `assets/browsers.json`, every one of them in the manifest's `<queries>` so PassBundle can check it), checked by package name and release signing certificate, and any the person trusts on this device. A certificate the list also names for a debug build doesn't count, since debug keys can be public.
  - **Trusting one:** an app that opens web links and gives a page's domain gets one more entry in Android's list, "Logins for <domain>", which asks in PassBundle's own dialog whether to trust it as a browser.
    - The dialog shows the package name, the app's name made safe to show (one line, nothing that changes how it reads), and the domain only if it's a hostname. Trust can't be tapped for its first second, and touches through anything drawn over the dialog don't count.
    - Never offered to an app using a listed browser's package name without that browser's key.
    - Trusting keeps its package name and signing certificates in the app's no-backup folder (written atomically), so an app put in its place with another key isn't trusted; a browser that rotates its key, with Android's proof, stays trusted.
    - **Stopping:** Settings lists the browsers trusted on this device, by name and package name, each with Stop trusting. Without them, that app's pages get its own logins only, and the offer to trust it again.
  - **Filling checks again:** Android hands the app being filled the request that opens PassBundle's fill screen, so that app could send it again later. A fill goes ahead only if the login still matches the app, and its page if it's a browser trusted now.
  - **Other apps,** WebViews in them included, fill only their own `androidapp://` logins, and a sign-in saved from one is saved for the app.
  - **An app's own website, when both say so:** an app that names a site in its manifest (`asset_statements`, the way Android asks apps that share sign-ins with their sites to name them) gets that site's logins after its own, once the site's Digital Asset Links (`/.well-known/assetlinks.json`) name the app's package and signing certificate for sharing sign-ins (`delegate_permission/common.get_login_creds`). It's the check passkeys use (the core fetches the site's file itself: HTTPS, no redirects, 64 KB, 10 seconds), so an app can't take a site's logins by naming it, and a site can't hand its logins to an app that doesn't name it.
    - A site's logins are the ones a browser on that site gets (its registrable domain, by the usual matching rules), and each says which site it's from, as a browser's address bar would.
    - **A page the app shows itself** (a WebView: an in-app browser, say) gets a site's logins only if it's that site (or under it). A link opened inside the app is someone else's page, and it never gets the logins of the sites that trust the app.
    - Only the sites the app names are fetched (at most five, hostnames only), never anything from the vault, so fetching tells no one what's in it. A site does learn that this phone opened the app's sign-in form, as it does when Android checks the app's links at install; the fetch doesn't say it's PassBundle.
    - Answers are kept for a day, and a failed fetch for two minutes. A fill waits for a site's answer for two seconds at most; a slower site counts at the next sign-in form. While PassBundle is locked, the check starts anyway, for once it's unlocked. One check runs per site, app, and key at a time, a few at once, so an app asking again and again can't pile them up.
    - Filling checks again (fetching, if the day is up) before a password leaves the core, so a login it was once offered fills only if the site still names the app.
    - An app signed by several keys has no one certificate to name, so it gets none. PassBundle sees other apps' manifests and certificates through a `<queries>` entry for apps with a launcher icon.
  - Chrome (since version 135, with its "autofill using another service" setting) and Firefox pass the page's domain to autofill.
- **The core stays in the process:** the service runs in the app's process, so it shares the unlocked core with the app. When the app is locked, so is autofill.

**iOS: a Credential Provider extension** (`ASCredentialProviderViewController`), in Swift.
- It's a separate process with a tight memory limit, so it doesn't run Flutter. Its few screens (the matching logins, and the unlock screen) are native SwiftUI, drawn in our design.
- It links the same core, reads the kept vault from the App Group, and unlocks on its own (Face ID makes that quick), because it can't share the app's memory.
- **Beside the app, reading only** (November 2026): the extension opens the app's folder for reading (`pb_autofill_open`, `Accounts::open_beside`): the accounts `accounts.json` lists with a kept vault, in its order, with their names and colors, all locked. It never changes the folder (no `accounts.json` written, no account's folder removed, no install from before carried over, no policy's sign-out), because the app may be signing in or out of an account in the same folder meanwhile, and a sign-in part way through has no vault yet, which the app's own start would take for one given up. The refresh tokens it could read are in the Keychain group the two share; filling a password needs none.
- **Several accounts** (DESIGN.md, "Several accounts in the apps"): it asks to unlock the account the app shows (or the account of a suggestion picked above the keyboard), with that account's Face ID at once where it's on, else its master password; "Switch account" unlocks another instead. Then the website's logins come from each account unlocked here, the app's shown one first, each labeled with its account's name in its color when there's more than one, and "Other accounts" unlocks the rest. Each unlock is that account's own: its Keychain item and its own Face ID prompt, or its master password, so one prompt never opens two accounts. A login fills only from its own account (`pb_fill_secret`, naming the account), and searching looks through every account unlocked here.
- A login that asks for the master password again asks for it on the extension's own screen before it fills: its own account's.
- **Locking:** the extension holds a vault for one request. As the request ends (a fill, Cancel, or the sheet swiped away), every account locks, its keys and everything decrypted wiped, and the core lets them go (`pb_autofill_close`), since iOS may keep the process for the next request. There's no wait to count there, so the core doesn't check one for the extension.
- **Suggestions above the keyboard:** after each sync the app gives iOS each login's username and the domains it fills on, by the same matching rules (`ASCredentialIdentityStore`), never passwords, so iOS can suggest a login. They come from every unlocked account, each naming its account and item (`<account>/<item>`), and replace what iOS had: after each sync, once AutoFill is turned on, and once an account is signed out of, so iOS forgets that account's. A locked account's go when another's replace them, and come back after its next unlock. Picking one opens the extension just for that account's Face ID, which then fills that login: the extension's process starts locked, so it can't fill without the person.
- **Turning it on:** the app does it with the person, as on Android ("Turning it on" above): after unlocking, and after the offer of Face ID, a sheet "Turn on AutoFill" offers its card, whose Turn on opens Settings' own page for AutoFill providers (`ASSettingsHelper.openCredentialProviderAppSettings`, iOS 17 and later), where the person switches PassBundle on. iOS says whether it's on (`ASCredentialIdentityStore`'s state), asked again whenever the app is back in front; once it's on, the app gives iOS its suggestions then. "Later" isn't asked again on that phone, and Settings has the same card under AutoFill.
- **Passkeys** are in the same extension (below).

## Passkeys

The core signs and makes passkeys (`docs/core.md`, "Passkeys"); each OS asks for them its own way. Both providers are built; iOS's runs in Safari only from a signed build ("Order and tests" below).

**Android: a credential provider** (`CredentialProviderService`, from AndroidX's `credentials` library, Apache 2.0), in Kotlin, in the app's process like autofill.
- **Android 14 and later only.** Earlier versions take passkeys only from Google's own provider.
- **Turning it on:** the card's passkeys row, in the step after unlocking and in Settings (Autofill, "Turning it on").
- **Signing in:** Android asks first what PassBundle has for a site (`onBeginGetCredentialRequest`). It answers with the site's passkeys by account name (only those the site can find by itself, discoverable ones, when it names no credential, as WebAuthn has it), or "Unlock PassBundle" while it's locked (unlocking as autofill does, then the list). Picking one opens PassBundle's own screen (`PasskeyActivity`), which asks for a fingerprint or face unlock when the site wants proof or prefers it (the master password when biometric unlock is off and the site requires it, or for a login that asks for it again), then has the core sign.
- **Who's asking:** a browser on Google's privileged list (the one autofill uses, `assets/browsers.json`, checked by signing certificate) gives the page's origin and the client data hash, and the browser has already checked the site's ID against the page. Any other app is checked against the site's Digital Asset Links: the core fetches `https://<site>/.well-known/assetlinks.json` itself (HTTPS, no redirects off the site, at most 64 KB, 10 seconds) and goes on only if it names that app's package and signing certificate for `delegate_permission/common.get_login_creds`. The answer is kept in memory for a day. Then the provider builds the client data with the app's origin (`android:apk-key-hash:` and the certificate's SHA-256). With a browser's hash, the response's `clientDataJSON` is a placeholder, as Android's guidance has it. The screen checks who's asking again; it never trusts the earlier list.
- **Making one:** Android asks where to save a new passkey (`onBeginCreateCredentialRequest`). PassBundle offers itself; its screen checks who's asking, asks "Save a passkey in PassBundle?" naming the site's ID first (and the name it gives itself only after), proves who they are as for signing in, and the core makes it in a new login for the site, saved before Android hears of it. Choosing an existing login is not yet.
- **Browsers the person trusted for autofill don't count here.** An unlisted app can't give Android a page's origin, so it's checked as an app.

**iOS: the AutoFill extension** (iOS 17 and later), the same one that fills passwords.
- It says it provides passkeys (`ProvidesPasskeys`), and iOS hands it the site's ID and the client data hash, having checked the app's associated domains or Safari's page itself.
- **Suggestions:** after each sync the app gives iOS each passkey's site, account name, credential ID, and user handle (`ASPasskeyCredentialIdentity`), never a key. iOS lists them in its own passkey sheet, and the extension opens only when one is picked.
- **Signing in and making one:** the extension unlocks as for passwords, asks for Face ID when the site wants proof and it wasn't just given, and answers with `ASPasskeyAssertionCredential` or `ASPasskeyRegistrationCredential`.
- **Several accounts** (November 2026): the site's passkeys come from each account unlocked in the extension, labeled as its logins are, and each signs with its own account (`pb_passkey_assert`, naming it). A suggestion picked from iOS's sheet names its account and item (`<account>/<item>`), and the extension unlocks that account for it. Unlocking there, with that account's Face ID or its master password, is the proof a site asks for. Saving a new passkey names the site's ID first, then the account on the site, and with more than one account unlocked there, asks which PassBundle account it goes in ("Save in"); it's saved in a new login there, on the server, before iOS hears of it, and iOS lists it at once.
- **Never syncing beside the app:** saving a passkey, or a passkey's raised counter, goes to the server, and the app's next sync brings it into the vault the app keeps. The extension never syncs (`App::sync` refuses beside the app), so it never writes the app's kept vault in the App Group folder, and never forgets the session the app shares with it.

**Tests:** the core's Digital Asset Links checks (which statements let which app, which site IDs may be fetched, the day's memory); on the emulator, the autofill test app makes a passkey and signs in with it through Credential Manager, checking what comes back as a site would (its challenge, its own origin, the site's ID, and the signature with the passkey's public key). Debug builds read the test site's asset links from a file in the app's folder instead of fetching them, as they stand in for the biometric prompt; release builds always fetch. On the simulator, the extension's own tests sign in with the sample vault's passkey and check the answer against the core's vectors byte for byte, and check that making one asks which account it goes in ("Order and tests" below); the AutoFill test's page does what the emulator's does, in Safari, once builds are signed.

## Approving a sign-in

The same as on a computer (`docs/core.md`, "Approving a sign-in"; DESIGN.md, "Approving a sign-in from another device"): someone choosing "Sign in with a device" on the web vault or in the browser extension approves it on the phone, after comparing the fingerprint phrase.

- **When the phone shows a request:** while PassBundle is open and unlocked, it asks the server every 10 seconds, and shows each new request once. When it opens and unlocks, it asks at once, so a request made while it was closed shows then (after the offer to unlock with a fingerprint, if that comes first). Settings lists every request waiting.
- **Not while it's closed:** a notice on a closed phone needs push notifications (APNs on iOS, FCM or UnifiedPush on Android), and those wait on PassBundle's own push service, which doesn't exist yet. Until then, someone signing in with a device opens PassBundle on the phone to see it. The server already sends upstream's notice to push when it's set up for that, so it's the delivery that's missing.
- **Confirming it's you** (on until Settings turns it off, which asks for it too): the phone's own fingerprint or face, through the same Keystore key or Keychain item that unlocks the vault, in a prompt of the approval's own, saying "Approve sign-in" (`biometricConfirmApproval` on the app's channel). Kotlin opens the user key from the Keystore after the prompt (Swift reads it from the Keychain) and hands the bytes straight to the core's call for confirming an approval (`confirmApprovalWithKey`, `pb_confirm_approval_with_key`), never its unlock call, then zeroes them, as biometric unlock does; the core takes it only if it's the open vault's key. The key never reaches Dart. Unlocking, and a passkey's check that it's the person (which also uses that prompt), never confirm an approval. "Use master password" in the prompt, or no biometric unlock, asks for the master password instead.
- **Nothing new is kept on the phone:** the requests are in memory while unlocked; the user key leaves the core only wrapped to the request's own public key.
- **New-device checks** (DESIGN.md, "New-device check") show the same way, while PassBundle is open and unlocked: typing the number the new device shows approves it, a wrong number denies it, and no fingerprint or face is asked, since no key goes. Push while PassBundle is closed is still not built.
- **The phone as the new device:** its first sign-in to an account on it, without two-step login, shows the number and waits while PassBundle is open. If PassBundle closes meanwhile, signing in again starts a new check with a new number: a check has one holder, the copy of the app that has its token. Each account keeps a device token of its own, kept at sign-out.

## Locking

- **Lock after a time away:** phones have no "idle time" for the whole device, so the wait counts from when the app leaves the screen. The choices are the desktop's (1, 5, 15, or 30 minutes, 1 or 4 hours), plus "Immediately", which phones' password managers offer because people switch apps all the time. The default is 5 minutes.
- **When the phone locks** (on by default): Android's screen-off broadcast; iOS's notice that protected data is about to become unavailable.
- **Back in front:** the app checks the wait the moment it's shown again, before the vault is in front of anyone.
- **Out of screenshots:** the vault stays out of screenshots, screen recordings, and the app switcher's preview (`FLAG_SECURE` on Android). iOS doesn't let an app leave itself out of a capture, but it says while the screen is recorded, mirrored, or shared (`sceneCaptureState`, iOS 17), and for that long the app switcher's cover stays over the vault, saying why (passbundle-apps#76). A screenshot can't be stopped on an iPhone, by any app.
- **On Android, autofill follows the app's lock;** on iOS the extension locks when it closes. Autofill and passkeys can unlock with biometrics while the app's screens aren't running, or show the vault as locked, and then nothing on the screens asks whether it's time to lock. So the core checks the wait itself before each fill, copy, passkey, and master password check from the phone's native code (counting from that unlock, or from when the app last left the screen), and the screen-off broadcast is heard for the whole process (`Core.start`), not only while the screens run (security pass, November 2026).
- **"Immediately" and autofill on Android:** "Immediately" (the person's, or an organization's policy) has no wait to count, so it locks as PassBundle's own screens hand back their answer, the way leaving the app does. A login's values handed to the other app, and a passkey's sign-in or new passkey (or a refusal) handed back to Android, lock the vault at once (`Core.answered`). Unlocking from Android's list ("Unlock PassBundle") hands back a list to pick from, so the vault stays open for the pick only (`Core.offered`): it locks when the pick's fill is handed back, or a minute later if nothing is picked, by either clock, the phone asleep or not. A pick that didn't fill (cancelled, or refused) leaves that minute as it is, for another pick. The app's own screens, opened and used meanwhile, have the vault as usual, and leaving them locks it.

## Order and tests

1. **Android first:** its emulator runs in CI on Linux, autofill included.
   - The core built for Android, and its tests run on the emulator (the test programs pushed with `adb`).
   - The app on the emulator: sign in, unlock, browse, copy, lock.
   - Then the Keystore, biometric unlock, and the autofill service, each with tests on the emulator.
     - Biometric unlock: debug builds have a stand-in for Android's prompt that says yes, with a Keystore key that needs no biometrics, as the desktop agent's test authenticator does. Release builds refuse it. Everything but the OS prompt is tested: sealing the user key, unlocking with it, and signing out removing it. The real prompt gets checked by hand on a real phone, because enrolling a fingerprint on an emulator means typing a PIN into Android's own prompt.
     - Turning autofill on: debug builds record what the card's buttons would open instead of opening it, so the emulator test checks, without Android's real screens, that the step shows after unlocking (with the passkeys row only on Android 14), that Turn on asks for Android's request for PassBundle, started for a result, and that on Android 14 the passkeys button sends Credential Manager's settings. The app's own tests cover what the card shows on each version, a row turning On when the app is back in front, and "Later".
     - Autofill is driven with a small test app that has a sign-in form (`app/android/autofilltest`): PassBundle, signed in and locked with biometric unlock on, offers to unlock, then the login, and fills the form. With biometric unlock off, "Unlock PassBundle" asks for the master password in PassBundle's dialog (a wrong one says so there), then offers the login, which fills only once it's picked. JVM tests (`UnlockingTest`) cover what's offered (signing in, unlocking, the logins) and how a locked account unlocks. On the test app's screen that says it's a bank's website, only the app's own login is offered, with the offer to trust the app as a browser; once trusted, the website's login fills. Settings then lists the test app, and once it's no longer trusted there the website's login isn't offered again.. The test app names two sites in its manifest: its login for the one whose asset links name it back is offered and fills; the one whose name another key, and a website it doesn't name, aren't offered. In the app's own WebView, a page on another site doesn't get the linked site's login, and the linked site's own page does (debug builds read the test sites' asset links from a file, as for passkeys). (Android 10 doesn't pass a web domain an app sets on its own views, so these website steps run on Android 11 and later: CI's Android 14 emulator.)
2. **iOS second:** CI's Macs build it and run it in the simulator: the core's tests, and the app's own tests with debug builds' stand-in for the Face ID prompt, as on Android, including the AutoFill step after unlocking (debug builds record that Settings would open instead of opening it). The AutoFill extension is tested the way someone uses it (`tools/ios-autofill-test.sh`): Settings turns PassBundle on for AutoFill, and Safari, on a sign-in page served over HTTPS as `phone.example.test` (with a throwaway authority the simulator trusts), fills it from iOS's suggestion above the keyboard. The app's half and the script's talk through files in the App Group folder.
   - **Until builds are signed:** iOS's AutoFill entitlement has to be allowed by a provisioning profile, which needs an Apple Developer account, and the simulator's Settings doesn't offer a provider from an app signed ad hoc, as CI's builds are now, though iOS has it registered (turning it on through PlugInKit doesn't make iOS ask it for logins either; tried October 2026). So CI checks what it can: the extension is built with its entitlements (in its signature) and the core, iOS has it registered, and the app signs in with Face ID unlock on and gives iOS its suggestions; then it stops before Safari. With a signed build the same script goes all the way, passkeys included. The core's own tests cover opening beside the app (`core/src/accounts.rs`).
   - **The extension's own code** is tested without iOS handing it a request (`tools/ios-autofill-screens.sh`, `app/ios/AutoFillTests`): in a bare host app that's never shipped, the tests drive its screens and the core under them as iOS's requests would, on two accounts kept as the app keeps them. Each account unlocks on its own, and a wrong master password says so; logins are labeled by account and fill from their own; a suggestion picked unlocks its account with that account's Face ID item (debug builds' stand-in); a passkey signs as the core's vectors say; making one asks which account it goes in; and nothing in the app's folder changes. CI keeps the screens they draw (the iOS job's `ios-screens` artifact).
3. **Real phones:** a check by hand at each release, as for Windows Hello. Store listings, signing keys, and the Apple Developer account are the owner's.

## Not yet

On iPhone, everything that needs an Apple Developer account: AutoFill and passkeys anywhere but the simulator's own tests (iOS takes a provider's AutoFill entitlement only from a provisioning profile), security keys and YubiKey codes over NFC at sign-in (NFC's reader and Associated Domains entitlements), a sign-in request's or new-device check's notice while PassBundle is closed (push needs APNs, besides our own push service), and App Store or TestFlight signing; and by hand on a real iPhone, the real Face ID prompt and the screen-capture cover. Elsewhere: a sign-in request's notice while PassBundle is closed on Android (push), Wear OS and watchOS, tablets' own layout (they get the desktop layout when wide enough), and sharing from other apps into a new item.
